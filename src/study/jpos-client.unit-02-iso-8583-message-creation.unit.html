The client from unit c1 passes all its tests. On its first morning against the acquirer's test host, two purchases in a batch come back as null when their timeout runs out. The host never received the first and approved the second. Nothing in the client threw an exception.

Both failures come from one line that set a 17-character merchant ID in a field that holds 15. The unit has six rules for building requests, one per section heading.

An ISOMsg Holds Strings, and the Packager Decides the Bytes

An ISOMsg is a map from field numbers to values (unit c6 covers its API). It knows nothing about field formats. Only when a packager packs it do the values become bytes, and only then is anything checked. Here is a purchase with a short amount and a short STAN, packed with the course's packager (jar:packager/iso87ascii.xml) and unpacked as the host would:

The host echoes field 11 in its response. Does "731" equal what comes back?

It doesn't. The packager pads a short numeric field with zeros on the left, so the host receives and echoes 000731 while your ISOMsg still says 731. QMUX pads field 11 itself when it matches the response (unit c12), so the response still arrives. But code that stores the STAN with the transaction and later looks for "731" finds nothing. Set every fixed-length numeric field at its full width (ISOUtil.zeropad), and the message in memory is the message on the wire.

Besides padding, the packager refuses a value that is too long, and checks no content at all:

An amount written as "25.00" went out as 000000025.00: twelve characters, so it fits, and nothing in jPOS complains. Field 4 holds the amount in the currency's minor unit: 25.00 dollars is 2500, sent as 000000002500. Unit c13 covers what each field packager checks.

A Message That Doesn't Pack Fails on the Channel Thread

In production your code hands the message to a MUX, and the channel packs it on its own thread just before writing it to the socket.

We ran a real client in one JVM: the ChannelAdaptor and QMUX of unit c1, connected over 127.0.0.1 to a QServer that approves everything. A good purchase gets its 0210. Then we send one with the 17-character merchant ID (purchase(stan, amount, merchantId) is a test helper that fills in the other fields):

request didn't throw. It waited the full five seconds and returned null, as it does when the host is slow. The client's log has a warning:

The log then shows the server's session ending and a new one starting. In 2.1.7 the ChannelAdaptor's sender treats an ISOException from send as a broken link: it disconnects, and the adaptor reconnects after its reconnect delay.

Now suppose another purchase is in flight. We sent purchase 000103, which the host answers after 800 ms, and 200 ms later purchase 000104 with the long merchant ID:

The host approved 000103, but the client had closed the socket, so the approval never arrived:

  • 000104, the bad one, never left the client. Its caller sees null.
  • 000103, the good one, went through, and the cardholder's money moved. Its caller also sees null.

Unit c12 shows that null means "you don't know" and the client must reverse both. One reversal undoes a real purchase. The other carries the same bad merchant ID, so it fails to pack too and takes the link down again.

The fix is to pack the message yourself, with the channel's packager, before it goes to the MUX. Then a failure is an exception in your code, and you know that message was not sent:

For fields your code builds itself, a unit test that packs every message type is enough (2.3 shows one). For values from outside, such as a merchant record or a terminal's input, pack before you send. Building and packing a purchase took about 1.5 microseconds.

Keeping the link up. The ChannelAdaptor element <ignore-iso-exceptions>yes</ignore-iso-exceptions> stops the disconnect. With it, the in-flight purchase got its 0210, and the bad one still returned null after five seconds. It limits the damage but doesn't tell your code what happened.

The Fields Every Request Shares Are Set in One Place


Every message a client sends carries fields that have nothing to do with what it asks for: when it was sent (field 7) and its number on the link (field 11). Card requests also carry the terminal and merchant (fields 41 and 42). jPOS 2.1.7 has no class that builds requests, so you write one. Field 7 Is GMT, Whatever the Server's Time Zone


Field 7, the transmission date and time, is MMddHHmmss (24-hour clock) in GMT. jPOS's helper for it has two forms. The same instant, 23:30 GMT on 5 November, on four servers:




The one-argument form formats in the JVM's default zone. On a laptop set to UTC, both columns agree and every test passes. On a server in New York, every message claims to have been sent five hours early; in Tokyo, nine hours late and on the next day. A host that checks field 7 against its own clock sees requests from the past or the future, and a reversal copies the wrong time into field 90 (unit c12).


The factory in 2.3 formats in ZoneOffset.UTC, so its test expects 1105233000 even from a New York clock.


Fields 12 and 13, the transaction's time and date, hold the terminal's local time instead.


The STAN Is One Sequence per Link


Field 11, the System Trace Audit Number, is the sender's number for a message. With field 41 it is how QMUX matches a response to its request, and a request with the key of one still waiting is refused with a Duplicate key exception (unit c12). So two requests in flight on one link must never share a STAN. Three common ways to pick one, simulated over a million requests on a link that starts ten per second and has 20 in flight at any moment:



The counts are requests whose STAN was still in use by one in flight. A random STAN collided 17 times in a million, rarely enough to pass every test, and about twice a day on a link that carries 100,000 requests a day. The time of day collides whenever two requests start in the same second, which at ten per second is nine times out of ten. A counting sequence never collides, because a number comes back only after 999,999 others.


The sequence wraps from 999999 to 000001, and the obvious way to write that gets it wrong:



The factory computes (n - 1) % 999999 + 1, which never gives 000000. Many host specifications reject a STAN of zero, so check yours.


One sequence per link means every message on it, echoes included, takes the next number from the same counter, as the 0800 did in 2.3. In a running Q2 application the counter lives in a Space: SpaceUtil.nextLong(space, "stan.host") increments it atomically, so every thread that sends on the link shares it. Unit c4 puts it in a persistent space so a restart doesn't start again at 1.

Mask What You Print, Never What You Send


The factory prints the PAN as 411111______1111 with ISOUtil.protect, which works on a copy of the string, never on the message:




Put the masked PAN into the message "to be safe", and the host receives a card number that doesn't exist and declines it. Call dump on a request in your own logging, and the clear PAN lands in a log file, which then falls under the same rules as your card database. Summary


  • An ISOMsg holds strings, and the packager decides the bytes. It pads short numerics and refuses long values only when it packs, and never checks content. Set numeric fields at full width and amounts in minor units.
  • A message that doesn't pack fails on the channel thread. request returns null after the full timeout, and the 2.1.7 adaptor drops the link, losing answers to other requests in flight. Pack with the channel's packager before you queue.
  • The shared fields are set in one place: your own factory with an injected clock and counter, tested by packing every message type.
  • Field 7 is GMT. Format the instant in UTC; never rely on the JVM's default zone.
  • The STAN is one counting sequence per link, 000001 to 999999 and around again, shared by every message type. Random and time-based STANs collide.
  • Mask what you print. The message keeps the real PAN; dump prints it in clear.

Challenges


  1. Your merchant records come from another team's database. Do you pack-check the messages built from them when a record is loaded, when a message is built, or just before it is sent? What does each choice cost when a record changes during the day?
  2. A link carries 50 requests per second at peak, and a request waits at most 30 seconds. How long until the sequence comes back to the same number, and how many requests are in flight at once? What would make a counting sequence collide after all?
  3. Two client instances share one terminal ID on one link, each with its own Space counter. What happens on the first morning? Design a counter both can share.
  4. A host wants field 7 in its local time, against the standard. Where in the factory does that belong, and how do you keep a test from passing on a laptop in that zone?


Design Note: Why Doesn't ISOMsg Check Anything?


An ISOMsg doesn't refuse a 17-character merchant ID when you set it, because it doesn't know its fields' formats. Field 4 is twelve ASCII digits in iso87ascii, six bytes of BCD in a binary packager, and a network may define it differently again. The format belongs to the link, and an ISOMsg can travel between links: a gateway reads it from one channel and sends it on another.


The price is an error that appears late, on a thread that isn't yours. GenericValidatingPackager can also check content (unit c13), but in 2.1.7 pack never runs those checks; they run only when your code calls the packager's validate. So whoever builds a message packs it once, with the packager of the link it is going to, before anyone else has to find out.
