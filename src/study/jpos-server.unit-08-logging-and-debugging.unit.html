A merchant calls about a 900.00 purchase from terminal 29110001, refused with 61 (exceeds amount limit) at 20:11. Their limit is 5000.00, they say, so why? You open the server's log. The TransactionManager wrote one event for the purchase, and it names the participant that refused it. It doesn't say which amount that participant read, which limit it applied, or whether someone typed the limit wrong.

The server's logger is the one of unit c1, with ProtectedLogListener first. Unit c8 explains how events reach it and what the filter can mask, and unit s1 turned off the TransactionManager's Context dump (debug-context) because the filter can't mask it. On top of that, a server has to write enough to explain a refusal, a slow purchase or a hung transaction: five rules, one per section heading.

Every output comes from jPOS 2.1.7: a real Q2 and TransactionManager in one JVM, fed by unit s4's DirectTerminal, with the logger above and the dump off.

The Transaction Event Says Who Voted, Never Why

The participant that refused the purchase does what units s4 and s6 do with their reasons: it notes them in the Context.

Responses.reply is unit s4's helper. The chain is this participant, then Approve, which puts a 00 response in the Context, then SendResponse, and the descriptor sets max-amount to 50000. We sent 120.00 and 900.00. Before you read the log, where do you expect "over limit" to appear?

It appears nowhere. The event lists the participants that ran (c.e.j.s.p. is com.example.jpos.server.participant) and their votes. ctx.log writes into a LogEvent kept in the Context, which is printed only in the Context dump. The status line comes back in 8.5.

The descriptor had max-amount at 50000 minor units, 500.00; the merchant's contract says 5000.00. To learn that, you repeat the purchase on a test system with the dump turned on, ticket by ticket. The one reason the TransactionManager does write is an exception that escapes prepare, as a <warn> (unit s6). Unless an earlier participant put a response in the Context, the terminal then gets no answer.

A Participant Writes Its Own Event, and Only If Its Element Names a Logger

The participant has to write the reason itself, in an event of its own:

Extending org.jpos.util.Log makes it a LogSource. The TransactionManager builds each participant through Q2's factory, and the factory calls setLogger with the logger and realm of the <participant> element, but only when the element has a logger attribute:

We sent the same two purchases with this element, then with logger and realm removed, then with only realm removed. The first time the log holds a check-amount event for each purchase (8.3 shows one), and the TransactionManager names the participant with its realm:

Without logger, the participant ran and refused the second purchase with 61, and the log has the TransactionManager's events and nothing from CheckAmount. Unit c8 showed why: an event created by a Log that has no logger goes nowhere, and nothing reports it. A participant can pass every test, where the test calls setLogger itself, and write nothing in production because of one missing attribute. Without realm, the events come out under the element's name, participant. Every participant that leaves realm out shares that name, so a realm filter (unit c8) can't tell them apart. Give every participant that logs both attributes.

One Event per Transaction, Carrying Its Id and the Message Itself

The support desk knows the terminal and the STAN, 000302. Here is the participant's event for it, followed by the TransactionManager's:

The last line of the first event answers the ticket: the limit in the descriptor is 500.00. The numbered lines in CheckAmount make that possible:

  • (1) One event per transaction. Everything the participant learned about this purchase is in one block. With two or more sessions, events written one per step interleave with other transactions' steps, as unit c8 showed for a client. Create the event inside prepare: one participant instance serves every session (unit s1), so an event kept in a field collects other transactions' messages.
  • (2) The transaction id. txn 2 matches the :2 on the TransactionManager's first line. The TransactionManager's event carries no message, so the id is what joins the two: search for the STAN, read the id beside it, and find the votes and timings of the same transaction.
  • (3) The message as an object. The filter masked field 2 because the ISOMsg itself is in the event. It replaces each ISOMsg with a masked copy and leaves every other entry, an exception included, as it is. A string such as "card " + request.getString(2), or the Context, would reach the writer in clear (units c8 and s1).
  • (4) Written in finally. A refusal, an approval and an exception each leave one event. A participant that logs only its refusals leaves no trace of the approvals that should have been refused.

Problem statement

The support desk has a run of tickets about cards refused with 54 (expired card), and a few with 30, from cardholders whose cards are valid until next year. The server's log has the TransactionManager's events and nothing else: prepare: c.e.p.CardExpiry ABORTED. Nobody can tell which expiry date the server read, or which month it compared it with.

Write prepare in src/main/java/com/example/practice/CardExpiry.java. refusal already decides and reply builds the answer: 54 for an expired card, 30 for an expiry that can't be read.

When you're done, an operator who has a terminal ID and a STAN finds in the log one entry for every purchase this participant handled, whether it let it through, refused it, or couldn't read it, with what it decided and why. From that entry the operator can find the TransactionManager's event for the same transaction. The log is shipped to a platform that a few hundred people can search. About 15 lines.

The tests call the participant directly. They give it a logger whose chain is the production one, ProtectedLogListener and then a writer, the way logger="Q2" realm="card-expiry" would under Q2. The current month is fixed at November 2026.

The TransactionManager Times Participants; a Profiler of Your Own Times the Steps


A terminal reports that purchases take three-quarters of a second. The chain starts with NotedCardLookup, and the TransactionManager's <profiler> gives each participant's time and the running total, in milliseconds:



The time is in NotedCardLookup, which makes three lookups: the card, the blocked-card list and the card's limits. Its author marked each with ctx.checkPoint("card found") and so on, and none of them appear here. Like ctx.log, ctx.checkPoint writes into the Context, so its output shows only in the dump. With the dump turned on, on a test system:



Even there, the first step shows 0.0 ms. The Context creates its profiler at the first checkPoint, so the first step ran before the profiler existed.


A participant whose steps you want timed in production starts an org.jpos.util.Profiler of its own and adds it to its event:




The blocked-card list takes 600 of the 722 ms, so that is the query to fix. This profiler is created before the first step, so it times that step too, which the Context's profiler can't.


A Transaction That Never Ends Writes Nothing, and the Ones After It Show Where It Is


The TransactionManager writes its event when a transaction ends. We ran two sessions. The participant demo.IssuerCall stands in for a call to an issuer with no timeout: for terminal 29110077 it waits on a latch that nobody releases. That terminal sent a purchase, then 29110001 sent five more. The five were answered 00, and 29110077 got no answer. There is no event for transaction 1, no error and no warning. The events of the five carry the TransactionManager's status line:



head is the id the next transaction gets, and tail the oldest one that hasn't finished. head moves with every purchase while tail stays at 1. The first number of in-transit says one transaction is running, and the second counts how far tail is behind head. Transaction 1 is stuck.


To find where, read the threads. A session renames its thread while a participant runs, and SystemMonitor (unit c8) lists every thread in the event it writes every sleepTime:



The name gives the transaction, the phase, the participant and the time it started. A jstack of the process shows the same names, with the line each thread is waiting on.


The TransactionManager has no timeout for a participant, so the session is held for as long as the call hangs, possibly until a restart. That was half of this server's sessions. A second hung call takes the other one, and every request then waits in the queue until the listener's timeout drops it (unit s1), and terminals reverse purchases that never ran. Put a timeout on every call a participant makes (unit s4), and watch tail.


When a server stops answering, read in this order:


  1. <warn> events from Q2.system and the TransactionManager: a component that didn't start, or a participant that threw (units s1 and s6).
  2. The status line: tail, and outstanding (unit s4).
  3. The thread list: a session that has been in one participant for too long.
  4. The QServer's session-start and session-end events (realm iso-server.server.session/<address>): connections opening and closing in a loop are clients giving up on you.

Summary


  • The transaction event says who voted, never why. ctx.log and ctx.checkPoint go into the Context and appear only in its dump, which is off wherever real cards flow.
  • A participant writes its own event, as a Log whose <participant> element has logger and realm. Without logger its events vanish silently; without realm every participant shares the realm participant.
  • One event per transaction, created in prepare, with txn <id> to join it to the TransactionManager's event, the ISOMsg itself for the filter to mask, and Logger.log in finally.
  • The TransactionManager's profiler times participants. To time the steps inside one, put a Profiler of your own into its event.
  • A transaction that never ends writes nothing. tail stops while head moves, and the session's thread name gives the transaction and the participant. A hung call holds a session until it returns.

Challenges


  1. Your chain has six participants, and each writes one event per transaction. At 200 transactions a second, how many events is that a day, and which would you keep if the log platform charges by volume?
  2. Design an alert from the status line alone: which values, over what period, mean a stuck transaction rather than a busy server? How does a paused transaction (unit s4) change it?
  3. Operations ask for the reason of every refusal in a nightly report. Is the log the right source, or should the participant write somewhere else too? What does each choice cost when the participant itself fails?
  4. CardLookup's profiler shows 600 ms in one query on most transactions and 5 ms on a few. What would you add to the event to find out what the fast ones have in common, without logging card data?


Design Note: Why the TransactionManager Logs Votes and Not Reasons


The TransactionManager doesn't ask participants for a reason. The return value is the whole contract, the same for a limit check, a database write and a call to a host. What a reason looks like, and what may be printed safely, is known only inside the participant.


ctx.log looks like a way around that, but it puts the reasons inside the Context, and the Context is the one object a server can't log safely in production. So the participant writes its own event, at the cost of a few lines in each participant and one attribute in each element.
