The acquirer's support desk opens a ticket. Their host rejected your purchase with STAN 000913 at 10:15 with code 30, format error, and they attach the bytes it received, dumped with the Unix tool hexdump -C. You want a failing test built from their bytes, so that nobody has to argue about what the message "looked like".

You paste the attachment into a test, read it with ISOUtil.decodeHexDump, unpack it with your packager, and the packager blames field 62. The purchase has no field 62.

Getting from the evidence you are handed to a message you can test and compare, without putting card data in the log, comes down to six rules, one per section heading.

A Dump Is Evidence Only When It Reads Back to the Bytes It Shows

The attachment, the same 99 bytes as our client packed them, and what our packager makes of each:

ISOUtil.hexdump (unit c8) writes a four-digit offset, eight digits only past 64 KiB. What will decodeHexDump do with an offset of eight digits?

decodeHexDump knows one layout, the one ISOUtil.hexdump writes: four characters of offset, two spaces, then up to sixteen hex pairs. Given eight digits of offset, it strips nothing and reads each line's offset as four bytes of data, the final 00000063 line included. It also takes at most sixteen pairs from a line, so it drops the last real byte of every full line. The 99 bytes become 125 (99, less 6 dropped, plus 8 offsets of 4 bytes). They begin with four zero bytes where the MTI should be, and the packager fails at field 62, which the host never saw.

A dump with a line missing is worse, because nothing about it looks wrong. Lines go missing when a dump is copied out of a mail client or a chat window. decodeHexDump joins the 83 bytes left, and the packager blames field 52, the PIN block. Neither error is the real problem, which 17.3 finds: the purchase has no currency code (49=null).

Ask the acquirer about field 62 and they answer that there is no field 62, and the ticket has lost a round trip between two companies. A dump from outside needs a reader that checks it:

  • Each line's offset is the number of bytes read before it. That catches a missing or repeated line on the spot: 0030 right after 0010 means 16 bytes were lost.
  • Bytes come from their columns. The text column is never data, even when it looks like hex: a field holding the text AB 12 CD shows exactly that in the text column.
  • The layout is recognised, not assumed. Four or eight digits of offset, a text column with or without bars, a final line with only the offset (00000063 is the length, 99, in hex).

Our own logs need the same care. When a channel can't unpack what it read, its receive event ends with the bytes (17.6 shows the whole event), and the writer indents only the first line:

Copied as it stands, the indent hides the offset from decodeHexDump, which reads two bytes of the offset as data and drops the line's last byte: these two lines decode to 33 bytes, starting 0000, instead of 32. A reader that skips leading spaces handles it, and the offsets prove nothing was lost on the way.

A Logged Message Gives Back the Bytes Only After You Put Back What the Log Masked


Our own log of the same purchase, written through ProtectedLogListener as in unit c8, is a second piece of evidence. XMLPackager reads the <isomsg> block that ISOMsg.dump writes, so the log seems to hold the message already. What will the masked fields do when it is packed again?




(1) The message still has the XMLPackager it was unpacked with, so pack() writes XML again. Set your own packager first.


(2) The wiped PIN block comes back as the four bytes AA55AA55, and field 52 must be eight. This error at least tells you what the log took away.


(3) The masked card number fails silently. 411111______1111 has the right length, and the numeric field packager doesn't check that a value is digits when it packs, so the message packs to 99 bytes, but not the ones that were sent. A test built from them reproduces a message nobody sent, and if it passes, you close the ticket on the wrong evidence.


(4) With a test card in field 2 and a test PIN block in 52, the bytes are the ones that left. They match exactly here because our purchase carried those test values. For a production ticket, put back test values of the same length: every length, prefix and position then stays as the host saw it, and that is what a format error is about.


For every field your protect and wipe lists name, put a test value back before you pack. Don't ask for the unmasked log instead; that only moves the card data into your test suite.


Two Messages Are Compared Field by Field, and Binary Fields by Content


The same terminal had a purchase approved yesterday, and the support desk sent its bytes too. What is different about today's?


The quick answer compares the values of both messages' fields with equals:



Two of those six lines are noise. An unpacked message keeps the bitmap it read under key -1, and the bitmap only restates which fields are present. Field 52's value is a byte[], and two arrays are equals only when they are the same object, so equal PIN blocks are reported as different. With twenty fields and a few binary ones, the real difference hides among false ones. Had the card numbers differed, both would have gone into the ticket in clear.

On the same two purchases, and then on two messages built in a test with a nested field 48 and different cards:



The amount, the transmission time and the STAN differ on every purchase. Field 49 is the difference that matters: today's purchase went out without its currency code, and that is the format error.


  • The bitmap is left out. It is recomputed at pack time.
  • Binary values compare by content, with Arrays.equals, and print as hex.
  • A nested message is compared sub-field by sub-field, with a dotted path (48.2). ISOMsg doesn't override equals, so comparing two nested messages as values would always report them different.
  • Card data stays protected, because a diff goes into tickets: fields 2, 35 and 45 go through ISOUtil.protect, and the PIN block and chip data (52, 55) are only reported as different, never shown.

Before each release the team replays a day of recorded requests through the new build, against a host simulator like the ones in unit c16, and compares every response the new build gets with the response recorded for the same request. Some fields differ on every run by design: the transmission time, the STAN, the retrieval reference number. The release fails when anything else differs.

Each View of the Bytes Answers a Different Question


When the diff is empty and the host still says the bytes are wrong, the problem is in bytes that aren't fields: framing around the message, or a character set the host reads differently. ISOUtil has a view for each:




  • hexString is one unbroken string: the form for an assertion or a value in a ticket.
  • dumpString keeps the printable characters and names the control bytes. On a link that frames messages with STX and ETX, it shows whether the frame is there, where hexdump's text column shows dots.
  • hexdump reads every byte as ASCII in its text column, so for an EBCDIC peer a message that is fine looks corrupt.
  • hexDump with a character set (capital D) reads the text column as EBCDIC (ISOUtil.EBCDIC, code page IBM1047), and the message reads 0800 T1. Its layout is different (a decimal offset, a bar before the text), so use it for reading and hexdump for anything you will paste back into a test.


For the bytes the channel read next to the message it made of them, org.jpos.iso.filter.DebugFilter adds them to the receive event of every message the channel unpacks. It is a raw incoming filter, so the channel hands it the header and the image:



We ran an ASCIIChannel with this filter against a peer on 127.0.0.1 that sent one 0110, with ProtectedLogListener in front of the writer:



The message is masked, but the image shows the card number in clear, across the end of line 0010 and the start of line 0020. 17.6 deals with it.


ISOUtil's Helpers Fail Quietly Where You Expect an Error


Several ISOUtil helpers don't complain when a value doesn't fit:




zeropad(long, len) keeps the last len digits. A STAN counter that nobody wrapped sends its millionth message as 000000, then 000001, 000002: the numbers the host saw a million messages earlier. If an earlier request with the same terminal and STAN is still waiting, you get the duplicate keys of unit c12; if not, a host that checks for duplicates declines a purchase it has never seen. zeropad(String, len) refuses the same value. Use the String form where a value that doesn't fit is a bug, and the long form only where wrapping is what you mean, and then wrap on purpose (unit c12 wraps from 999999 to 000001).


On a track 2, protect masks everything after the separator (=, or D): the expiry date and the service code go too. A protected log can never show you a track 2 problem, so that one needs a test card. (A track 1, with ^, follows other rules; check what your log shows of field 45.)


bitSet2String starts at bit 0, which is not a field. The character at index n stands for field n, so the first 1 above, at index 2, is field 2. Count from one and you read every field one number too high.


calcLUHN is the one you can rely on: it gives the check digit for the digits you pass, which is how a test BIN becomes a valid test card. 5555555555554444 is 555555555555444 plus 4.


Raw Bytes in the Log Are Text, So a Filter of Your Own Has to Withhold Them


ProtectedLogListener masks the ISOMsg objects of an event and no text (unit c8). A channel puts raw bytes into its receive event in two forms that are not ISOMsg objects: DebugFilter's image above, and a dump when a reply can't be unpacked. The same 0110, sent with its last byte missing:



The event holds no message, only the exception, the string --- data --- and the hex dump as a second string (and --- header --- with its dump when the channel has a header). DebugFilter's image is an org.jpos.util.Dumpable. Neither is an ISOMsg, so ProtectedLogListener passes both through, card number included. The number is split across two lines of the text column, 4111111111 and 111111, so a scan of the log for sixteen digits in a row reports it clean. Every message your side can't unpack puts its card number, if it carries one, into a log that was assessed as masked.


A listener is one method, LogEvent log(LogEvent ev). This one withholds both kinds:




The same two runs with the scrubber after ProtectedLogListener:




The markers stay, so the log still shows that bytes were withheld, and the masked message is as ProtectedLogListener left it. Any listener you write needs four properties:


  • It returns the event. A listener that returns null stops the chain, and no writer after it sees the event.
  • It replaces entries in the list and leaves the objects alone, as ProtectedLogListener does with its masked copy. Masking the ISOMsg itself would change a message your code still holds, such as a response the MUX handed back or a request kept for a reversal.
  • It holds the list's lock while it walks it, as ProtectedLogListener does, because the component that created the event may still be adding to it.
  • It sits after ProtectedLogListener and before every writer. A filter protects only the listeners after it.


You lose the bytes of a failed unpack, which 17.1 needs to build a test. Get them from the peer's trace, or from a test link with a test card where the scrubber is off.


Spot the Problem: One Line per Event


The operations team ships the log to a platform that reads one event per line. org.jpos.util.FlatLogListener renders the event, removes the line breaks, and passes a one-line event on (combine-spaces also folds runs of spaces). Someone adds it at the top of the chain, and later a realm filter to keep only the sender:



Every listener in it is a stock jPOS class with the usual settings. What reaches the platform?


Nothing. We built chains of these listeners in several orders and logged one purchase from the realm client.sender through each:



FlatLogListener doesn't pass the event on. It passes a new, frozen event that holds only text: no ISOMsg for (2) to mask, and no source, so no realm for (3) to keep. With (1) first and no realm filter, the platform gets every card number in clear. With the realm filter added after (1), it gets nothing at all.


A listener can only work on objects that are still in the event. Filters that look at messages or realms come first, FlatLogListener after them, and the writers last. The same holds for anything that turns the event into text, such as the SLF4J bridge of unit c8.

Summary


  • A dump is evidence only when it reads back to the bytes it shows. decodeHexDump reads one layout and checks nothing: a hexdump -C dump or a lost line gives other bytes, and the packager then blames a field that is fine. Check every line's offset and read bytes from their columns.
  • A logged message gives back the bytes only after you put back what the log masked. A wiped binary field fails to pack, a masked card number packs silently into different bytes, and a message read from XML still has XMLPackager until you set yours.
  • Compare two messages field by field: without the bitmap, binary values by content, nested fields by path, card data protected. Comparing values with equals reports equal binary fields as different.
  • Pick the view for the question: hexString for assertions, dumpString for framing, hexdump for text you paste back, hexDump with a character set for EBCDIC, DebugFilter for the bytes beside the message.
  • ISOUtil's helpers fail quietly: zeropad(long) cuts a STAN to 000000, protect hides the whole of track 2 after the separator, bitSet2String counts from bit 0.
  • Raw bytes in the log are text. A failed unpack and DebugFilter put card numbers into the log past ProtectedLogListener. Withhold them with a listener that replaces list entries and returns the event, placed after the masking filter and before FlatLogListener and every writer.

Challenges


These have no single answer.


  1. The support desk can send its traces only as screenshots of their tool, which shows decimal offsets and no text column. What can a reader still check, and what evidence would you ask for instead?
  2. Pick the fields that differ on every purchase in your network (17.3 had 4, 7 and 11). Which of them could also be the cause of a format error, and how would a diff that ignores them hide it?
  3. DebugFilter adds a hex dump of every message it receives to the log. Measure the log volume of a test link with and without it at 50 messages a second, and decide how long you could leave it on.
  4. RawDataScrubber recognises the channel's dump by the exact strings --- data --- and --- header ---. What happens after a jPOS upgrade that changes them, and what test in your build would notice before production does?


Design Note: Why the Log Is a Format a Packager Can Read


jPOS writes messages to the log as <isomsg> blocks, the format XMLPackager reads and writes, rather than in a format meant only for people. A block can be read back into a message, as 17.2 did, and a simulator or a test can replay it with no parsing code of its own.


One cost is card data: the log has to be masked, so every block needs repair before it means anything on the wire. The other is size: a line of XML per field, for every message of the day.


The listener chain follows from the same choice. Listeners receive objects, not text, so a filter can mask a message and leave the rest of the event alone, but only while the objects are still there, which is why 17.6.1 puts every flattening step after the filters.
