The acquirer's host restarts at 03:10. The ChannelAdaptor of unit c3 waits its reconnect delay and connects again. The ready entry is back, mux.isConnected() says true, and the first purchase of the morning comes back declined. So does every purchase after it, until someone at the acquirer looks at the log at 07:30.

The host wanted a sign-on on the new connection, and nothing in jPOS 2.1.7 sends one. The unit has six rules, one per section heading.

A Connected Link Is Not a Signed-On Link

The examples run a real Q2 with the descriptors of units c3 and c4 against a small host on 127.0.0.1. Like hosts that want a sign-on, it keeps a signed-on flag per connection and declines every purchase on an unsigned connection with response code 91. It can also drop its connections, hang, refuse sign-ons and send echoes of its own. The adaptor's reconnect-delay is 3 seconds, to keep the runs short.

The 03:10 restart, compressed: a purchase on a fresh connection, a sign-on by hand, another purchase, then the host drops the connection and we try again:

isConnected() was true every time. It reads the adaptor's ready entry (unit c4), which says only that a TCP connection exists. Whether the host will take traffic on it is settled at the ISO 8583 level, with network management messages: MTI 0800, the function in field 70:

  • 001, sign-on. "I am here and ready to send you traffic." Many hosts refuse financial messages on a connection until it has signed on.
  • 301, echo. "Are you still there?" Sent every few minutes.
  • 002, sign-off. "I am about to stop." Sent before a planned disconnect.

The host answers each with an 0810, 39=00 when it agrees. The sign-on is per connection: when the connection goes, the session goes with it, and the reconnect starts unsigned.

jPOS 2.1.7 has no component that sends these messages. The org.jpos.tutorial.LogonManager of the jpos.org tutorial is tutorial code, not a class in the 2.1.7 jar. We write our own in 11.3.

Networks differ. Some hosts decline unsigned traffic, some drop it without an answer, some close the connection. Some also require a key exchange after sign-on (unit c15). The client's side of the problem is the same.

Only an Echo Proves the Host Is Answering

Two settings have "alive" in their name, and a team that has switched both on may think the link is watched. Neither proves what an echo proves:

MechanismConfigured asWhat goes on the wireWhat an answer proves
network echoan 0800 / 301 that your code sendsa real request, answered by the host applicationthe host application is taking messages
adaptor keep-alive<keep-alive>yes</keep-alive> on the ChannelAdaptoran empty frame when nothing was sent for reconnect-delay msnothing: the adaptor neither expects nor checks an answer
TCP keep-alivechannel property keep-alive = trueoperating system probes on an idle socket, often after two hoursthe far side's TCP stack is there

Hang the host's application while its process keeps reading the socket. Read timeout 5 seconds, one echo every 5 seconds by hand:

Each time the read timeout fires, the adaptor reconnects, and the host's process accepts a new connection that is just as dead: accepting is not the application's job. Seven connections in 40 seconds, and isConnected() was true at almost every check.

The same run with <keep-alive>yes</keep-alive> and a reconnect delay of 1 second:

One reconnect in 40 seconds instead of six. The 2.1.7 ASCIIChannel, at either end, answers an empty frame with an empty frame inside its own read loop, before any application code sees it. So the hung host's channel kept answering, and the read timeout seldom saw five seconds of silence.

Only the echoes showed it: eight sent, eight expired (rx_expired=8 in the QMUX counters). Every purchase sent in that time would also have expired, each an unknown outcome to reverse (unit c12). A failed echo has to take the link out of service, which the sign-on manager in 11.3 does.

Echoes also keep a quiet link from tripping the read timeout or an idle firewall, as long as they come more often than either fires. Unit c12 sizes all the timeouts together.

A Sign-On Belongs to One Connection

Each connection needs exactly one sign-on, made after it opens and before it carries traffic. How does a manager know that the connection it signed on is the one that is up now?

The adaptor puts a new Date object under host-channel.ready for every connection (unit c3), so that object names the connection. Store the same object when the sign-on succeeds, and the question becomes one comparison: is the object I signed on the one there now? After a reconnect it is not, whatever happened in between.

A boolean "signed on" flag, cleared when the manager sees the link down, can't tell. The manager below runs one loop for all its links, and one unanswered exchange blocks that loop for timeout (30 seconds by default), while the adaptor reconnects within reconnect-delay (10 seconds). A link can drop and come back while the loop is busy elsewhere, and the flag still says "signed on" about a connection that never was.

The manager keeps its whole state in the Space, as marks next to the ready entry:

Space keyValueWritten whenLives for
host-mux.logonthe ready object of the connection that signed ona sign-on is answered with 00logon-interval, e.g. 24 hours
host-mux.echoBoolean.TRUEa sign-on or an echo is answered with 00echo-interval, e.g. 5 minutes
host-mux.enabledthe same ready objecta sign-on is answered with 00until the manager sees the link down, an echo fails or the manager stops

Self-expiring entries replace timers. When the echo mark has expired, an echo is due. When the logon mark has expired, or holds another connection's object, a sign-on is due.

(1) Identity, not equality. != compares objects. Two connections opened in the same millisecond have equal Dates, and equals would call them one connection.

(2) An echo is due when its mark has expired, and only on a connection that signed on.

(3) put, not out. out adds a second entry, and rdp keeps returning the first one. put replaces it.

(4) The enabled mark is the ready object. 11.4 shows who reads it.

(5) A failed echo starts over. The link leaves the pool at once, and the next pass signs on again. Against the hung host of 11.2 that sign-on gets no answer either, so the link stays out until the host recovers. Unit c15 discusses when one failed echo is too few.

The STAN comes from the same sequence as the link's purchases (unit c4), so the host never sees two messages from this link with the same STAN. An 0800 carries no field 41, so QMUX's key for it is the out queue, the MTI and field 11, and only this client's own 0800s compete for it. Field 7 is in UTC, as the standard wants.

A Pool Uses a Link Only While It Is Signed On

Two links, A and B, sit behind a round-robin MUXPool (unit c4), with one manager for both. Host B drops its connection, and when the adaptor reconnects, host B refuses the first three sign-ons. Eight purchases come in, one every half second from the moment B reconnects. Where do they go?

Half went to B and were declined. The pool asks each member only isConnected(), B's adaptor is connected, and the manager has no way to tell the pool otherwise. Add one property to the pool:

and run the same morning again:

With check-enabled, the 2.1.7 pool counts a QMUX that has one <ready> name as usable only when it is connected and the Space entry <mux name>.enabled is the same object as its ready entry. The test is ==, made on every request. B's enabled mark held the ready object of connection 1, so it stopped matching when connection 2 brought a new one, before the manager had noticed the reconnect. B came back into rotation with its first successful sign-on.

The == test also rejects Boolean.TRUE as the enabled mark, a natural choice for "enabled": TRUE is never the ready Date. One link behind a pool with check-enabled; after the first purchase we put the ready Date there by hand:

With Boolean.TRUE the link is never used. Every purchase waits its full timeout and comes back null without leaving the pool, while the host is signed on and waiting. The caller can't tell that null from a lost answer, so under unit c12's policy it would reverse purchases the host never saw.

A client without a pool has no check-enabled and has to ask the same question itself before it sends.

One link, several addresses. The channel properties alternate-host and alternate-port, repeated in pairs, give one adaptor more addresses to try when a connect fails, the primary first: failover at connect time, one connection at a time, no pool. Each new connection still needs its sign-on, which the manager handles the same way. Unit c14 compares this with a pool.

Take a Link Out of Service Before You Sign It Off


Every Tuesday night, operations take link A out for maintenance. Each link has its own manager (host-logon-a, host-logon-b), and the plan is to remove 30_host_logon_a.xml from deploy/, which makes Q2 call the manager's stopService. A first version:



Purchases flow through the pool, one every quarter second, and the host takes a second to answer the 002. Later the manager is deployed again. What goes wrong?



A purchase was lost to the sign-off. Between (1) and (2) the link was still enabled: the host had already processed the 002, and the pool kept routing purchases to A while the 0810 was on its way. One cardholder was declined; on a busy link that second costs dozens.


The link never came back. The redeployed manager found a logon mark that still matched the ready object, because the connection was the same one. decide said "signed on, echo due", the echoes were answered, and nothing wrote an enabled mark again. In production link A stays out of the pool until the logon mark expires, a day later, while the host has been told the client left.


The order follows from what each mark means:


  • the enabled mark is what routes traffic, so it goes first;
  • the 002 goes only to a connection that actually signed on: the ready entry is there and is the very object in the logon mark. A link that is down, or that reconnected since, has no session to end;
  • the logon mark goes last, whether or not the host answered, because the session is over either way.

The Host's Own Echo Is a Request, and Someone Must Answer It


A host may check the link from its side too: it sends an 0800 / 301 every few minutes and drops the connection after a few go unanswered. One arriving at a QMUX configured as in unit c4:



QMUX found no waiting request for it and put it on the <unhandled> queue, where it expires after two minutes. Neither QMUX nor the channel answers an 0800 by itself, so the host gives up and drops a healthy link.


Messages that match no waiting request go first to the QMUX's request listeners, in order, and only reach <unhandled> when none of them takes the message:



Add it to 20_host_mux.xml:




The source a listener receives is the channel that read the message: the 2.1.7 BaseChannel marks every message it receives with itself, so the reply leaves through the channel the echo came in on. QMUX passes itself only for a message that carries no source.


The reply copies only the fields an 0810 needs. clone(int...) copies exactly the fields you name, so field 0, the MTI, has to be in the list. Without it getMTI throws, the listener returns false, and the echo lands on <unhandled>. Return false for anything you don't handle, so that late answers to your own requests still reach <unhandled> (unit c12).

Summary


  • A connected link is not a signed-on link. The ready entry says that TCP is up. A host that wants a sign-on declines or drops everything on a new connection until it gets one.
  • Only an echo proves the host is answering. Adaptor and TCP keep-alives are answered below the application, so a hung host passes them; an 0800 / 301 that expires is the signal to take the link out.
  • A sign-on belongs to one connection, and the adaptor's ready object names it. Store that object in the logon mark and compare with ==; a boolean flag misses a reconnect that happened while the loop was busy.
  • A pool uses a link only while it is signed on: with check-enabled, the enabled mark must be the very ready object. A reconnect takes the link out by itself, and Boolean.TRUE keeps it out for good.
  • Disable, sign off, forget. Remove the enabled mark before the 002, send the 002 only to the connection that signed on, and remove the logon mark whatever the answer, or the link stays out of the pool after the next deploy.
  • Answer the host's echo with a request listener on the QMUX, through the source it is given. Unanswered echoes end on <unhandled>, and the host drops the link.

Challenges


  1. Your host answers a sign-on in 200 ms but sometimes takes 25 seconds to answer an echo under load. Choose the manager's timeout, echo-interval and the read timeout, and say what a 25-second echo does to the other links served by the same manager thread.
  2. A host requires a sign-on per connection and also a daily sign-on at its cutover, 00:00 host time, on every open connection. Which mark would you change, and how, so that the existing decide handles it?
  3. Two client instances each run their own adaptor to the same host, one connection each, and share a terminal ID. Does each need its own manager? What do they have to share, and what must they never share?
  4. Measure how long a link stays in the pool after its host application hangs, with an echo interval of 5 minutes, a manager timeout of 30 seconds and the loop of 11.3. How would you shorten it without echoing every few seconds?


Design Note: Why Marks in the Space and Not a State Machine?


A sign-on lifecycle is a state machine, and the obvious code keeps the state in a field: DOWN, CONNECTED, SIGNED_ON. This manager keeps no state in fields. Everything it knows sits in the Space, as entries that expire by themselves or stop matching when another component writes something new.


The state is not the manager's. The connection belongs to the adaptor, which can replace it at any moment without telling anyone. A field in the manager is a copy of the adaptor's state, wrong from the moment the original changes until it is next refreshed. Storing the adaptor's own object removes that window: a stale mark stops matching the moment the adaptor writes a new ready entry, and the pool, which reads the same entries, sees the change at the same moment. Expiry replaces the timers a state machine would need for "echo due" and "sign-on expired", each one more thing to cancel correctly on every path.


The price is that the logic is spread over keys rather than written in one place, and a mistake in one of them shows up somewhere else: a mark that is never removed keeps a link out of the pool (11.5).
