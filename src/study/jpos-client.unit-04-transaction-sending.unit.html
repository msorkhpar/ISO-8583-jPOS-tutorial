  17. Design Note: Why Queues Between the MUX and the Socket?

A checkout service runs two hundred threads over one TCP connection to the acquirer's host, the ChannelAdaptor of unit c3. Thread 17 sends a 0200 for 10.00, and the next 0210 off the socket answers thread 42's purchase of 40.00, which thread 17 must not read. When the host says nothing, or the link is down, thread 17 still has to tell a cashier something.

QMUX solves this for every thread at once. What it promises and what it leaves to you comes down to seven rules, one per section heading. Every output is from jPOS 2.1.7: Q2 in the same JVM, started from the descriptors shown here (a ChannelAdaptor and a QMUX), and an ISOServer on 127.0.0.1 playing the host, with a 500 ms reconnect delay so the examples finish quickly.

QMUX Sits on the Adaptor's Queues, Crossed

The ChannelAdaptor of unit c3 never talks to your code. It writes what it takes from the Space queue host-send to the socket, and puts everything it reads on host-receive. QMUX is the other end: it writes requests to the queue the adaptor sends from and reads the queue the adaptor fills.

deploy/20_host_mux.xml, the same file as in unit c1:

Each element is named from the QMUX's point of view: its <in> is what comes in from the host, the adaptor's <out>, and its <out> is the adaptor's <in>. What happens if you copy <in>host-send</in> and <out>host-receive</out> from the adaptor's file, because the names look like they should match? Each version on its own, with the link up, sending one purchase with a 2-second timeout:

The copied QMUX writes the purchase into host-receive, a queue only the adaptor should write to, and listens on host-send, where no answer arrives. The purchase never leaves the JVM. Q2 logs nothing, isConnected() is true because the adaptor's ready entry exists, and every request returns null after its full timeout. A client that handles null correctly (section "A Missing Answer Comes Back as null") reports every purchase as "outcome unknown" and, with unit c12's policy, queues a reversal for each. When every request times out and the host has no record of any, check the queues first.

<ready> names the entry the adaptor keeps in the Space while it is connected, host-channel.ready (unit c3); section "A Request on a Down Link Waits in the Queue" shows why you need it. <unhandled> is where QMUX puts messages nobody is waiting for.

Every Thread Gets Its Own Answer

Five threads send a purchase at once over the one link, each with its own STAN and amount. The host holds all five and answers them in its own order. Which thread gets the first 0210?

Thread 2 got the first answer, because it was for STAN 000102. When QMUX sends a request, it computes a string from it, the key: by default the out queue, the MTI (a response's 0210 mapped back to 0200), and fields 41 and 11. It parks the waiting thread under that key, computes the key of every message on host-receive, and hands each to the thread parked under the same key. Unit c12 takes the key apart and shows what goes wrong when two requests share one.

A message that matches no waiting thread (an answer that came too late, or a request the host sent on its own) goes to <unhandled>, where it stays for two minutes (fixed in 2.1.7) unless you read it first.

The usual alternative, a lock around "write, then read the next message", serialises the service: with a host that takes 300 ms to answer, it completes about three purchases a second, however many threads it has. The same reasoning ruled out pools of raw channels in unit c3.

A Missing Answer Comes Back as null

The host receives a purchase for 42.00 and never answers. What request gives back, and what the obvious next line does with it:

request waited the whole timeout and returned null; it did not throw. Unit c3's socket read timeout is an exception, so it is easy to expect one here. The ISOExceptions that request does throw mean the message was refused before it was sent: none of the key fields is present, or the key is a duplicate (unit c12).

The NullPointerException is the cheap part of the bug. It lands in a generic error handler and the cashier sees "system error", while the host's log shows the purchase arrived. The host may have approved it and lost the answer, and nothing in the code starts the reversal that unit c12 builds for this case. A null from request is an unknown outcome: not a decline, and never a reason to send the same purchase again.

A Request on a Down Link Waits in the Queue

The host restarted, and the adaptor is reconnecting. A thread calls request with a 5-second timeout anyway. Does the purchase fail at once?

In 2.1.7 request never checks the link. It puts the message on host-send with the timeout as its lifetime and waits. If the adaptor reconnects in time, the message goes out, here after a second and a half. If not, it expires in the queue unsent, and request returns null like any missing answer. (send, the method without an answer, does check, and throws ISOException "MUX is not connected".)

In the first ending, a purchase can reach the host many seconds after it was made, when a terminal that waits less than your timeout has already shown a failure. In the second, the cashier waits the full timeout to hear "outcome unknown" about a purchase that never left the building. The reversal queued for it is usually harmless but is noise, and the true answer was available at once: the host is unavailable, try again or take another payment method.

So ask first. With <ready> configured, isConnected() is true only while the adaptor's ready entry exists; without it, whenever the QMUX is running. A client that keeps the endings apart:

Against a host that approves, declines, drops, and then goes away:

The check is not a guarantee: the link can drop between isConnected() and the write, which puts you back in the first ending. It turns the common case, a link that has been down for a while, into an immediate and certain answer.

  1. Answer the API caller truthfully when the host is silent or out of reach

    • request() does not check the link: on a down link the message waits in the queue for the timeout and may go out later, so the client asks isConnected() first and reports the host as unavailable.
    • request() returns null when no answer comes in time; that is an unknown outcome, not an exception, not a decline and not a reason to resend.

Problem statement

Your payment API answers each purchase with an HTTP status, and its callers act on it. A 503 makes the caller retry at once or offer another payment method. A 504 tells it to wait while a reversal job settles the purchase. Support has two complaints. On busy days some callers get a 500 with a NullPointerException in the log. And during last week's host restart, every caller waited the full timeout for a 504, and the reversal job then sent hundreds of reversals for purchases the host had never seen.

The constants at the top of the class are the four statuses. About seven lines in total.

The tests run a real QMUX against a host on the far side of its queues. That host keeps reading host-send even while the QMUX reports the link as down, the way the adaptor would once it reconnects.

The Asynchronous Form Calls Back Once, With an Answer or With null


A blocking request holds its thread as long as the host takes. A service waiting on thousands of answers can pass a listener instead and get its thread back at once:



The listener is an ISOResponseListener. Its one abstract method is responseReceived(response, handBack), where the hand-back is any object you passed in, returned untouched. When the timeout passes with no answer, QMUX calls expired(handBack), whose 2.1.7 default calls responseReceived(null, handBack), so a lambda sees null on expiry as the blocking form does. An answered request and a dropped one, with the thread each callback ran on:



A response's callback runs on the adaptor's receiver thread, the one thread that reads the socket, and an expiry's on a QMUX scheduler thread. Neither is yours.


A listener that ignores null, say one that completes a future only when a response arrives, leaves that future waiting forever:



The caller, perhaps an HTTP request in your own API, hangs until its own timeout, and every dropped purchase adds another hung caller.


A listener that does real work holds up the whole link. One asynchronous request whose listener spends three seconds writing to a database, then a blocking request with a 2-second timeout that the host answered at once:



The receiver thread was inside the first listener, so nobody read the second approval off the socket until the blocking request had given up: the host approved 000702, the caller got null, and the approval went to <unhandled>. Keep the listener to completing a future or handing the message to a queue of your own, and do the work elsewhere:




The asynchronous request throws the same ISOExceptions as the blocking one, before anything is sent. That third ending is not a null: the host never saw the message, so there is nothing to undo.

Each Link Numbers Its Own Messages


Field 11, the STAN, has six digits and is one of the two default key fields. The host uses it with field 41 to spot duplicates, and a reversal names its original by it. Where should it come from?


A random number looks unique enough. One terminal ID, simulated with 20 purchases in flight and 100,000 a day, each with a random STAN:



Each collision is a purchase QMUX refuses as a duplicate key while the other waits. Over a day, 100,000 draws from a million values also repeat many times, which a host that looks for duplicates notices. Use a counter: one sequence per outbound link, 000001 to 999999, then 000001 again.



SpaceUtil.nextLong takes the number from the Space, adds one and puts it back while holding the Space's lock, so two threads never get the same number. Started at 999997, it continues:



Where the counter lives decides what a restart does. A program that takes three STANs, run twice with a transient space (tspace:stan) and twice with je:stan, the Berkeley DB space that ships with jPOS 2.1.7 (the part before the colon picks the kind of space, the part after names it):



After a restart the transient counter starts at 000001 again, so the afternoon's first purchases repeat the morning's terminal and STAN, and a host that checks duplicates by those fields may decline them. Production uses a persistent space. The lock is local to the JVM, though: two processes that share a terminal ID on one link need one shared sequence, such as a database sequence, rather than a space each.


Keep every request with its transaction record. A reversal (unit c12) copies fields from it and names it by its MTI, STAN, field 7 and acquirer ID. The rest of the request comes from unit c2's request factory.

Code Names a MUX and Never Keeps One


Q2 registers each QMUX in the NameRegistrar as mux.<name>, and QMUX.getMUX("host-mux") looks it up. The registry is per JVM, so this works only in the process that runs Q2, as the application or embedded in it (unit c1).


A lookup in the constructor fails if the service is built before Q2 has deployed the descriptor. Here a service looked up host-pool, the pool of section "A Pool Takes the Name's Place", too early:



A reference kept from startup goes stale when an operator edits the descriptor and Q2 redeploys it. After touching the file, one purchase through a kept reference and one through a fresh lookup:



The old QMUX is stopped but still wrote the purchase to host-send, as any request does. The adaptor sent it, the host approved it, and the approval reached the new QMUX, which had nobody waiting for it, so the caller got null for a purchase that went through. Look the MUX up when you use it:



A Pool Takes the Name's Place


The lookup returns the MUX interface, and the code needs nothing more. When one link is not enough, each link gets its own ChannelAdaptor and QMUX, and a MUXPool in front of them is itself a MUX, registered the same way. deploy/25_host_pool.xml:



The second pair is the first one with other names: adaptor host-channel-b with queues host-b-send and host-b-receive, and QMUX host-mux-b. Each QMUX reads only its own in queue, so the two links never confuse each other's answers.


The pool looks its members up once, when it is deployed, so it comes after them (25_), and a missing name fails the deployment. It keeps those references: redeploy a member and the pool still holds the stopped one, so redeploy the pool with it. With two hosts, A and B:



primary-secondary uses the first member that is connected, so B takes over when A drops. With no member connected, the pool checks again every second until the timeout is spent and then returns null without handing the purchase to any member, the same answer as a lost response. Ask isConnected() first here too: the pool's is true while any member is. The application changed one word, host-pool for host-mux. Unit c14 covers the other strategies and how to design for failover.


The pool's asynchronous form differs. In 2.1.7, MUXPool.request with a listener also waits in the caller's thread for a usable member, up to the timeout, and then throws ISOException "No MUX available" instead of calling the listener. In our run that took the full 3000 ms.


Depending on MUX also lets a test hand the client a fake that answers, declines or stays silent on demand (unit c10).

Summary


  • QMUX sits on the adaptor's queues, crossed. Its <in> is the adaptor's <out>. Copied unchanged, every request times out without leaving the JVM or logging an error.
  • Each thread gets its own answer, matched by a key, in whatever order the host answers. A lock around write-then-read serialises the whole service.
  • A missing answer is null, not an exception. It means "unknown", never "declined" and never "send it again".
  • request doesn't check the link. On a down link the message waits in the queue for the timeout and may go out late. Ask isConnected() first, with <ready> configured.
  • The asynchronous listener runs once, on a jPOS thread, with null on expiry. Complete the caller's future in both cases, and keep the listener short, or every answer on the link waits.
  • One STAN sequence per link, wrapping 999999 to 000001, kept in a persistent space. Random or in-memory numbers repeat.
  • Look a MUX up by name when you use it, and depend on MUX. A kept reference goes stale on redeploy, and a MUXPool can take the name's place.

MethodDoes

With <property name="check-enabled" value="true"/> a QMUX member also needs an entry named after the QMUX plus .enabled, which must be the same object as its ready entry when the QMUX has one <ready> name, and merely present when it has several (unit c11).   1. Your host answers in 300 ms on average, and 2% of answers take 8 seconds. How many threads does a service using the blocking form need for 200 purchases a second? How many does the asynchronous form need, and what does it need instead?
  2. The link drops for 40 seconds at lunchtime. Your request timeout is 25 seconds and the adaptor's reconnect delay is 10 seconds. Draw what happens to purchases submitted at seconds 0, 20 and 35, with and without the isConnected() check.
  3. Two instances of the checkout service share one terminal ID on one link. Design their STAN numbering without a shared database. What happens at a restart?
  4. Write a request listener for <unhandled> traffic that logs late approvals. Which fields would you log, and which must you never log?


Design Note: Why Queues Between the MUX and the Socket?


QMUX never touches the socket. A MUX that owned the channel would be shorter by one thread, but jPOS puts Space queues in between.


The queues keep the two sides independent. The adaptor reconnects and backs off without the MUX knowing, and the MUX keeps its waiting threads throughout. A message written while the link is down waits, which suits an advice (a 0220 reporting something already done) and, as section "A Request on a Down Link Waits in the Queue" showed, can send a purchase late. Anything can sit on the other end of the queues: a second adaptor, a test host in the same JVM, a recorder. Unit c12 replaces the adaptor with a scripted host, and QMUX can't tell.


The price is that the queues hide the link. A write to a queue always succeeds, so a mistake like copied queue names shows up only as timeouts, and a stopped QMUX can still put a purchase on the wire. The MUX's whole view of the link is a single Space entry, the ready flag.
