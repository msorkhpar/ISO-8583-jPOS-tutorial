22:14:050200000731100.00
22:14:350420000732

The purchase got no answer. Did the cardholder pay? Each message's first four digits, its Message Type Indicator (MTI), say what it is, what answers it, and what approving it commits. Reading the log takes four rules, one per section heading.

The Third Digit Pairs Every Message With Its Answer

The third digit, the function, says where a message sits in an exchange: 0 a request, 1 its response, 2 an advice (a report of something already done, 4.3), 3 the advice's response. jPOS derives the answer's MTI with setResponseMTI. What answers an 0420, and what answers its repeat, the 0421?

The answer keeps the first two digits and adds one to the third. An advice gets an advice response: 0420 → 0430, never 0410. The fourth digit loses its repeat mark, because the answer is to the message, not to one attempt at sending it: 0421 → 0430 too. A response has no answer, and jPOS refuses to make one.

The MTI pairs kinds of message, not transactions. Ten terminals on one link get ten 0210s, so a response belongs to your request only when it also carries the request's STAN (field 11) and terminal ID (field 41). Take the next 0210 on the link as yours, and one cardholder's approval is reported on another's purchase. Unit c12 shows this in jPOS.

Later editions. The pairs hold in 1993 and 2003: 1804 is answered by 1814. The Reference maps this unit's MTIs to their later counterparts.

Practice: Reading the MTI

Every ISO-8583 message opens with four digits, and those four digits are the whole of its identity. Section "The MTI's Four Digits Say Edition, Class, Function and Origin" calls them the Message Type Indicator, and each one answers a different question: which edition of the standard the message is written against, what class of business it is, where in the exchange it sits, and which side of the link sent it.

The tables are short enough to hold in your head. A 0100 is an authorization request from an acquirer, written against the 1987 edition (version digit 0; 1 is the 1993 edition and 2 the 2003 one). Change the third digit to a 1 and it becomes the response. Change the second to an 8 and the message is no longer about money at all — it is network management between the two ends of the link: sign-on, sign-off, key exchange, or an echo test that checks the link is alive.

That is the point of this first practice: an MTI is not opaque, and you do not need a library to read one.

Problem statement

Make parts in practice/mti/Mti.java return the four parts of an MTI — its version, its message class, its message function and its message origin, in that order — and refuse anything that is not four digits.

The Second Digit Says What an Approval Commits


The second digit is the class: 1 authorization, 2 financial, 4 reversal, 8 network management. An 0100 and an 0200 built from the same fields and packed with iso87ascii.xml (the PAN masked for printing):



Only the second byte differs, the class digit, and it decides what an approval does:


  • an approved 0100 places a hold on the amount. The money moves later, when the acquirer clears the transaction (unit 7). Credit card purchases mostly work this way;
  • an approved 0200 posts the debit at once. ATM withdrawals and PIN debit purchases work this way;
  • an 0800 touches no account. Field 70 says what it does, such as 301, echo test.


A fuel pump asks for 100.00 before the customer fills up, and the customer takes 35.00. As an 0100, the 100.00 is a hold, a completion advice (0220) carries 35.00, and the rest is released. Sent as an 0200 on a link that accepts it, 100.00 is debited at once. Until a second message gives 65.00 back, the cardholder has paid for fuel they never took.


An echo with no answer needs no clean-up, because it committed nothing; the next one is a new message.


An Advice Reports What Already Happened, So It Is Repeated Until It Is Acknowledged


An advice tells the receiver about something already decided: a network's stand-in approval (0120), a completion or an offline purchase (0220), a reversal (0420). The receiver can't decline it; it acknowledges it. Until the acknowledgement arrives, the sender sends the advice again as a repeat. setRetransmissionMTI changes the fourth digit from 0 to 1 and nothing else, STAN included, so the receiver can tell that it has seen this message before. With a new STAN, the repeat of an 0220 would look like a second completion and could be posted twice.


jPOS 2.1.7 assumes the acquirer. setRetransmissionMTI writes 1 into the fourth digit whatever was there, so an issuer's 0422 becomes 0421 instead of 0423. On the issuer side, set the repeat MTI yourself.


Spot the Problem: The Dispatcher That Ignored a Repeat


An issuer's host dispatches each incoming message on its MTI:



respond clones the message, calls setResponseMTI and sets field 39. One night the 0430 for a reversal is lost on its way back to the acquirer. What happens next?



The repeat matches no case and falls into (2). The acquirer repeats until its limit, then parks the reversal for someone to look at (unit 20), though the issuer applied it long ago. If the issuer was down for the 0420 itself, every attempt it sees is an 0421, the reversal is never applied, and the cardholder pays for a purchase the terminal reported as failed.


Dispatch on the class and function, digits 2 and 3, and let setResponseMTI build the answer. The same reversal, then an 0600 and a late 0810:




An unsupported request gets error 12, invalid transaction (unit 9), so its sender isn't left waiting. isRequest is true for any even third digit, so an unknown advice gets that answer too. A response nobody waits for, such as a late 0810, gets no answer; log it. The issuer still has to notice that it already applied 000732 before it undoes the purchase a second time; unit 20 builds that.


A Request Without an Answer Is Reversed, Never Sent Again


The 0200 in the opening got no answer in 30 seconds. Either it never reached the issuer, or the issuer declined it, or the issuer approved it and the answer was lost. The acquirer can't tell which. Send the 0200 again, and in the third case it is a second purchase: an issuer that doesn't look for duplicates approves it, and the cardholder pays twice.


A reversal says "if you approved this, undo it". It changes nothing in the first two cases and gives the money back in the third. It goes as an 0400 request or, more often, an 0420 advice, and either way it is a new message that points back at the original:




It has its own STAN and time, because it is a new message on the link. The issuer finds the original through field 90, not field 11.


Field 90, original data elements, names the original in 42 digits:



It copies only what identifies the transaction. Track 2 (field 35), the PIN block (52) and chip data (55) stay out of a message that may wait in a queue for hours.


The 0420 at 22:14:35 reversed purchase 000731. Its 0430 was lost, the 0421 repeated it with the same STAN, and the 0430 at 22:15:06 closed it. Whatever the issuer did with the purchase, the cardholder hasn't paid for it.


Networks differ. Most networks want an 0420 after a timeout; some want an 0400, the original's STAN in field 11, a reason code, or more of the original's fields. Unit 7 places reversals in the transaction flow, and unit c12 builds and queues them in jPOS.

Summary


  • The third digit pairs every message with its answer: request 0 with response 1, advice 2 with advice response 3, and a repeat is answered like the original. A response is yours only if it also carries your STAN and terminal ID.
  • The second digit says what an approval commits: an 0100 holds, an 0200 posts, an 0800 touches no account. The wrong class takes the wrong amount from the cardholder.
  • An advice is acknowledged, never declined, and repeated until it is. A receiver that dispatches on the whole MTI ignores the repeats and leaves the sender repeating.
  • A request without an answer is reversed, never resent. The reversal is a new message with its own STAN that names the original in field 90.

Challenges


  1. A hotel takes an 0100 for three nights and the guest stays two. Which messages follow, and what does the cardholder see on their account in between?
  2. Your issuer receives an 0420 for a purchase it never saw, and the purchase arrives a second later. What should each message do, and what must the host remember to get it right?
  3. A network sends you 0620 administrative advices, which your dispatcher has no case for. Should it acknowledge them, answer with an error, or log them, and what does each choice cost the sender?


Design Note: Why Four Digits in Front?


The MTI puts a message's purpose before its bitmap, so a receiver knows what it holds before it parses a single field. A switch can route on four digits, and it can answer a message it doesn't support with the matching response MTI without knowing its fields.


Four digits can't name every message: the 1987 edition puts what a network message does in field 70 and leaves the rest to each network. The 1993 edition added field 24, the function code, so the MTI names a family of messages and a field names the exact one; a 1993 echo test is 1804 with field 24 = 831. A receiver now reads two places to know what it holds.
