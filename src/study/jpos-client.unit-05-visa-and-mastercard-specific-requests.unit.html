Your client has sent Visa purchases through your acquirer for a year, and product wants Mastercard in the next release. Which parts of your request code change, which come from configuration, and which can't you write until someone hands you a document you don't have yet?

That document is the network's interface specification: licensed to member institutions and processors, revised with each network release, and defining the network-specific fields byte by byte. Distrust any tutorial, this one included, that prints a "Visa field 62 layout" from memory. This unit uses what is public and stable: the ISO 8583 structure both networks build on.

Most clients never talk to Visa or Mastercard directly. A merchant system or a gateway talks to its acquirer's host, and its specification is the acquirer's interface document, which usually hides most of the differences. The unit comes down to five rules, one per section heading.

One Builder Makes What Every Network Shares

A Visa and a Mastercard purchase for 10.50 USD at one terminal, built by the same code. The PAN is masked only in print. Which fields differ?

(Packed with the course packager, GenericPackager and jar:packager/iso87ascii.xml.)

Two: the card number and field 32, the acquiring institution ID, which the acquirer assigned to this merchant once for Visa and once for Mastercard. Every other field is defined by ISO 8583:1987 and means the same on both networks. The networks differ elsewhere: in the private-use fields they define for themselves (5.4), in the values they accept in a few shared fields such as 22 and 55 (5.3), and sometimes in a layout detail such as the positions inside field 43 (5.2.2).

So one builder takes the network as a parameter, and the merchant's data comes from a MerchantProfile (5.2):

Fields 7 and 11 are left out on purpose: they belong to the moment of sending and come from the link's sequence, whatever the network (units c2 and c4).

The alternative, a VisaRequests class and a MastercardRequests class copied from it, drifts. Fix a merchant name too long for field 43 in the Visa class, because Visa purchases are the ones failing, and Mastercard purchases at that merchant keep failing. The bug report reads "Mastercard declines at one store", and everyone looks at Mastercard.

Before the profile existed, the builder looked up field 32 in a map filled from a properties file:

Mastercard goes live, and the release is deployed without the new property. What happens to the first Mastercard purchase?

ISOMsg.set(n, null) doesn't complain: it removes field n. The purchase packs, leaves and reaches the host without an acquirer ID, and nothing in your logs looks wrong. Every Mastercard purchase from this merchant fails at the host, and your support desk hears about it from the merchant.

The profile refuses instead, before anything is sent, and so does Network.of for a network it doesn't know. The tempting "if it isn't Mastercard, it's Visa" would send an American Express card as a Visa purchase with Visa's acquirer ID:

The exception comes at the first purchase, in your own code, and names what is missing. To get it before the first cardholder does, build a test request at startup for every network you accept.

Field 43 Has Positions, Not Separators

Field 43 holds three values with nothing between them. The receiver finds them by position: the name in characters 1 to 25, the city in 26 to 38, the country in 39 and 40. Here is field 43 for two Springfield merchants, CORNER CAFE and the 30-character EXAMPLE CORNER CAFE AND BAKERY, filled three ways and read back by position as a host would:

Joined concatenates the three strings. The packager pads the field to 40 characters at the end, so it packs, and the host reads one long name with no city and no country. A host that checks the merchant's country refuses the purchase. One that doesn't prints the wrong name on the cardholder's statement.

Padded pads each part to its width but doesn't cut the long name, so the field is 45 characters and doesn't pack. The IF_CHAR javadoc says it truncates, but in 2.1.7 the length check runs first. Inside a ChannelAdaptor that failure happens on the channel's thread, far from your code (unit c2).

Fitted cuts each part to its width and then pads it, as MerchantProfile.nameAndLocation does. A long name loses its end, and the city stays where the host looks for it.

Networks differ. The 25/13/2 split is common, not universal. Some specifications divide the 40 characters differently, for example with a state or region code. Take the positions from yours and keep them in nameAndLocation.

How the Card Was Read Decides the Card Fields


Field 22, the POS entry mode, says how the terminal got the card's data. Its first two digits name the method, and the third says whether the terminal can take a PIN. A keyed card has no track, so the request carries the expiry date in field 14. A stripe read carries track 2 in field 35. A chip read carries the chip's track 2 equivalent there and, in field 55, the cryptogram and the data objects the card signed for this transaction.


A chip read fails, and the cashier swipes the same card. What should field 22 say now, and which fields go?


The request is now a stripe read: track 2, no field 55, and an entry mode that says so. Integrations often get this wrong by taking the entry mode from the terminal's configuration ("a chip terminal", code 05 plus the PIN digit: 051) and the card fields from what actually happened. The swiped fallback then leaves claiming a chip read and carrying no chip data. What the issuer does with that depends on the network's rules. A decline for a good card is likely.


So set field 22 and the card fields from one value, and refuse a read that lacks its data:




The same purchase read four ways, then a chip read without chip data, then the chip data the first chip read used:



Here the chip kernel produced four data objects, packed as BER-TLV with org.jpos.tlv.TLVList. Your code copies those bytes and never computes them. Whether they travel as raw bytes or as hex text depends on how the packager defines field 55 (unit c6 shows both). Track 2 and the chip's track 2 equivalent are sensitive card data: send them, and keep them out of logs and storage (unit c8).


Networks differ. Both networks commonly use the entry-mode codes above. Your specification lists the codes you may send, adds others (for a swipe after a failed chip read, for example), may give field 22 another length (jPOS's Base1Packager declares four digits, not three), and says what field 25, the POS condition code, must carry beside it. Keep all of it in CardRead, copied from the document.

Private Fields Come From the Network's Specification, Behind One Hook


Fields 48, 60 to 63 and 120 to 127 are reserved for private or national use. ISO 8583 gives each a number and a maximum length and nothing else, so each network decides what goes inside. jPOS doesn't know the content either: its Base1Packager, written for Visa, declares fields 48, 62 and 63 as plain binary of up to 99, 59 and 255 bytes. The layouts are in the licensed specifications and nowhere else.


Keep that knowledge behind one interface, implemented once per network:




A network with no rules configured is refused, for the reason of 5.2.1:



Against an acquirer that hides the networks, both entries are NONE. Connecting to a network directly adds one class and changes nothing else. That class reads its constants from configuration (the services you are certified for, for instance) and writes subelements as nested fields such as 48.1, which pack only if the packager defines the field's subelements (units c6 and c13).


A private field filled from a blog post, from memory or from the other network's layout is either rejected, and certification takes another round, or accepted and misread, and you may find out only when a transaction is disputed.


Each Network Is a Destination of Its Own


When Visa and Mastercard traffic go to different hosts, each host gets its own ChannelAdaptor and QMUX: visa-channel with visa-mux, mc-channel with mc-mux. A QMUX doesn't route: it writes every request to its one out queue, which leads to one link, so choosing the network's host means choosing its MUX. Each QMUX names its own adaptor's ready key in <ready>, as in unit c4, because without it isConnected() stays true while the link is down:

Our scripted host approves anything. A real Visa host receives a Mastercard card with Mastercard's acquirer ID and can at best decline it. The router reports at once that the Mastercard host is unavailable, and since it sent nothing, there is nothing to reverse.


A MUXPool (unit c4) is different: its members are links to the same host, and any of them can carry any request. A pool per network, visa-pool in place of visa-mux, is fine. A pool across networks repeats the mistake above in configuration.


The Link Speaks the Network's Framing


A direct link to a network also has its own framing (unit c3). For Visa, jPOS 2.1.7 ships org.jpos.iso.channel.VAPChannel with the BASE I header (org.jpos.iso.header.BASE1Header) and org.jpos.iso.packager.Base1Packager. Here is one binary 0800 sent through a VAPChannel and a NACChannel to a loopback socket:



The message is the same 28 bytes. NACChannel puts a 2-byte length in front of it. VAPChannel puts a 2-byte length that counts the header too (0032 where NACChannel wrote 001C), two zero bytes and a 22-byte BASE I header that carries the destination station ID 222222 and the source 111111; fundamentals unit 5 takes the header apart byte by byte. A host that expects only the length, as a NACChannel does, reads the zero bytes and the header as the start of the message and can't unpack it. The station IDs are assigned to you and go in the descriptor:



jPOS has no channel named after Mastercard. Pick the channel whose frame matches the specification's, as in unit c3, and build the packager from its field table (unit c13).

Summary


  • One builder makes the fields every network shares, with the network as a parameter. Copies per network drift, and a fix reaches only one of them.
  • The network shows up as configuration: an acquirer ID per network and the merchant's boarding data. ISOMsg.set(n, null) silently removes the field, so refuse a missing value. Field 43 is cut and padded into fixed positions.
  • How the card was read decides the card fields. Field 22 and fields 14, 35 and 55 come from one value, so a swiped fallback never claims a chip read.
  • Private fields come from the network's specification, behind one hook per network, never from memory.
  • Each network is its own destination: its own MUX, never another network's link, and a channel that speaks its framing.

Field 3 transaction codes used in this unit: 00 goods and services, 01 cash, 20 refund. Positions 3-4 and 5-6 are the from- and to-account types, 00 when unspecified. Your specification lists the codes it accepts, including the one for a balance inquiry.

Challenges


  1. Your acquirer starts accepting a third network next quarter. List every place in this unit's code that changes and every value someone must add to configuration. Which would a startup check catch?
  2. A merchant's name contains É and Ø. Field 43 is 40 characters in your packager, but does the host count characters or bytes? Find out from your specification, and decide where in MerchantProfile the answer belongs.
  3. The Mastercard link is down for 20 minutes at lunchtime, and product asks for "a fallback, any fallback". What could you offer that doesn't send Mastercard cards to the Visa host, and what does each cost?
  4. Your terminals report the read method, but an older model always reports CHIP, even after a failed chip read. Where would you detect that, and what would you send?


Design Note: Why ISO 8583 Leaves Fields to the Networks


ISO 8583 could have defined every field. Instead it defines the ones every institution needs (card, amount, terminal, time, trace number) and leaves others, field 48 and the range 60 to 63 among them, to private and national use, with a number, a data type and a maximum length.


Every network has products and rules of its own, and adds more with each release. A standard that named all of that data would need a revision for each, agreed by every member, and would always lag behind. Private fields let each network change at its own pace inside a frame everybody can parse: any system can unpack a Visa message and find the amount, even if field 62 is opaque bytes to it.


Anyone who connects to more than one network pays for that freedom: the same fact about a purchase can live in different fields, with different codes, on each, in documents you need a licence to read. Keeping the common part in one builder and each network's part behind one hook puts the line in the code where the standard put it.
