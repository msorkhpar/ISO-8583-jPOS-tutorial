The client's test suite is green, run every night against the acquirer's certification host. Then the host stays silent for a minute in production, and request returns a null that no test has produced. A certification host won't decline, answer late or stay silent on demand, so a test has to play the host itself. Where to put that stand-in, and what each kind catches, comes down to five rules, one per section heading. Every output is from jPOS 2.1.7, in one JVM.

The fake returns null at once, although the client asked for 30 seconds. It also records what it was sent, which a cashier never sees: the unanswered purchase went out exactly once (unit c12 explains why a second attempt would be a second charge), and on a down link nothing went out.

A hand-written fake reads better than Mockito once the answer depends on the request. Either way, the fake has to answer the way QMUX does, and that is easy to get wrong.

Spot the Problem: The Fake That Answered With the Request

A team's three-line fake, and a slip in its client:

Every test passed. What did production do?

Line (2) reads field 39 from the request instead of the response. Against this fake that makes no difference, because line (1) turns the request into the response: they are one object. QMUX hands back a different message, unpacked from the wire, and the request never gets a field 39:

In production every approval is reported as a decline. The host has moved the money, the cashier says the card was refused, and the client sends no reversal, because a decline needs none. The cardholder pays with another card and is charged twice, until reconciliation or a dispute catches it.

So a fake answers with a new message and leaves the request alone. Like QMUX, it returns null, never an exception, when nobody answers, and calls expired on the listener form.

  1. Coding practice

    Make the fake host keep the promises QMUX keeps

    • A fake MUX lets a test decide every answer, and it must answer as QMUX does: a new message with the response MTI and the request's fields, null for silence, expired on the listener form, and a record of everything sent.

The payments team tests its clients against ScriptedMux, a stand-in host in src/main/java/com/example/practice/ScriptedMux.java. A test scripts the next answers with then(...): a response code such as "00" or "51", or ScriptedMux.SILENT for a host that says nothing. Once the script runs out, the host approves.

Last month two bugs reached production although tests had been written for both. A client that sent every unanswered authorization a second time passed the test that was meant to catch it, and a client that kept the 0100 it sent, to build a reversal from it later, found an 0110 there instead. Both times the fake was the culprit, and its answering part is now blank.

Finish the three methods marked TODO: both forms of request, and answer, which builds the response. When you're done, a client tested against ScriptedMux meets the same behaviour it will meet behind a real QMUX, for authorizations, reversals and anything else it sends. A Fake Checks Your Decisions, and Only QMUX Checks jPOS's Rules


The fake decides answers and nothing else. QMUX builds a key from each request, by default from fields 41 and 11, refuses to send a request it could never match, and hands an answer only to the request with the same key (unit c12 takes the key apart). FakeMux does none of this.


QMUX needs no socket for it: it writes requests to its <out> queue, host-send, and reads answers from its <in> queue, host-receive. A listener on those two queues, in the same Space, can play the host for a real QMUX in the test:



That QMUX is unit c1's deploy/20_host_mux.xml, unchanged, deployed by Q2. It names no <space>, so it and the queue host share SpaceFactory.getSpace(), where the queue host's ready entry makes isConnected true.


Three situations, each sent through FakeMux and through QMUX with a QueueHost, with a one-second timeout. Does the fake notice anything?


  • an 0800 echo with only field 70, no STAN or terminal ID;
  • a purchase for terminal 29110001, STAN 000417, sent while another with the same pair is waiting;
  • a purchase, STAN 000418, to a host that answers without field 41.



The fake answered all four requests. QMUX refused the echo before sending it: its key held only the queue name and the MTI, so no answer could match it. It refused the second purchase, because one answer would match both. The answer without field 41 matched no key, so the caller got null after its full second and the answer went to the <unhandled> queue, host-unhandled.


The fake compares no keys, so it answered both purchases that shared one. In production that collision takes two requests in flight at once, and unit c12 shows a gateway whose STANs collide while its tests stay green. A host that doesn't echo a key field is worse: every purchase is a null, and every null becomes a reversal.


Keep the fake for decisions. When the test is about what QMUX does with your messages (concurrency, STANs, a host's echo), run the real QMUX against a queue host: it starts in a few hundred milliseconds and opens no socket.


Only a Test That Deploys Your Files Tests Them


Neither the fake nor the queue host packs a byte or opens a connection. The channel, packager, host, port, adaptor name and queues live in deploy files that no test has run yet.


A client gets a second network, and someone renames the adaptor in 10_host_channel.xml from host-channel to visa-channel to tell the links apart in the log. The QMUX descriptor still says <ready>host-channel.ready</ready>. The fake reads no descriptor, and the queue host writes host-channel.ready itself, so neither notices. The client against those two files and a host on 127.0.0.1:



The link is up, announced under the new name, but QMUX looks for the old one and reports the link down, so the client sends nothing and returns HOST_UNAVAILABLE. In production every cardholder is asked for another payment method while the link is healthy, and the host sees no traffic, so nothing fails on its side.


The test that catches this plays the host with an ISOServer on 127.0.0.1:



Then it starts Q2 in the test's JVM on copies of the descriptors you ship. Unit c1's channel descriptor reads its port as ${host.port:8000}, so the test sets the system property host.port:




With the renamed adaptor, this test fails in its setup, at "link up", after ten seconds.


An environment variable wins. jPOS 2.1.7 reads ${host.port} from the environment (host.port, then HOST_PORT) before the system property, so a HOST_PORT on a build machine silently overrides the test.


Q2 has to run in the test's JVM: QMUX.getMUX and NameRegistrar.get read the NameRegistrar, a static map per JVM (unit c1), so a test can't reach a Q2 that a script started in another process.


Q2 can end the JVM. In 2.1.7 an exception that escapes Q2's main loop ends in System.exit(1). Maven Surefire forks a JVM for tests by default, so the build reports a crashed fork instead of disappearing. Keep it forked.


The Packager Without the Socket


Unit c9 sent the bakery's 41-character merchant name into a field that holds 40. Nothing checked it on the way in: ISOMsg.set accepts any string, and QMUX queues the message as it is. The adaptor's thread packed it when it wrote to the socket, failed, and dropped the link. A test can load the same packager file without a socket: pack a copy, unpack it into a fresh message, and compare.




The bakery's name is now refused in the build, and the test stays red until the client checks the name before sending it, as unit c9 does. The first test shows why a test compares what was sent the way the packager writes it: the client set 1500, and the host receives 000000001500. The test packs a clone because setPackager changes the message it is called on.


Use the packager file the channel descriptor names. Another packager proves only that the message fits that one.


A Test Waits for a Condition, Never for a Time


q2.start() returns at once. Q2 deploys the directory on its own thread, and the adaptor connects on another. So when can the test send? One start, with the host already listening:



Right after start, the QMUX doesn't exist yet. q2.ready(timeout) waits until Q2 has deployed the directory once, so the QMUX is registered, but the adaptor may not have connected. In eight of twelve runs the link was still down at that moment, and a millisecond later it was up in all twelve.


That millisecond makes a test flaky. It is longer on a loaded build server, and much longer when the host isn't listening at the first attempt. Here the host started 200 ms after Q2:



The first connect failed, and the adaptor tried again after its reconnect-delay of 10 seconds. A test that sleeps two seconds after start passes on the developer's machine and fails on the build server whenever the host is slow to listen. A test that fails now and then gets re-run until it passes, and then its real failures get re-run too.


So the test in 10.3 waits for the two things it needs with jPOS's blocking reads. NameRegistrar.get("mux.host-mux", 10000) returns once the QMUX is registered, and SpaceFactory.getSpace().rd("host-channel.ready", 10000) once the adaptor announces the link, the entry that isConnected reads (unit c1). Each returns null after 10 seconds. When the condition holds after 3 ms, the test goes on after 3 ms, and the 10 seconds only bound a failure. Start the host before Q2, too, so the first connect succeeds.


The no-answer path waits the whole request timeout, so give it a short one: silentHostIsNoAnswer waits 300 ms, not production's 30 seconds. And a test that checks something on another thread, such as a reversal reaching the host from a store-and-forward queue (unit c12), waits for the host to receive it, not for a guessed number of milliseconds.

Problem statement


An integration test checks that a reversal leaves the store-and-forward queue and reaches the host. The SAF sends on its own thread, so the test asks the host's log for it: awaitReceived("0420", 5000). The test host puts every message it receives, in order, on a Space queue, and HostLog in src/main/java/com/example/practice/HostLog.java reads that queue.


The test fails about once in twenty runs on the build server and never on a laptop. Nobody has found the cause, so the team re-runs the build until it passes. awaitReceived sleeps half a second and then looks once.


Rewrite awaitReceived, the one method marked TODO. It returns the next message of the asked type, as soon as the host has it, and gives up when the time the test allowed is over. Network messages such as echoes can reach the host at any moment and are not what the test is waiting for. When the message doesn't come, the failure must say so in the test that waited, not as a NullPointerException three lines later. About ten lines.


Some of the tests deliver a message only after your code has started looking for it.

A Load Test Is Judged by Its Slow Tail and Its Nulls


A load test runs outside the unit suite, against the embedded stack or a simulator (unit c16), never a certification or production host.


Here 2000 purchases from 20 threads go through the stack of 10.3 with a 500 ms request timeout, and the host ignores one purchase in fifty. Each purchase takes its STAN from one StanSequencer (unit c4), because random STANs on one terminal ID would sooner or later collide in QMUX:



The mean is about 11 ms. Is the client fast?



Half the purchases took under 0.3 ms, and 40 took the full 500 ms and came back null. The mean describes neither group.


The second line is what a report shows when it drops the null samples as "errors": a p99 of 6.1 ms. Yet 40 cardholders waited the whole timeout for "outcome unknown", and each of those purchases now needs a reversal. A null is a request that took as long as you let it, so it goes into the latencies at that time, and the null count goes beside the percentiles.


Size the load as a rate from the business: the busiest hour's purchases divided by 3600, times a factor for bursts. Threads are only what it takes to reach that rate.

    Report a load run so the timeouts show
    

      

    • A load run is judged by percentiles over every request, with each null counted at the time it waited, and by the number of nulls; the mean and answered-only percentiles hide the timeouts.

Summary


  • A test plays the host through MUX. Declines, silence and a down link become short tests, if the fake answers as QMUX does. Otherwise it hides bugs production finds.
  • A fake checks decisions; QMUX checks the rules. Key fields, duplicate keys and a missing key field show up only with a real QMUX, against a queue host.
  • Only a test that deploys your files tests them. Run Q2 in the test's JVM on the shipped descriptors, and round-trip through the link's packager.
  • Wait for a condition. q2.ready means deployed, not connected: block on the registry and ready entries.
  • A load test is judged by its tail and its nulls. Count a null at the time it waited, and report how many there were.

Design Note: Why Cut at the MUX Interface?


Above the MUX interface are your decisions; below it are jPOS's keys, queues, adaptor, packager and socket. Its four methods are small enough to fake in about fifty lines.


Cutting higher, behind your own interface such as a PaymentGateway, makes the fake easier to write and lets it drift from jPOS: it returns what the team wishes the network did, such as an exception for a timeout instead of QMUX's null. Cutting lower, at the socket, makes every test pay for framing, a packager and a server. An HTTP mock such as WireMock can't stand there at all: a jPOS channel writes a length header and an ISO 8583 message, not an HTTP request.


The price of the MUX cut is that the fake has to keep the interface's promises, which 10.1.1 shows breaking, and that it can't keep QMUX's, which is why the queue host and the embedded stack exist.
