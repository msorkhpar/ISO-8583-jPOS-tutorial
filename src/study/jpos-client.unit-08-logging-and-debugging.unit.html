The acquirer's support desk calls about a purchase from 10:15 that their host declined with response code 30, format error. They want what you sent and what came back. You open the log. Either the exchange isn't there, or it is there with the card number in clear, and you can't send it to anyone.

Unit c1 put ProtectedLogListener at the front of the Q2 logger. What that filter can and cannot see, how an event reaches a logger at all, and where to look when the log is silent come down to seven rules, one per section heading.

A Log Event Holds One Piece of Work and Is Written When the Work Ends

Two purchases are in flight on one link, and the client logs one line per step, as most Java code does:

Which purchase got no answer? That is the one you must reverse (unit c9), and the log can't tell you. A STAN on every line helps until twenty exchanges are in flight and the support desk has to stitch each one together from scattered lines.

In jPOS, a LogEvent collects everything about one piece of work, and the logger writes it as one block when the work is over. This sender creates the event before the request and writes it in finally:

Two purchases through a real QMUX; the host answered the first after 300 ms and dropped the second:

The second block answers the support desk on its own: purchase 000732, no response, after 1002 ms. lifespan runs from creating the event to writing it, so creating it at (2) makes it the duration of the exchange. The tag (info, warn, error) says how the work ended, and realm says which component did it. Writing at (4), in finally, keeps the failures: an event written only on the success path is missing for every exchange that went wrong.

An Event Goes to Its Source's Logger, and a Channel Without One Writes Nothing

Logger.log(ev) is static, so which logger receives the event? We gave our own logger (mine) and the Q2 logger each a listener that counts events, and logged "hello" four ways:

The event's source decides: Logger.log asks the source for its logger. An event built with new LogEvent(tag) has no source, so it falls back to Q2. In a test with a fresh logger that is nowhere you look, and the test reports that nothing was logged. An event created by a Log (line (1) above) reaches the logger the Log was given. Such an event is also marked to honour its source's logger, so when the Log has none (the third line) it does not fall back to Q2. It goes nowhere, and nothing tells you.

QBeans such as the ChannelAdaptor and QMUX start out with the Q2 logger, attribute or not. The objects a QBean builds from its child elements are different: the channel inside an adaptor, a packager, a request listener that implements LogSource. Q2 calls their setLogger(logger, realm) only when their own element has a logger attribute. Without it they drop every event the way new Log() does, so the channel needs its own attribute:

We sent one purchase through this client in Q2 three times: as shown (full), without logger="Q2" realm="host-channel" on <channel> (nochannel), and with the attribute back but no 00_logger.xml (nologger), and counted the events other than Q2's own. The second receive is the channel noticing the socket close at shutdown:

Without the channel's attribute, the purchase went out and its answer came back, and the log has no connect, send or receive. The adaptor's own logger covers only the adaptor. The support desk asks for the 10:15 exchange, and it was never written.

Without 00_logger.xml, Q2 finds no listeners on the Q2 logger and attaches a console writer with no filter. Nothing fails, and the console, with whatever collects it from the container, carries the card number and track 2 in clear.

The jar's own template. jPOS 2.1.7 carries a sample 00_logger.xml under META-INF/q2/installs/deploy/. It has a console writer, a buffer and a DailyLogListener, and no ProtectedLogListener. Add the filter before you use it. One of its comments says compression defaults to gzip; in 2.1.7 it defaults to none.

The Filter Masks Messages, Never Text


With the filter first in the chain, is everything after it safe? We logged the same purchase six ways through ProtectedLogListener (protect 2 35 45, wipe 52 55) and a writer into a buffer, and searched the output for the card number. The Exchange row is 8.3.1's subject; the last line checks the message we hold afterwards:



The logger, as a test builds it:



ProtectedLogListener never reads the text that will be written. It walks the event's list of messages and replaces each one that is an ISOMsg with a masked copy (it also looks inside a jPOS SimpleMsg). A string that contains a card number is left alone. ISOMsg.toString() and a list of messages print only 0200 000731 29110001: safe, and no help to the support desk. Because the filter masks a copy, the message on the wire keeps its PAN. When a string has to mention a card, protect it yourself: ISOUtil.protect("4111111111111111") gives 411111______1111.


Spot the Problem: The Exchange Record


A developer wants each request and its response grouped in the log, and writes a small Loggeable for it:



After a decline the sender calls log.warn(new Exchange(request, response)). The block looks like the <isomsg> blocks of 8.1, and the filter is first in the chain. What does the log hold? The card lines of the writer's output:



The card number, track 2 and the PIN block, in clear, twice. The event's only message is an Exchange, not an ISOMsg, so the filter passes it through, and line (1) dumps the real messages when the writer asks. A PCI assessor finds card data in a correctly configured log, and every such event since the change went live has to be purged from every copy that log shipping made.


An ISOMsg is masked only if it is itself a message of the event (or sits in a SimpleMsg). Add the request and the response to the event directly, as LoggedSender does. The same trap catches any object that holds messages and dumps them itself, such as a TransactionManager's context (unit s8).


Bytes and Packager Traces Are Text Too


A format error means the host could not parse something you sent, so the support desk asks for the bytes. ISOUtil.hexdump gives the offset, hex and ASCII view of what pack() produced:



The PAN starts at 0x16, track 2 at 0x3A, and the PIN block is the last sixteen characters. A dump is a string, so no filter touches it, and the packager's own trace is text too. With packager-logger set on the channel, GenericPackager logs a <pack> and an <unpack> event for every message, and with ProtectedLogListener first the unpack event still carried:



A reply the channel can't unpack is logged as a hex dump too, its card number in clear; unit c17 shows that event and a filter that withholds it. For a message that carried a real card, mask a copy and dump the copy:




Masking keeps every length, so the bitmap, the length prefixes and each field's position are what the host received, and a format error is about those. Dropping field 2 instead would show the analyst a different message from the one their host rejected.

A Realm Filter Narrows the Log and Drops Everything It Doesn't Name


In a busy log you want only the channel and your sender. RealmLogFilter keeps the realms listed in <enabled> (or drops those in <disabled>). It goes after ProtectedLogListener and before the writers:



We gave it events from seven realms and one with no source:



The filter cuts the realm at the first / and compares the rest exactly, which is why the channel, whose realm carries the address it is connected to, matches. A dot is not a separator, so client.sender.retry is a different realm. Name sub-components with a slash if one entry should cover them.


What it drops, it drops for every listener after it, because it returns null and the chain stops (with dump-interval set, it now and then passes on a summary of the realms it dropped). Q2 keeps watching deploy/ and reports a descriptor that fails to deploy, at start-up or later, under Q2.system. With this filter in place, a typo in 20_host_mux.xml makes the MUX vanish without a word in the log, so add Q2.system to the list. Q2 redeploys 00_logger.xml when it changes, so you can add the filter for an hour and remove it without a restart.


A Late Answer Is Counted, Not Logged, by the MUX


The host's log says it approved purchase 000732, and your request returned null. Your sender's warn event is all your code wrote. Where did the approval go?


It arrived after the wait was over, found nobody waiting for its key, and went to the MUX's <unhandled> queue (unit c12 follows that path). If the channel has its logger, its <receive> event shows the 0210, but nothing ties it to the request. QMUX writes no event for it; it only counts it. SystemMonitor, a QBean you deploy as 99_sysmon.xml, writes one event every sleepTime milliseconds with the state of the JVM and of every component registered in the node:



Our node's host answered 000731 and 000733 at once and 000732 after 1.5 seconds, against a one-second timeout. The end of the monitor's event:



The channel received three messages and the MUX matched two. One request ended with no answer (rx_expired=1), and one answer matched nothing (rx_unhandled=1). tx_expired=0 says the unanswered request did go out. A connects count that keeps rising is a link that keeps dropping, and tx rising with rx flat is a host that has gone quiet. rx_unhandled counts only when the MUX has an <unhandled> queue. Without one, and without a channel logger, a late answer leaves no trace at all.


The event's first lines also carry the process's user name, host name and working directory. Treat it like any other log before you paste it into a ticket.


A Bridge to SLF4J Sits After the Filter and Keeps Each Event Whole


jPOS into SLF4J. The operations team wants everything in Logback, and jPOS 2.1.7 ships no listener for it. Write one that renders each event whole, as one SLF4J message, and put it after ProtectedLogListener:




With Logback 1.2 on the classpath, a warn event like 8.1's dropped purchase, logged through the filter and the bridge, comes out as one Logback record:



The bridge is a writer, so the filter must come before it; placed first, it ships clear card numbers to whoever can search the log platform. Split into lines, an event is back to the scattered lines of 8.1.


SLF4J into jPOS. Libraries you use may log through SLF4J. When there is no SLF4J binding on the classpath, Q2 2.1.7 tries to bind SLF4J to its own Q2 logger at start-up, so that library messages appear under realms such as slf4j::com.example.lib. On a current JDK that attempt fails quietly. Our program called the same binder and printed the exception Q2 discards, then SLF4J's warning:



SLF4J falls back to a logger that discards everything, so the library's messages go nowhere. Start the JVM with --add-opens java.base/java.lang=ALL-UNNAMED and the binding works. If the project already has an SLF4J 1.7 binding (Logback 1.2, as spring-boot-starter-logging 2.x brings), Q2 leaves SLF4J alone and that binding gets the messages. Q2 looks only for the 1.7-style binder class, so an SLF4J 2 binding doesn't stop it from trying.


Which JDKs. We saw the failure on Java 21 and 26. Java 17 already denies this kind of access by default, so expect the same there.

Summary


  • One piece of work is one event, created when the work starts and written in finally. It keeps a request with its answer, its duration and how it ended, even when the call throws.
  • An event goes to its source's logger. An event without a source goes to Q2, a channel without a logger attribute writes nothing, and a node without 00_logger.xml writes everything to the console unmasked.
  • The filter masks ISOMsg objects in the event, never text. Strings, and wrappers that dump messages themselves, pass through in clear. Protect strings with ISOUtil.protect.
  • Dumps and packager traces are text. Share a dump of a masked copy, which keeps every length and so keeps the bug you are hunting.
  • A realm filter stops the chain for every realm it doesn't name, Q2.system included.
  • The MUX counts a late answer and logs nothing. rx_unhandled and the other QMUX counters in SystemMonitor tie it to the MUX when the log can't.
  • A bridge to SLF4J is a writer, so it goes after the filter and keeps events whole. Q2's own SLF4J binding needs --add-opens on a current JDK.

org.jpos.util.SimpleLogListenerwriter: System.outnone
org.jpos.util.RotateLogListenerwriter: one file, rotatedfile, window (seconds), copies, maxsize (bytes), rotate-on-startup
org.jpos.util.DailyLogListenerwriter: one file per period, named by dateprefix, suffix (.log), date-format (-yyyy-MM-dd), sleeptime (seconds, default one day; the jar's template says window, which this listener ignores), compression-format (none, gzip, zip), maxsize, maxage


Neither file writer creates its directory (unit c1).


LoggerAdaptor (00_logger.xml): <property name="redirect" value="stdout, stderr"/> sends System.out and System.err through the logger.


The event header: realm is the source's realm; at is the local time when the event was written; lifespan is the time from creating the event to writing it, left out when it is 0 ms.


Packager logging (properties on the <channel>): packager-logger (a logger name), packager-realm, packager-log-fieldname (default true). Test cards only.


SystemMonitor (99_sysmon.xml): sleepTime (ms, default 3600000), detailRequired (default false; true adds each registered component's own dump, such as the counters below).


QMUX counters: tx requests sent, rx answers matched, rx_expired requests that ended with no answer, tx_expired those of them that never left the queue, tx_pending messages still in the <out> queue, waiting for the adaptor to send them, rx_pending requests waiting for an answer now, rx_unhandled messages nobody waited for (counted only with an <unhandled> queue), rx_forwarded messages offered to the MUX's request listeners.


Challenges


  1. Your log platform keeps logs for a year and is searchable by three hundred people. Your network wants field 45 (track 1) masked as well, and a field 127.2 that carries the PAN again. Write the protect and wipe lists, and decide how you would prove, every night, that no clear PAN reached the log.
  2. A LoggedSender event is created before request and written after it. At 500 exchanges a second with a 30-second timeout, how many events can be open at once, and what does that cost in memory? When would you write an event early?
  3. The support desk wants a hex dump of every message their host rejected with code 30 last month. Design how you would capture them, given that the client keeps no raw bytes and must not log card data.
  4. RealmLogFilter compares realms exactly. Design a realm naming scheme for a client with two links, a sender per link and a reversal process, so that one <enabled> list can show one link's whole story.


Design Note: Why Mask in the Logger and Not in the Message?


It is tempting to mask the PAN in the message before you log it. jPOS masks a copy in the logger instead.


The message has to stay real. The host needs the PAN, and the same object travels from your code through the MUX to the channel, which logs it on the way out. Masking it in your code would either break the transaction or force every caller to copy it first. Masking in the logger means one decision, in one file, applies to every component that logs a message: the channel, the MUX, your sender, and libraries you didn't write.


The price is that the filter protects only what it recognises, an ISOMsg. Every leak in this unit came from turning a message into something else before the filter saw it.
