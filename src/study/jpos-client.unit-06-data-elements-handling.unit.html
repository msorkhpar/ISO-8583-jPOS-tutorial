The new chip terminals go live on Monday. Stripe purchases are approved as before, but every chip purchase is declined for bad chip data. The host's trace shows field 55 as 58 bytes. The terminal produced 29.

The terminal's software hands over the chip data as hex text, and the client sets it with m.set(55, iccHex). Nothing threw, the message packed, and the host received the wrong bytes. The cause is in what an ISOMsg field holds.

Every output below comes from a program run against jPOS 2.1.7, packing with the course's jar:packager/iso87ascii.xml unless the text says otherwise.

A Field Holds Text, Bytes or a Message

Each value in an ISOMsg is an ISOComponent of one of three kinds:

  • ISOField holds a String. set(n, String) makes one.
  • ISOBinaryField holds a byte[]. set(n, byte[]) makes one.
  • ISOMsg holds other fields. A field with sub-fields is a message inside the message (6.3).

Below is a purchase with one of each, read along with a field it doesn't have. What does getString return for field 55, which holds five bytes, and for field 48, which holds sub-fields?

getString on bytes gives their hex form, ten characters for five bytes. getBytes on text gives the characters as ISO-8859-1 bytes. On a nested message both return null, although hasField(48) is true: you read it through its sub-fields, getString("48.1").

An absent field never throws: getString, getBytes and getValue return null, and setting a field to null removes it (unit c5). getMTI is the exception. With no MTI it throws ISOException (MTI not available).

Receipt code goes wrong on that null. Field 38, the approval code, comes back on approvals only:

Every approval prints a receipt, so the tests pass. The first decline in production throws on the thread that holds the host's answer. A caller that treats an exception as "no answer" reverses a purchase the host declined, and the terminal shows a communication error. The cashier tries the card again and gets the same decline, with a reversal in the log for each attempt. Read any field the host may leave out with a null check or with the constant first: "00".equals(response.getString(39)).

Binary Data Goes In as Bytes

On Monday the terminal hands over its 29 bytes of chip data, the TLVs unit c5 built with TLVList, as 58 hex characters. The string set as it came, and the same data set as bytes:

39 46 32 36 is the ASCII for the characters 9F26: the host received the hex text, twice as long. Read as TLV, its first tag is 39 and nothing after it makes sense, hence the decline on every chip card.

jPOS converts hex in one case only: set(int, String) asks the message's packager whether the field is binary, and if so stores hex2byte(value). A new ISOMsg has no packager. The channel attaches its own when it sends (BaseChannel.send calls setPackager just before packing). Field 52, the PIN block, is binary in iso87ascii.xml, so it shows both cases (iso87 is a GenericPackager loaded from that file):

A request built from scratch is the second case. Behind a QMUX and a ChannelAdaptor the pack fails on the channel thread, as in unit c2, and mux.request waits out its timeout and returns null.

The first case turns up where you don't expect it: clone() copies the packager along with the fields, so a copy of a message that was already sent converts hex again. Field 55 in iso87ascii.xml is declared as text (IFA_LLLCHAR), so there nothing fails at all and the hex goes out as it is. A packager that declares 55 as binary, such as iso93ascii.xml, does the same with a string set before it was attached: it sends the 58 characters as 58 bytes. Convert at the edge, where the hex comes in, and set bytes: set(55, ISOUtil.hex2byte(hex)). Then the packager decides only how the bytes travel.

set(n, byte[]) stores your array itself, not a copy. A PIN pad driver that reads every PIN block into the same buffer makes every request share it:

The bytes are read when the message is packed. A request that waits in the out queue while the link is down (unit c4) is packed after the next cardholder has typed a PIN, and goes out with the wrong PIN block. Give the message its own copy, set(52, pinPad.clone()), whenever the array isn't yours to keep.

  1. Coding practice

    Hand the terminal's chip data and PIN block to the host intact

    • An absent field reads as null from every getter but getMTI, so optional fields are read with a null check.
    • Binary data is set as bytes; a hex string becomes bytes only if a packager is attached when it is set, so in a client it goes out as text or fails to pack.
    • set(n, byte[]) keeps the caller's array, so a reused buffer changes a request that has not been packed yet.

Sub-fields Are a Nested Message That Only a Declaring Packager Can Carry


Say the acquirer's interface document splits field 48 into sub-fields: 1 is the order channel (three characters, ECM for e-commerce), 2 the merchant's order reference (up to 25 characters with a two-digit length). In an ISOMsg, field 48 then becomes an ISOMsg whose own field number is 48, and a dotted path reaches inside it:



The layout of those sub-fields is in the packager, not the message, and the stock iso87ascii.xml declares field 48 as plain text. The acquirer's packager is a copy of it whose field 48 declares the two sub-fields. The same message packed with each:




With the declaration, field 48 is 014 (14 characters follow), ECM (sub-field 1, fixed at three), then 09INV-20931 (sub-field 2 behind its own length). The outer class, IFA_LLLCHAR, writes the field's length; GenericSubFieldPackager lays out the inside. Without the declaration the text packager is handed a message and fails, on the channel thread. emitBitmap="false" suits sub-fields that always come in order; unit c13 covers the other attributes, including a sub-field bitmap.


Setting sub-fields by path keeps the ones already there. Setting a new ISOMsg(48) replaces the field, as set does with any component. From 48.1 and 48.2 set by path, one message gets a new ISOMsg(48) holding only sub-field 1, the other set("48.1", "MOT"):




When two steps of your code each fill in their own sub-fields, the one that builds a fresh ISOMsg(48) erases the other's without an error.


The Receiving Side Needs the Declaration Too


The same bytes unpacked as a client unpacks a response, once with each packager:



Nothing failed on the stock side. The field is there as 14 characters of text, and every dotted path into it returns null, because getString("48.2") finds text where it expects a message. The same happens with any field declared as text, and iso87ascii.xml declares 48, 60 to 63 and 120 to 127 that way (IFA_LLLCHAR). If the host returns loyalty points in sub-fields of field 63 and your channel still uses the stock packager, every response reads as "no points", and no log line explains why. Both ends of a link need the same declaration, so the packager named by the channel's packager-config must declare the sub-fields. A test that unpacks a recorded response from the host and reads one sub-field catches the mismatch.

A Follow-up Copies the Fields It Lists and Leaves the Original Alone


Many messages start from another one: a response from its request, a reversal from its original (unit c12), a completion from a pre-authorization. A hotel authorizes 300.00 at check-in with an 0100, stores the request, and at check-out sends the final 254.30 as an 0220 completion advice built from it:




clone(int...) copies only the listed fields into a new message, so the check-in's track 2, PIN block and chip data (35, 52, 55) stay behind. The stored original still says 0100 and 300.00, which matters on the day someone reverses it.


The other way is to copy everything and remove what shouldn't go:




Whoever wrote the unset remembered track 2 and the PIN block. The chip data went out with the completion and sits in every store-and-forward queue and log that keeps completions. With a list of what to keep, a forgotten field is missing instead: the host says so, and you add it.


clone() and clone(int...) give the copy its own field map and nested messages, but the text and byte fields are the same objects as in the original:




Writing into the array that getBytes returns writes into both messages. Change a copy through set and unset only.


A response is a follow-up too. setResponseMTI() turns the request's MTI into the response's, and a repeat gets the same response MTI as a first attempt:



A test host, the stand-in for the real host that unit c12 builds, answers the same way: it clones the fields it echoes, sets the response MTI and adds field 39. The request it was given stays as it was.


Networks differ. Your network's specification says which fields a completion carries, whether it points back at the pre-authorization through field 90 (Original Data Elements, unit c12) or the approval code, and whether it is an 0220 at all. Either way, list what you copy.

Summary


  • A field holds text, bytes or a message. getString on bytes gives hex and on a nested message gives null; an absent field gives null everywhere, so read optional fields with a null check or the constant first.
  • Binary data goes in as bytes. A hex string is converted only if a packager is attached when you set it, which a new message doesn't have, so it goes out as text or fails to pack. set(n, byte[]) keeps your array, so give it one nobody else writes to.
  • Sub-fields are a nested ISOMsg, set and read by dotted paths. Only a packager that declares them can pack them, and a receiver without the declaration gets flat text and a null for every sub-field, without an error.
  • A follow-up lists the fields it copies, never copies everything and prunes. The copy shares its leaf values with the original, so change it through set and unset.

Challenges


  1. Your terminals send chip data as hex over JSON, and your host wants it as raw bytes. Where does the conversion belong: in the JSON layer, in the code that builds the request, or in a channel filter? What does each choice make harder to test?
  2. Write a unit test that would have caught Monday's declines before release. What does it pack with, and what does it compare?
  3. A host adds a sub-field 3 to field 48 in its next release, and old clients will keep sending two. With emitBitmap="false", what does your packager send for a message that has sub-fields 1 and 3 but not 2? Run it, and decide whether you want a sub-field bitmap.
  4. A completion is built from a pre-authorization stored eight hours earlier. List the fields that must come from the original, the ones that must be new, and the ones that must never be stored at all. Which of them does your network's specification decide?


Design Note: Why a Field Can Be a Message


jPOS models a message as a tree. ISOMsg, ISOField and ISOBinaryField all extend ISOComponent, so a field can be a leaf or a whole message, and the same packing code recurses into it. That is why a network's sub-fields cost one XML element and no Java, and why 48.2 reads like a path.


The price is that the message carries no layout of its own. An ISOMsg doesn't know that field 48 has sub-fields until a packager tells it, or that field 52 is binary unless a packager is attached when you set it. A message built in your code and the same message unpacked from the wire can hold the same data as different components. Code that reads fields by kind (bytes with getBytes, sub-fields by path, absence as null) works on both; code that assumes one kind breaks when the packager changes.
