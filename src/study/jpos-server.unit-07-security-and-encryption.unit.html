A tester on the acquirer's security review sends our server a refund of 950.00 to card 4111111111111111, from terminal 29110002, with eight zero bytes where the MAC goes. The server answers 63, security violation. The Visa network credits the 950.00 to the card anyway.

The MAC check did run. It had been added as the last participant before the response was signed and sent, and by then QueryHost had forwarded the refund and the network had approved it.

Every terminal's PIN blocks, MACs and card numbers arrive at the server. Unit c7 showed what a client does with each; on the server, each step has a place in the TransactionManager and leaves something behind. TLS on the QServer is unit s3's subject. Four rules, one per section heading.

A Server With a Security Module on the Desk

The server's security module is unit c7's SMAdaptor descriptor, saved as deploy/05_hsm.xml, which registers the module as hsm and names logger="Q2". A client holds a handful of keys. A server holds two for every terminal, a PIN key (TPK) and a MAC key (TAK), plus the keys of each network link. They live in a key store, which Q2 deploys as a QBean and registers under its name, here ks. This is deploy/06_keys.xml:

SimpleKeyFile keeps each key under an alias of your choosing. We use the purpose and the terminal ID: tpk.29110001, tak.29110001. A setup program, run once per development machine, creates the module's master key (the LMK) and loads the published test keys:

Part of the file it writes:

Each key is encrypted under the LMK in cfg/dev.lmk, and each check value is the one you compare with the terminal vendor's or the network's (unit c7).

The server is unit s5's forwarding chain, with three security participants that this unit builds:

Requests come through unit s4's DirectTerminal, from a terminal with its own module and the same clear keys. It encrypts the PIN under its TPK, signs with its TAK, and checks every answer's MAC as unit c7's client does. Behind the visa QMUX's queues, unit c7's test acquirer plays the network: it reads the PIN with the network key and answers 00, or 55 for a wrong PIN. Every output in this unit comes from jPOS 2.1.7 run this way, in one JVM.

A Request's MAC Is Checked Before Anything Acts on It

VerifyMac checks the MAC with unit c7's MacService, under the key of the terminal that field 41 names. A request without a MAC, or from a terminal with no key on file, fails like a wrong one. On failure it leaves a 63 answer built with unit s4's Responses.reply and votes ABORTED, and SendResponse sends that answer on the abort path (unit s1).

We sent the opening's forged refund (processing code 20, a refund), then a genuine purchase from 29110001, once with VerifyMac after AnswerFailures and once first, as above:

The terminal sees the same answers in both runs; only what the network received differs. The forged refund's trail with VerifyMac after AnswerFailures (SignResponse, an abort participant, is 7.4's):

QueryHost sends in prepare without waiting for the vote (unit s5), and an abort reaches only participants that joined, which it didn't. Our server put its 63 in the Context in place of the network's approval, so its records show a declined refund. The network has credited 950.00, and nothing on our side reverses it. A forged purchase on a stolen card number goes the same way: approved at the issuer, declined in our records.

After an abort nothing commits, a participant that joined gets its abort to undo what it reserved, and what is in the Context never leaves our server. What a participant does outside the server in prepare, as QueryHost does, nothing calls back. So VerifyMac goes first, and a forged message costs one 63 and touches nothing else.

A PIN Block Is Safe Only While Its Key and the LMK Stay Apart

The translation is unit c7's translatePIN; the server's part is choosing the key, the TPK of the terminal in field 41. QueryHost sends a copy, UPSTREAM, in place of REQUEST: it carries the translated block and not the terminal's MAC, which belongs to the terminal's link. The request stays as the terminal sent it. Three PIN purchases of 20.00 on card 4111111111111111; the first line is the first purchase's field 52:

Terminal 29110002 has a MAC key but no PIN key yet, so its purchase got 96 and the network never saw it.

Why a key per terminal? A terminal stands in a shop, and keys can be extracted from a stolen one. With one PIN key shared by all terminals, that key reads the PIN blocks of every terminal you serve. With a key per terminal, it reads one shop's.

A copy of the key file is harmless only because its keys are under the LMK. Someone copies cfg/keys, and has the block 2A3D408A1977DDE9 from the terminal's link. They load the TPK into a module of their own, then try again with a copy of cfg/dev.lmk as well:

Under another LMK the TPK almost always decrypts to bytes without DES key parity, and the module refuses them. Under ours, the PIN comes out. So the LMK file never sits where the key file, the logs or their backups sit. A hardware module keeps its LMK inside the device. The software LMK is for development only (unit c7).

Spot the Problem: The Module That Logged Everything

Both descriptors in 7.1 name logger="Q2", as every QBean in this course does. Here are parts of log/q2.log after the PIN purchase above. Which of these would you mind someone reading?

The s-m-adaptor realm logs every call to the module with its parameters. The translation entry holds the terminal's PIN block next to the TPK, as the key file stores it, so with dev.lmk the log alone reads PINs. The MAC entry holds the packed request in hex, and 3431313131… is the card number, 4111111111111111. The key-store realm logs each key it hands out as well. ProtectedLogListener masks fields of a message in the event (unit s1); a byte array in hex is not a message, so it passes untouched.

Deploy SMAdaptor and KeyStoreAdaptor without a logger attribute. We removed it from both descriptors and ran the same purchases. The log had no s-m-adaptor or key-store entry, and no card number in hex. Turn the module's log on only on a test system with test cards.

  1. Coding practice

    Let only genuine requests through to the network

    • A request's MAC is verified under the key of the terminal it names, before any participant acts on it; a missing MAC or an unknown terminal fails like a wrong MAC, and a participant that sends in prepare acts before a later abort.
    • A PIN block is translated from the TPK of the terminal in field 41 to the network's key, on a copy for the network without the terminal's MAC; a block that can't be translated is refused, never sent on without it.

Every Response Is Signed, on the Abort Path Too


A terminal that checks MACs, as unit c7's client does, believes only an answer that verifies under its key. Our first signing step was a plain participant right before SendResponse:



Two purchases from 29110001: the network answers the first and stays silent on the second, so unit s5's AnswerFailures answers 91. What does the terminal make of each?



The 91 left unsigned. After CheckHostAnswer voted ABORTED, the TransactionManager asked only abort participants (unit s4), and PlainSignResponse isn't one. Every answer the server builds on the abort path goes out the same way: VerifyMac's 63, TranslatePin's 96, each decline of AnswerFailures.


The terminal can't tell an unsigned decline from a forged one. Unit c7's client reports the purchase as unknown, reverses it and raises a MAC alert. Ten minutes of network outage at 50 purchases a minute make 500 reversals for our server to answer and 500 MAC alerts. A real tampering attempt in those ten minutes looks like all the others.


The signing step is an abort participant, so both paths reach it:




It stands after everything that builds or changes the answer, so it signs what is sent, as unit c7 requires of a client. It sets the packager of the terminal's link on the answer: a network's answer was unpacked with the network link's packager, and the MAC must cover the bytes the terminal receives. Signing also replaces any field 64 the answer carried: a MAC under the network's key, or the request's own MAC in an answer cloned whole, means nothing to the terminal. When the network signs its answers, check its MAC when the answer arrives, after QueryHost, as unit c7's client checks a host's; an answer that fails it is no answer.

A Key Is Loaded While the Server Runs, and Never Written in Clear


A new terminal arrives with keys of its own. They come as unit c7 described: clear components typed in at a key ceremony, or a key encrypted under a key-encrypting key the two sides share. Either way the module turns them into a key under the LMK, and that is all the key file ever holds. The ceremony program writes it to the same file the server reads, as LoadTestKeys did in 7.1.


Does the server need a restart to use it? A SimpleKeyFile that is already open, asked for tpk.29110002 before and after another program adds that key to the file, then after it replaces the key:



SimpleKeyFile reads the file again on every lookup, so the next PIN purchase from 29110002 translates without a restart. A replaced key takes effect the same way, at the next lookup. A terminal still MACing with its old key gets 63 from then on, so a key change is agreed with the other side and loaded at the moment both sides switch.


The keys for card data at rest follow the same rule. Unit s9 stores card numbers under an AES key and finds them by an HMAC key; those keys come from a key store or the HSM, with the key store's password from the environment (unit c3), never from the descriptors or the database.

Summary


  • A request's MAC is checked before anything acts on it. VerifyMac goes first, with the key of the terminal in field 41. Behind QueryHost, a forged message reaches the network, which approves it while our records say declined.
  • A PIN block is safe only while its key and the LMK stay apart. Translate with the terminal's own TPK, keep the LMK away from the key file and the logs, and deploy the module and the key store without a logger: their log holds PIN blocks, keys and card numbers in hex.
  • Every response is signed, on the abort path too. SignResponse is an abort participant right before SendResponse. An unsigned decline is an unknown outcome to the terminal, and it reverses.
  • A key is loaded while the server runs, and never written in clear. The key file holds keys under the LMK and is read again on every lookup, so a new terminal needs no restart; a changed key takes effect at once, so change it when the other side does. Keys for card data at rest (unit s9) come from a key store or the HSM, never from configuration.

Challenges


These have no single answer.


  1. Terminal 29110002 gets a new TAK at 02:00, and its first purchase after that is MACed with the new key before your key file has it. What do you load first, what do you keep, and for how long?
  2. SignResponse can't sign when the terminal has no TAK on file, and VerifyMac refuses that terminal anyway. Should the 63 go out unsigned, or not at all? What does the terminal do in each case?
  3. A network changes its PIN key (zpk.visa) every day at 02:00. Purchases are in flight at that moment, some already translated under the old key. What do you load, when, and what does the network need to accept for a while?
  4. A hardware module answers in 5 ms, and every PIN purchase now needs three calls to it. At what rate of purchases does the module become the bottleneck, and what would you measure first?


Design Note: Why the Server Keeps Keys It Can't Read


Every key in cfg/keys is useless to the server's own code. The code passes those bytes to the module, and only the module, holding the LMK, turns them into something that can decrypt. A server with thousands of terminals keeps thousands of keys this way, none of them in a form that the process, its heap dumps or its backups can use.


The price is that every PIN and every MAC is a call to the module. A hardware module is a separate box with its own throughput and failure modes, and the server can't authorize a PIN purchase without it. The boundary also holds only while nothing copies what crosses it. The module's own log, which writes PIN blocks next to their keys and messages in hex, is such a copy, and one logger attribute decides whether it exists.
