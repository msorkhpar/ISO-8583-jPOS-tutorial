The server's suite has ninety tests, runs in four seconds, and every participant has a unit test. In the first week of production a cardholder's daily limit fills up with purchases that were declined, and now and then a terminal receives another terminal's answer. Both participants had green tests. Each test checked what its author believed jPOS does, and the belief was wrong.

Every output comes from jPOS 2.1.7: JUnit 5 under Maven, or a Q2 started in the test's JVM and fed by unit s4's DirectTerminal. Unit c10 tests the client the same way, and its rules on waiting for a condition and on reading a load test hold here unchanged.

A Participant Test Gets Its Context From IncomingListener

Unit s4 put ctx.get(REQUEST) into Authorize, and every terminal waited for an answer that never came. That participant had a unit test, and it passed:

The test and the participant use the same wrong key, so they agree. In production the Context comes from IncomingListener, which stores the request under the string "REQUEST", and a key matches only an equal key, so no other spelling finds it. A test can get its Context from the same place. This helper runs a real IncomingListener into a queue that no TransactionManager reads, and takes the Context back:

The same participant, given each Context:

Now the test fails in the build instead of at the terminals. The listener also adds SOURCE and TIMESTAMP, so a participant that reads them gets what production gives it. The fix is still REQUEST.toString() in the participant.

A participant test like this registers in the NameRegistrar any service the participant looks up, configures it with a SimpleConfiguration holding its <property> values, calls prepare, and checks the vote and what the participant left in the Context. It needs no Q2 and runs in milliseconds.

Only the Real TransactionManager Decides Who Hears the Outcome

A unit test of the abort path has to call abort itself. Here is the test of unit s4's ReserveDailyLimit in a version whose abort gives the amount back, but whose success vote is PREPARED | NO_JOIN. totals is the DailyTotals the test registered, and terminal an ISOSource:

It passes. What does the real TransactionManager do with the same purchase, when Authorize declines it?

The test called abort because its author expected the TransactionManager to. The TransactionManager read NO_JOIN and didn't. In production this is unit s4's cardholder, refused for her groceries after two declined purchases.

The unit test should assert the whole vote, assertEquals(PREPARED, vote), because the flags are what the TransactionManager acts on. The abort path gets a chain test: the real descriptor, deployed by Q2 in the test's JVM and fed through DirectTerminal:

It fails on the NO_JOIN version and passes on unit s4's fixed one (total today: 0). Once Q2 is up, a chain test takes a few milliseconds, so every participant that changes something outside the Context can have one for its abort path.

Tests That Share a Q2 Share Its State


A test class starts Q2 once, in @BeforeAll, because a start takes a few hundred milliseconds. Two tests of the daily limit of 500.00, in one class:



Each passes when run alone. The class:



The second test bought on a card that had spent 300.00 already. With the order reversed, the other test fails instead, and JUnit promises no order: adding a third test can change which one is red.


A @BeforeEach that registers a fresh DailyTotals under daily-totals replaces the registered object and gives the same output, because ReserveDailyLimit looked its totals up in setConfiguration, once, when Q2 deployed it. The participant still holds the first object, and only the test reads the new one.


The participants and the objects they found by name live as long as the Q2. The Space and the NameRegistrar are static, one per JVM, and outlive it, so a later test class in the same JVM still sees their entries. Give each test its own card, terminal and STAN. With its own card, the second test passes in either order. Where state must be reset, clear the object the participant holds instead of replacing it.


Only a Socket Test With the Terminals' Framing Tests 50_server.xml


DirectTerminal configures its own IncomingListener, so no test so far has read the server descriptor: the port, the channel, the packager, the listener and its queue.


The acquirer's terminals frame each message with a two-byte binary length, as jPOS's NACChannel does. The server's descriptor was copied from unit s1 and still says ASCIIChannel, four ASCII digits. Three terminals send a purchase to that server. Which of them notices?



The server logged, for the third:



DirectTerminal never reaches the channel. Unit s1's TestTerminal hard-codes ASCIIChannel, the class the descriptor was copied with, so it shares the descriptor's mistake. Only the client built from the network's specification fails: the server read the binary length and the start of the MTI as four ASCII digits, gave up and closed the connection (unit s3). In production every terminal connects, sends and is disconnected, and the server answers nobody.


So the socket test starts Q2 on copies of the shipped descriptors, setting the port through ${iso.server.port} as unit c10 sets ${host.port}, and builds its client channel and packager from the network's specification, never from 50_server.xml. Then it waits for the port: in the run above, after the TransactionManager had registered, the first three connects were refused. Retry the connect until a deadline.


Only Two Transactions in Flight Show What Sessions Share


Unit s1's TerminalCheck kept the request in a field, and when two terminals sent at the same moment, one got the other's answer. Its tests sent one request at a time. Can a test make two transactions overlap on purpose, every time?


It can, when the participant waits for something the test controls. Here the terminal table is a service that the participant looks up in setConfiguration, as unit s4's participants find theirs, and prepare now catches Exception:




The test registers a directory that holds the first lookup until a second one arrives:



The test sends an echo from 29110041, calls awaitFirst, then sends an echo from 29110042:



While the first session waited at (2), the second wrote the field at (1), and the first built its answer from it at (3). With a local variable, both terminals get their own answers. The TransactionManager needs sessions of at least 2. With one, the second echo waits in the queue behind the held one, the hold runs out after five seconds, and the first terminal gets no answer at all.


No sleep decides the order, so every run prints the same lines and the test fails every time. For a participant with no service to hold, place a test participant after it that waits on a latch in prepare. That catches state kept from prepare to commit.


A load test also puts transactions in flight, but finds this bug only by chance. Run it outside the unit suite, against a copy of the deployment, with STANs from one sequence, so concurrent requests never share a key. Unit c10 shows how to read its results, and unit s8's profiler where the time went.

Summary


  • A participant test gets its Context from IncomingListener. A hand-built Context can share the participant's wrong key, and then both are green together.
  • Only the real TransactionManager decides who hears the outcome. Assert the whole vote, and test the abort path through a chain test.
  • Tests that share a Q2 share its state. Give each test its own card, terminal and STAN; registering a new object doesn't reach a participant that already holds the old one.
  • Only a socket test with the terminals' framing tests 50_server.xml. Build its client from the network's specification, and wait for the port.
  • Only two transactions in flight show what sessions share. Hold one inside a stand-in the test controls until the other has passed.

Challenges


  1. Your chain has eight participants, and three change something outside the Context. Which chain tests do you write, and which participant tests could you then delete?
  2. Thirty test classes each start their own Q2. Share one Q2 across the whole run instead: what does every test have to do differently, and what do you gain?
  3. A participant counts purchases per card in a ConcurrentHashMap field. Is that state shared between sessions in the sense of 11.5? How would you hold two transactions to find out?
  4. The network's specification adds a five-byte TPDU header before each message. What does your socket test's client need, and what would a server that ignores the header do?


Design Note: Why Test Through jPOS's Own Pieces?


Every test in this unit runs a piece of jPOS the way production runs it: IncomingListener builds the Context, the TransactionManager runs the chain, QServer reads the socket. A test could replace each piece with a few lines of its own and run faster. But those lines are written by the person who wrote the participant, from the same beliefs about jPOS, and they agree with the participant exactly where both are wrong.


The price is a Q2 in the test's JVM, with its start-up time and the shared state of 11.3. Stand-ins still belong at the services a participant calls, such as a fraud check, an HSM or a database: they aren't jPOS, and the test has to control them. A hand-written stand-in or a Mockito mock registered under the service's name replaces them, as 11.5 does to force an interleaving.
