  15. Design Note: Why the Pool Knows Only "Usable"

The host runs two data centres, and you have one link to each, with a MUXPool in front of them (unit c4). At 14:02 the link to data centre B drops while a purchase is on it. The pool sends the next purchases to A, and the dashboard stays green. The purchase that was on B came back null. Someone suggests sending it again, since the pool will now pick A.

Was the cardholder charged? Where does the reversal go, and what does A make of it? The answers come down to five rules, one per section heading.

Links You Can Take Down

A pool never touches a socket. It asks each member whether it is connected, and a QMUX with <ready> answers by looking for its adaptor's ready entry in the Space (unit c4). So a test can run real QMUXes and a real MUXPool in one JVM, with unit c12's test host behind each QMUX, and take a link down by removing its ready entry.

A Pool Chooses a Link Once per Request

A round-robin pool sends the opening's purchase to host-mux-b, whose host answers 1.5 seconds late. The client waits one second, gets null, and tries again through the pool:

The second try looked like a success, and the cardholder paid twice: the resend of unit c12. With one link it double-charges too, once the slow host gets to it. A pool makes it look safe, because the retry may go to a healthy link and be approved at once.

The pool picks a member when request is called and hands it the message. From then on the member's QMUX does the waiting. If that link drops or the host stays silent, the member returns null at the timeout, and the pool passes the null up without moving the request. It has no way to tell a request that never arrived from an approval that got lost, any more than a single QMUX can.

New purchases stop going to a dead link, so a pool means fewer unknown outcomes, but the ones already on that link stay unknown. A null from the pool is reversed, never resent, whatever the strategy (unit c12).

The response comes back on the link that carried the request, because each QMUX matches only its own traffic (the out queue is part of the key, unit c12). A request still in a member's send queue when its link drops waits there until the link comes back or the request expires (unit c4); the pool doesn't take it back.

A Link Is Usable When It Is Connected and Signed On

The pool acts on a single signal per member: usable or not. It reads that signal on every request, so a link joins or leaves the rotation from one request to the next.

Without check-enabled, usable means isConnected(). Many hosts refuse traffic on a connection until the acquirer has signed on (unit c11), so a connected link is not enough. With check-enabled, a QMUX member is usable only while the entry <mux-name>.enabled holds the very object stored under its ready key. Two links, both connected, under a primary-secondary pool with and without check-enabled:

In the "reconnected" line, host-mux had signed on, its link dropped, and the adaptor reconnected. Nobody told the pool, and it stopped using the link anyway. The adaptor writes a new Date as the ready entry on every connect. The enabled mark still holds the old one, and the pool compares the two with ==, so the old sign-on no longer counts.

An equal copy fails too: a Date with the same time is equals, but it is not the ready object. For a QMUX with one <ready> name, a sign-on manager that writes Boolean.TRUE, a fresh Date or a copy keeps its link out of the pool for good. One that writes the ready object it signed on with (as signOn does above) gets it in. (With several <ready> names the pool only checks that the mark exists; see the reference table.)

The pool compares the two entries in its own <space>. If the adaptors write their ready entries to another space, both lookups return null, null == null is true, and check-enabled silently lets every connected link through. Leave <space> out, or name the adaptors' space.

A link whose host process hangs stays connected at TCP level, and the pool keeps sending to it. Unit c11's read timeout, echoes more often than that timeout, and a sign-on manager that removes <mux>.enabled when an echo fails turn that failure into the signal. A host that stops answering then leaves the rotation within one echo interval plus the echo's own timeout.

isConnected() on the pool is true while any member is usable, so as an alarm it stays quiet while one of two links is out. An alarm should name the members the pool is skipping.

The Strategy Decides Where Traffic Goes When a Link Fails


Three links, all usable at first. Each line sends requests with STANs from 000001 and shows which link received which STAN. In the first line host-mux goes down after two requests and comes back after four. The "split on 41" line sends two requests each from terminals 29110001, 29110002 and 29110003; the next line sends four from 29110001 alone:



primary-secondary takes the first usable member in <muxes> order. Request 5 went back to host-mux the moment it was up again: failback has no hold-down period. A flapping primary drags all traffic with it; with check-enabled it returns only after signing on again. It is also the default, and any <strategy> text the pool doesn't recognise selects it, so a typo in round-robin silently gives you active/standby.


round-robin keeps one counter for the pool and increments it before using it, so the first request goes to the second member. In the third line, with -b down, host-mux and -c got three requests each. A simpler rule, "start at the counter and take the next usable member", would give -c both its own turn and -b's, two requests out of three. The 2.1.7 pool increments the counter once more for every member it skips, which spreads a dead member's share evenly. Under load the shares are only roughly equal, because many threads move the counter at once.


split-by-divisor with <split-field> sends a message to member number value % size, here terminal ID modulo 3. Terminal 29110001 always lands on -c, while that member is usable. With -c down, its requests went round-robin to the other two, one each. A field that is missing or not all digits, such as GW000001, goes round-robin as well. So this strategy can't pin a terminal's traffic to one link.


round-robin-with-override keeps chosen MTIs on a named link while that link is usable, and otherwise sends them round-robin (14.6).


Spot the Problem: Eight Months of Uptime


A switch has run a round-robin pool of three links for 250 days at about 100 requests a second. Today two purchases in three fail before they are sent, and the third always goes to the first link. The same pool, with its private counter set close to its limit by reflection:



The counter is an int. After 2^31 increments it wraps to a negative number, and counter % size in Java keeps the sign, so the index is negative unless the remainder happens to be 0. That stays so until the counter climbs back above zero, another 2^31 increments later. At 100 a second, 2^31 requests take about 249 days, and skipped members and idle polling (14.5) add increments of their own.


A planned restart before that point resets the counter. A router of your own avoids it with Math.floorMod, as in 14.6.


With Nothing Usable, the Pool Spends the Request's Own Time


Both links are down, and a request arrives with a 200 ms timeout. Then a link comes up 300 ms into a request that may wait 5 seconds:



When no member is usable, the pool sleeps one second and looks again, until the deadline has passed. It checks the deadline only after the sleep, so a 200 ms request returns after a whole second. A link that comes up during the sleep is noticed at the next look, and the time spent waiting comes out of the request's budget: the pool turns the timeout into a deadline at the start and hands the member only what is left.


This null means nothing was sent, so there is nothing to reverse, but the caller can't tell it from the null of 14.2. Ask the pool's isConnected() first, as unit c4 did with a single QMUX: it answers at once, you can report "host unavailable", and every null that request returns afterwards means an unknown outcome. A member can still drop between the check and the request. You then reverse a purchase that was never sent, which costs one message and is safe.


Keep request timeouts well above a second, or the polling eats most of them.


The other entry points end differently when nothing is usable. send(m) throws No available MUX after one second, and the asynchronous request throws No MUX available once its timeout has passed, rounded up to whole seconds, without calling the listener (2500 ms became 3000 ms in our run). request(m, 0) does not just send. With two usable links:



In 2.1.7 a zero timeout makes the pool call send(m) first, and then fall into the normal path with a deadline of "now". Within the same millisecond, that path hands the message to a member again. Both copies are queued without an expiry, so on a link that drops they wait until it is back. When you mean to send without waiting, call send.

A Follow-Up That Must Reach Its Original's Host Needs a Router of Your Own


A reversal refers to an earlier message. Whether it must travel on the original's link depends on what is behind the links:


  • several connections to one host instance: any link works, and the reversal queue of unit c12 can send through the pool;
  • several host instances that share their state at once, such as two front ends on one database: any link works too;
  • instances that don't share state, or share it late, such as two data centres that replicate asynchronously: the reversal must reach the data centre that saw the original.


Take the third case with the opening's purchase. Data centre B approved it, and the answer was lost. The link to B is down. The test host for each data centre approves purchases and reverses only what it has a record of, answering 25 (original not found) otherwise. The pool uses round-robin-with-override with <follower-override>0420 0421</follower-override>, and the test puts the original link's adaptor name, host-channel-b, into the field that <original-channel-field> names. A real application would first have to learn that name: the pool doesn't say which member it chose.



With -b down, the override fell back to round-robin and sent the reversal to A, which had never seen the purchase. In most networks any answer acknowledges a reversal (unit c12), so the queue deleted it. B still holds an approved purchase that nobody will reverse, and the cardholder's money stays with the merchant until someone finds it at reconciliation.


Here the follow-up must go back to the original's link, and when that link is down it must wait in the queue. The 2.1.7 pool has no hook for a choice of your own (later releases add one). The MUX interface is small, though, so a class of your own can implement it, wrap the members, and take the pool's place under its name:



The same story through StickyRouter (an earlier purchase went to A, so this one goes to B):



(1) Its link, or wait. While B is down, request returns null and sends nothing. The reversal queue of unit c12 sees no answer and keeps the reversal, and the next attempt after B is back reaches it. Test a router like this with the original's link down: one that fails over passes every test in which all links stay up.


(2) The index survives the wrap. Math.floorMod keeps it between 0 and the member count when the counter goes negative, the failure of 14.4.1.


(3) The route is remembered under the original's identity, the way a reversal states it: field 41, and the STAN and transmission time from field 90 (positions 5-10 and 11-20, unit c12). The reversal's own STAN and time are new and match nothing. The routes live in a Space with a TTL longer than the network's reversal window, so they don't grow for ever; a persistent space keeps them across a restart. A reversal whose route is unknown (it expired, or the original went out before a restart with a transient space) goes round-robin here. If your hosts can't take that, return null for it instead, and decide what alerts on reversals that never leave the queue.



Usability here is isConnected(). To keep unsigned links out as well, test the enabled mark the way check-enabled does (14.3), in the adaptors' space, before choosing a member.


Your code sets field 11 before the router or the pool picks a link, so the STAN can't come from the chosen link's sequence. Use one sequence for the pool, such as stan.host-pool (unit c4), and every STAN is unique on every member. A network that wants the STANs on each connection to run without gaps needs the STAN set after the choice, inside a router like this one.

Summary


  • A pool chooses a link once per request. It never moves a request a member has taken, so a null is still an unknown outcome to reverse. A retry through the pool is a second purchase, often on another link that approves it at once.
  • Usable means connected, and with check-enabled signed on over this connection. The enabled mark must be the very ready object, so a reconnect takes the link out until it signs on again. A hung host leaves the rotation only if read timeouts, echoes and the sign-on manager say so.
  • The strategy decides where traffic goes on failure. primary-secondary fails back at once; round-robin spreads a dead member's share evenly, and its 2.1.7 counter breaks most requests after 2^31 increments; split-by-divisor and the override fall back to round-robin when their member is down.
  • With nothing usable, the pool polls once a second inside the request's own budget and returns null with nothing sent. Check isConnected() first, and never call request(m, 0).
  • A follow-up that must reach its original's host needs a router of your own, which remembers each original's link and makes the follow-up wait while that link is down. The STAN is set before the choice, so the pool uses one sequence.

Entry points when nothing is usable:


CallResult

The counter. round-robin, the fallback of split-by-divisor and of the override share one int counter. It is incremented once per round-robin choice (for the other two, only when they fall back), once per skipped member, and once per member on every one-second poll while nothing is usable. Past 2^31 it is negative, and every choice whose remainder is not 0 fails: round-robin throws ArrayIndexOutOfBoundsException, while the other two catch the exception, log it and return no member, so request returns null with nothing sent.


JMX. The pool's MBean shows getMuxNames() and getStrategy() (0 primary-secondary, 1 round-robin, 2 round-robin-with-override, 3 split-by-divisor). The members' QMUX counters (unit c11) show where traffic actually went.


Challenges


  1. Your primary link drops for a few seconds about once an hour. Compare primary-secondary with and without check-enabled, and with round-robin: how many requests move during each blip, and how many unknown outcomes does each choice produce?
  2. A round-robin pool of four links runs at 400 requests a second, and one link is down for 20 minutes every night with nothing usable for one minute of that. How long until the counter wraps? Work it out, then decide when to schedule restarts.
  3. Two data centres replicate within 3 seconds. Is that "sharing state" for reversals? Which reversals could still arrive before their original is known, and what would you measure to decide between the pool and a router of your own?
  4. StickyRouter keeps routes in a Space. Design the same memory as a column in the transaction table instead. What becomes simpler, and what happens to a reversal whose original's row has not been written yet?


Design Note: Why the Pool Knows Only "Usable"


MUXPool knows nothing about hosts or data centres, only one bit per member: usable or not (14.3). Writing the bit is someone else's job: the adaptor writes the ready entry, and the sign-on manager writes and removes the enabled mark.


That split keeps the pool under 300 lines in 2.1.7. The adaptor and the sign-on manager need not know the pool exists; they only follow its convention, the <mux-name>.enabled key and the identity rule. A failure the pool should react to needs a component that turns it into the bit, not a change to the pool.


The price is that the pool cannot link a message to an earlier one. It can route an MTI to a named link, but it doesn't know which link carried a reversal's original, and it returns the same null for "not sent" and "not answered". Those decisions need the application's knowledge, and in 2.1.7 the only place to put that knowledge is a MUX of your own in front of, or instead of, the pool.
