The acquirer's interface spec says: "Each message is preceded by a 2-byte binary length." We set up the client with the course's usual ASCIIChannel and a three-second read timeout, and send an echo. No answer comes, and nobody logs a format error:

Every field was right. The client and the host disagreed about where a message ends, so the host waited for 12336 bytes that never came. The object that owns that decision is the channel. The unit comes down to six rules, one per section heading.

The Channel Decides Where a Message Ends

An ISOChannel owns one TCP connection. send(ISOMsg) asks the packager for the message's bytes, writes a frame around them and returns void. receive() reads one frame, hands its bytes to the packager and returns the ISOMsg. The packager knows how each field is encoded. The channel knows what goes around the whole message: a length, sometimes a header.

The same 55-byte echo, written by three channels from org.jpos.iso.channel (the frame bytes before |, in hex):

ASCIIChannel writes the length as four ASCII digits, 0055. NACChannel and PostChannel write it as a 2-byte unsigned binary number, high byte first: 0x0037 is 55. The message itself is identical.

In the opening run the host has a NACChannel. It reads the ASCII digits 00, bytes 0x30 0x30, as a binary length: 12336. Both sides wait until the client times out and closes, and the host's read ends with EOFException. No message was ever complete, so nothing logged a format error.

The host's spec decides two things independently: the packager from its field table, the channel from its paragraph about message boundaries. A wrong packager shows up as format errors or unpack failures; a wrong channel usually shows up as silence. The Reference lists the common channel classes and their frames.

Inside this course both ends use ASCIIChannel with GenericPackager and jar:packager/iso87ascii.xml, because the frame is readable in a hex dump. Unit c13 covers packagers.

One Read Is Not One Message

TCP delivers a stream of bytes. The sender's stack may merge two small writes into one segment or cut a large one into several, and a busy receiver may find several messages waiting in its buffer. The frame lets the receiver find where each message ends.

A raw socket writes one frame in three pieces, 300 ms apart, then two frames in a single write. An ASCIIChannel on the other end calls receive() three times:

Why did the first receive() wait for the third piece?

The channel read the four length digits, which took two writes, then exactly 55 more bytes, across as many network reads as that needed. The 118-byte write held two frames, and the channel took one per call and left the rest in the stream for the next.

On loopback small writes usually arrive whole, so code that treats one read as one message passes its tests. Over a WAN, or under load, it unpacks half messages as garbage. When two answers arrive in one read, it loses the second, perhaps an approval.

A frame can also be empty. A sender with nothing to say may write a zero-length frame to keep the connection busy. The adaptor element <keep-alive> sends one; the channel property keep-alive is different and turns on TCP keep-alive probes. ASCIIChannel writes 0000 back and reads on. NACChannel and PostChannel accept it only with the property expect-keep-alive. A NACChannel receives a keep-alive and then an echo:

Without the property, the first keep-alive is an error, and a ChannelAdaptor drops the connection on it (unless it has <ignore-iso-exceptions>).

    Read a host's messages off a byte stream

    • The channel decides where a message ends and the packager what is inside it; a 2-byte binary length is an unsigned number, high byte first, and a wrong frame shows up as silence.
    • A receiver reads exactly the announced length, across as many reads as it takes and one frame per call, and a stream that ends early is an error.

receive() Returns the Next Frame, Not Your Answer


Four scripted hosts run against the same client, which sends one echo and then calls receive() until it has the answer or an exception:




  • The first frame isn't necessarily yours. Hosts send messages of their own (echoes, sign-on requests, key exchanges), and receive() returns whatever arrives first.
  • The read timeout measures silence, not your wait. The second answer took 1400 ms against a 1000 ms timeout and still arrived, because the host's echo at 700 ms restarted the clock. A host that keeps talking can keep a reader waiting for its answer forever.
  • Silence ends the connection. receive() never returns null. When the timeout fires it throws SocketTimeoutException, and in 2.1.7 the channel closes its socket before it throws. The host's answer, sent 357 ms later, went into a connection that no longer existed.
  • A closed connection is a different exception. When the host hangs up, receive() throws EOFException, and waiting longer is pointless. (A frame the packager can't unpack throws ISOException, and that one leaves the socket open, out of step with the stream.) Only the timeout means "the host may still be working on it".


Spot the Problem: A Pool of Channels


A team coming from JDBC keeps a few connected channels and lends one to each request:



Two channels with a one-second read timeout and four purchases, one after the other. The host sends its own echo on the first connection before it answers, and it is slow on the second. What does each purchase get?



Line (2) takes whatever comes next, so purchase 801 is "answered" by the host's echo. Purchase 802 waits through the read timeout. Its channel closes, and the host's approval for it is lost. Line (3) returns the closed channel to the pool anyway. Purchase 803 gets the first connection again and reads the approval meant for 801. Purchase 804 gets the dead channel and fails at once.


Checking the response and reconnecting don't fix it: a message that arrives while nobody holds the channel still goes to the wrong borrower or to no one. Networks also tend to limit an acquirer to one connection or a few, each signed on (unit c11), so a pool of ten may be refused. On a link, reading is a job for one thread that never stops, and matching answers to requests is a separate job.


jPOS 2.1.7 has a class named org.jpos.iso.channel.ChannelPool. Despite the name, it is a failover list: connect() uses the first channel that connects.

A Link Has One Reader That Never Stops: the ChannelAdaptor


org.jpos.q2.iso.ChannelAdaptor is a QBean that owns one channel and runs two threads:


  • the Receiver calls receive() in a loop and puts every message it reads on the <out> queue, whatever the message is;
  • the Sender takes messages from the <in> queue and calls send.


Application code never touches the channel. It writes requests to one Space queue and reads everything the host sent from another. QMUX (unit c4) does both and matches each answer to its request. Q2 deploys the adaptor from deploy/10_host_channel.xml:



The <channel> element names the channel and packager classes. Q2 gives its <property> children to both: the channel reads host, port, timeout and the like, and the packager reads packager-config. <in> is the queue the adaptor sends from, and <out> the queue it delivers to. From the application's side that reads backwards, so name the queues after the peer and the direction (host-send, host-receive). A second link (acquirer-b-send) then never collides with the first.


timeout is the read timeout, six minutes here. The Receiver always reads, so it fires only after six minutes of silence on the whole link. An echo every few minutes prevents that (unit c11 sets it up, and unit c12 relates all the timeouts).


The Adaptor Reconnects and Announces the Link


We deploy the adaptor above in a real Q2 against a host that answers echoes, with reconnect-delay at 3000 to keep the run short, and the host drops the connection:



Once the Sender has a connection it puts a java.util.Date in the Space under host-channel.ready, the adaptor's name plus .ready. When the Receiver hits EOF, a read timeout or an unpack error, it removes that entry, disconnects, and leaves a host-channel.reconnect entry that lives for reconnect-delay. The Sender won't connect while that entry exists, so a host that keeps dropping you is retried every few seconds instead of in a tight loop. Across runs the reconnect came after 3 to 4 seconds: the delay, plus the adaptor's own one-second pauses.



QMUX watches the ready entry through its <ready> element, so mux.isConnected() reports the real link state (unit c4). Each connection puts a new Date there, so code that has to act once per connection, such as a sign-on, compares the object it saw last with the one there now (unit c11). A cached flag can't tell that the link went down, or that it came back as a new connection.


Two Settings That Do Nothing


We deploy this descriptor, often copied between projects, and ask the running channel for its read timeout and the Space for the ready key the descriptor names:




The timeout attribute is ignored. The channel reads only the timeout property and falls back to its default of five minutes. With an echo every five minutes, the link can then be torn down and rebuilt whenever an echo comes a little late. The <ready> element is ignored too: the adaptor's ready key is always its name plus .ready, and <ready> belongs to QMUX. A QMUX pointed at acquirer.ready would report the link down forever.


In jPOS 3. The adaptor gains elements such as soft-stop and a reworked reconnect, neither of which exists in 2.1.7.


A TLS Channel Checks the Host Only When You Tell It To


TLS is not a channel class. A channel that extends BaseChannel opens its socket through a socket factory, and with an SSL factory the same frames travel inside a TLS session. In a ChannelAdaptor you name the factory in the channel property socketFactory, and the factory reads the channel's other properties:



What happens without the serverauth line? We start a TLS host whose certificate (CN=host.example.com) the client has never been told to trust, and connect four ways:



With serverauth false, which is the default, the 2.1.7 factory accepts any certificate. The link is encrypted, but anyone who can get between you and the host can play the host and collect every PAN you send. With serverauth=true the factory trusts what is in the keystore, which is also the trust store, so it needs the host's CA or certificate next to your own key pair.


The factory then compares servername (or, if that is missing, the peer's host name) with the certificate's CN, exactly: it does not look at Subject Alternative Names, and a wildcard CN such as *.example.com never matches. So host (or servername) must be the certificate's name, not an IP address the certificate doesn't carry. With a socket factory, the channel's connect-timeout is not used.


Don't write the passwords in the file. Q2 replaces ${KEYSTORE_PASSWORD} with the environment variable of that name, or a system property, or a value from the active environment file under cfg/. Leave them out, and the factory falls back to the system properties jpos.ssl.storepass and jpos.ssl.keypass, whose default is the literal password. Leave out keystore, and it reads ~/.keystore. Set all three.


For a test or a diagnostic tool, the same factory can be set up in code:

Summary


  • The channel decides where a message ends, the packager what is inside. Both come from the host's spec, and a wrong channel usually shows up as silence, not as an error.
  • One read is not one message. A channel reads exactly the announced length, across as many reads as needed and one frame per call. A zero-length frame is a keep-alive, and NACChannel or PostChannel needs expect-keep-alive to accept it.
  • receive() returns the next frame, not your answer. It never returns null. The read timeout measures silence, and when it fires the 2.1.7 channel closes the connection, losing any answer still on its way.
  • A link has one reader that never stops. Never pool raw channels. Deploy one ChannelAdaptor per link and let QMUX match the answers.
  • The adaptor reconnects by itself, after reconnect-delay, and puts a new Date under <name>.ready for each connection. The timeout attribute and the adaptor's <ready> element do nothing.
  • TLS checks the host only with serverauth=true, against the CN, with the keystore as trust store and the passwords from the environment.

Challenges


  1. A host's spec says "2-byte length", without saying binary or ASCII, or whether the length counts itself. What one test message, and what view of the bytes on the wire, would settle all three questions on the first connection?
  2. Your link carries an echo every five minutes, but the host answers echoes only while it is signed on. Choose a read timeout and an echo interval, and say what happens to a link whose sign-on fails at 3 a.m.
  3. A host allows two connections. Would you deploy two adaptors with one QMUX each behind a MUXPool (unit c4), or one adaptor? What does each choice do to message order, and to the reversals of unit c12?
  4. You have to accept a host whose certificate's CN is not its host name, with only a SAN that matches. What are your options in 2.1.7, and what does each one cost?


Design Note: Why the Channel Knows Nothing About Requests


A JDBC connection is request-and-response: you send a query and the next thing on the wire is its result. ISO 8583 links are not: either side may start a conversation at any time, answers can come back in a different order from the requests, and the host sends messages of its own. A channel that paired each send with the next receive would be wrong whenever any of that happens.


So jPOS splits the work. The channel only moves frames, in both directions at once, with no idea what they mean. The adaptor keeps one connection open and drains it into a queue. The MUX, a layer above, matches what it reads to what was sent. A different frame is then a different channel class, and a second link a second adaptor; neither touches the matching.


The cost is indirection. A round trip passes through two queues and three threads (the caller, the Sender, the Receiver), and a simple "send and wait" test needs a QMUX or a scripted host. Use the raw channel to see what crosses the wire, not to run a link.
