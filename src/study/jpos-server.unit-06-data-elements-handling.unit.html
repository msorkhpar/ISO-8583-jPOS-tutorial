The server of unit s1 gets its first real participant: it approves a purchase within a limit for its currency and declines it with 61 otherwise. It passes every test its developer typed in. In its first week of production, a balance inquiry gets no answer, a purchase of 7,000,000 yen is approved against a 75,000-yen limit, and a purchase whose field 4 starts with a minus sign is approved. On New Year's night every request sent in the last seconds of the year is refused as stale. And when the core system starts issuing longer approval codes, approvals that the server's log shows as sent never reach the terminals.

Each comes from reading a data element as what it looks like. The outputs come from unit s1's server in Q2 and its TestTerminal, which gives up after 10 seconds, or from participants called with a Context we built, all on jPOS 2.1.7.

A Missing Field Reads as null, and a Participant That Throws Answers Nobody

The first version of the limit check reads field 4 as a number of cents:

It puts its response in the Context before voting, as unit s1 requires. A terminal sends a purchase, then a balance inquiry, which moves no money and has no field 4. What does the terminal get for the second one?

getString returns null for a field the message doesn't have, and line (1), Long.parseLong(null), throws a NumberFormatException. The catch is for ISOException, so the exception leaves prepare. The TransactionManager catches anything a participant throws, logs it as a warning and counts it as an ABORTED vote:

The abort path called SendResponse, but the participant never put a response in the Context, so there was nothing to send: unit s1's silent refusal, though no line of code asked for it.

A purchase without an answer has an unknown outcome, so the acquirer reverses it (unit c12): a request you could have refused in a millisecond becomes a timeout, a reversal and a second message for your server.

The packager unpacks whatever fields the bitmap announces, and IncomingListener passes the message on without looking at it. So a participant checks every field before it reads it, with hasField or hasFields(int[]), and answers a request it can't read, usually with 30, format error. Around a call into code it doesn't control, such as a database or a library, it also catches RuntimeException and answers.

A Numeric Field Is Text That Nobody Checked

Field 4 is defined as twelve digits (n 12). This is what the server receives when a client puts other text in it, with iso87ascii.xml at both ends, and what four ways of reading it make of it:

The last column is ISOUtil.isNumeric(s, 10). Neither packager complained about any of these: the ASCII numeric field packager checks the length and pads with zeros, but doesn't look at the characters.

Give NaiveLimit (limit 500.00) a clean amount, the signed one and one ending in a letter:

The third is 6.1 again: in a server, no answer. The second is approved, because -25.00 is within any limit, and whatever books it next adds -25.00 to the cardholder's spending: a purchase that pays the cardholder. Field 4 has no sign; a refund is a different processing code in field 3. Integer.parseInt fails above 2,147,483,647 cents, so a purchase over 21,474,836.47 would get no answer either.

So check the form before you convert: exactly twelve characters, all digits. Then Long.parseLong and BigDecimal agree, and what remains is what the digits mean.

An Amount Counts the Minor Units of the Currency in Field 49

000007000000 is 70,000.00 US dollars, 7,000,000 yen (the yen has no minor unit) and 7,000.000 Bahraini dinars (three decimals). Field 4 counts the smallest unit of the currency that field 49 names.

With limits of 500.00 dollars, 75,000 yen and 150.000 dinars, each line compares the amount with its currency's limit once read as cents, like line (2) of NaiveLimit, and once with the currency's own decimals:

Reading cents everywhere approves the 7,000,000-yen purchase, over ninety times the limit, and declines a 120-dinar purchase within it. Tests written in dollars pass either way. ISOCurrency.parseFromISO87String(amount, currency) reads field 4 with the decimals of the ISO 4217 code in field 49. For a code it doesn't know it throws an IllegalArgumentException (Currency with key '123' was not found), which has to be caught too.

A Date Without a Year Takes the Year Closest to the Clock, Read in GMT


Field 7, transmission date and time, is MMddhhmmss in GMT: ten digits and no year. The server supplies the year, and the obvious choice is the current one.


Our server refuses requests sent more than five minutes ago, which the terminal has long given up on. At 00:00:03 GMT on 1 January, a request arrives that was sent at 23:59:58 on 31 December. How old is it?



With the current year, a request five seconds old was sent a year from now, and the check refuses it with every other request that crossed midnight. ISODate.parseISODate(field, now, zone) tries last year, this year and next year, and takes the one closest to now, which is right for any request sent within six months of the clock.


The third line passes no zone and was right only because the JVM ran in UTC. In a JVM whose default zone is New York:



Without a zone, parseISODate reads the digits as New York time, and every request is off by five hours in winter and four in summer. The last line is jPOS's CheckFields (unit s5), which puts field 7 into the Context as TRANSMISSION_TIMESTAMP in the JVM's default zone in 2.1.7. Developers' machines usually run in local time and containers in UTC, so the same code can pass on one and refuse everything on the other. Pass the clock (a java.time.Clock) and the zone yourself:



Check the field first, as in 6.2: exactly ten digits. parseISODate reads a 12- or 14-character value as one that carries a year, and runs Integer.parseInt on its pieces, so a letter throws. The calendar is lenient: a month of 13 rolls over into January and 0230 into early March, before the closest-year rule applies. If you use CheckFields, start the JVM with -Duser.timezone=UTC.


Networks differ. Fields 12 and 13 are the terminal's local time and date, in a zone the message doesn't name; fields 15 (settlement date) and 17 (capture date) are MMdd in the acquirer's or the network's calendar. The closest-year rule works for all of them, but only field 7 can be compared with your clock.

set Checks Nothing; the Packager Checks After the Vote


After an upgrade, the core system's approval codes grow from six characters to eight. A second participant, NaiveApprovalCode, adds the code to every approval:



Field 38 is six characters in iso87ascii.xml. What does a terminal get for a purchase within the limit, and what does the server's log show?



set stored the eight characters: an ISOMsg maps field numbers to values and knows nothing about lengths. The packager checks them when the message is packed, which on a server happens inside SendResponse, in commit, when the channel sends. The channel's entry:



and the TransactionManager's:



The transaction committed cleanly, and the channel logged a <send> with the whole 0210. Only the exception under it says that not one byte went out. SendResponse noted the exception in the Context, which is printed only with the dump unit s1 turned off, so a search for the STAN finds a <send> with 39=00.


The acquirer reverses a purchase the server approved. Unlike 6.1, no catch in a participant can help: by the time the packager objects, every participant has voted, commit can't change the outcome, and nothing runs after SendResponse to answer instead. The same goes for any value that doesn't come from the request, such as a reason text from a database, a balance or a code from another network. A value copied from the request into the same field fits, because the same layout unpacked it.


So check in prepare, while the participant can still choose the answer, by packing a copy with the channel's own packager. (A channel with outgoing filters, or one that picks its packager per message, can still differ.) IncomingListener put the channel in the Context under SOURCE:



With the same eight-character code, the terminal gets:



and the TransactionManager's event names the participant that refused:



With 96 the terminal shows a decline at once, nothing is reversed, and the event points at the cause. Line (3) matters as much as line (2): 96 with the eight characters still in field 38 can't be packed either, and the terminal is back to waiting. The check costs one more pack per response. Comparing each outside value with its field's length instead needs a new comparison for every new value; packing a copy covers them all, in whatever layout the link uses.


Don't truncate a value to make it fit: a cut approval code is a code the core system never issued.

Summary


  • A missing field reads as null, and an exception from prepare becomes an ABORTED vote with no response, so a purchase times out and is reversed. Check every field before you read it, and answer what you can't read with 30.
  • A numeric field is text that nobody checked. The packager checks lengths, not digits, and Long.parseLong and BigDecimal accept some of what arrives. Check for twelve digits first.
  • An amount counts the minor units of the currency in field 49. Yen have none and dinars three; ISOCurrency knows each, and dividing by 100 is wrong by a factor of 100 or 10.
  • A date without a year takes the closest year, read in GMT. The current year breaks every request that crosses New Year; the JVM's default zone breaks field 7 wherever it isn't UTC.
  • set checks nothing, and the packager checks in SendResponse, after the vote. A response that can't be packed is logged as a <send> and never sent. Pack a copy in prepare, and answer 96 without the field that didn't fit.

Response codes used here (ISO 8583:1987): 00 approved, 30 format error, 57 transaction not permitted, 61 exceeds amount limit, 96 system malfunction. Your network's specification has the full list and may use others.


Challenges


  1. A participant and the three after it all need the amount, the currency and the transmission time. Where do you parse them, where do you keep the parsed values, and what does a later participant do when they are missing?
  2. Your network sends field 4 on balance inquiries, as zeros. Should AmountLimit treat zero as an amount, and what would you need to know to decide?
  3. Instead of packing the response again in prepare, you could subclass the channel and catch the packing error in send. What could that channel do with the error, and what couldn't it?
  4. The core system's approval codes are eight characters and the network allows six. List the options, who has to agree to each, and what each costs when a cardholder disputes a purchase.


Design Note: Why Does jPOS Hand You Strings?


An ISOMsg unpacked with iso87ascii.xml gives you field 4 as a String, not as an amount. The packager knows each field's position, length and encoding, enough to turn bytes into fields and back. What a field means (that 4 goes with 49, that 7 is in GMT, that 38 comes from the issuer) is in the network's specification, and a packager that knew meanings would need a class per network.


So every participant that reads a field has to know what it means: one reads cents, the next reads yen, and both pass their tests. The usual remedy is to parse each field once, early in the chain, and put typed values in the Context for the participants after it; unit s5's CheckFields does this for the card, the processing code and the timestamps. jPOS's Common Message Format goes further: its packager (cmf.xml, unit s16) unpacks field 4 into an ISOAmount that carries its currency.
