  15. Design Note: Why a Thread per Connection?

Monday, 09:10. Terminals restarted over the weekend can't reach the server: "connection refused". Terminals that never disconnected still send purchases and get answers. The server's CPU is idle and the TransactionManager's queue is empty. On Friday a new firewall went in between the stores and the data centre. Where did the server's capacity go?

Everything the server knows about a terminal comes through one connection. The QServer of unit s1 decides how long a connection lives, who reads from it, who answers on it and who may open one, in six rules, one per section heading.

Every Connection Holds a Thread Until It Closes

The server's descriptor, deploy/50_server.xml:

For each accepted connection QServer clones the <channel> and runs a session on a thread from its pool. The session loops on receive() and hands each message to the listeners. It ends only when something throws: the client closes the connection, a frame can't be read, nothing arrives for timeout milliseconds, or a listener throws. maxSessions (default 100) sizes that pool, so it is also the most connections the server holds at once.

We deployed a server with maxSessions 3 and timeout 0, which disables the read timeout. Three terminals connect, send an echo and go silent. A fourth tries to connect every two seconds:

Why "refused", and not a connection that waits for a free thread? When the pool has no thread left, the 2.1.7 ISOServer closes its listening socket, so the operating system refuses every new connection at once. The server checks the pool four times a second and opens the port again when a session ends. While it waits, it logs a warning once a minute:

The connections that hold the threads keep working, which is why the old terminals in the opening still transact.

The three silent terminals stand in for terminals behind that firewall. A firewall that drops an idle flow tells neither side, so the server can't tell a terminal that went away from one with nothing to say. The terminal reconnects on a new connection (unit c12 tells it from the client's side), and the old session stays. Each reconnect leaves a dead session holding a thread, until one Monday morning the last thread is taken. From then on, only the terminals that never needed to reconnect can transact.

The read timeout ends a dead session. The same run with timeout set to 3000:

Each silent session logged <io-timeout/> and <session-end/> about 3 seconds after its last message, and the port opened again. A real server uses minutes. Without the property the channel's default is 300000 ms (five minutes), so the pile-up needs timeout set to 0 or to something very long, and both turn up in descriptors copied from project to project. Agree the value with the clients: longer than their echo interval, so that a quiet but healthy terminal is never cut off (units c11 and c12), and shorter than the firewall's idle limit.

Size maxSessions from the number of terminals or hosts that connect, plus room for reconnects: a client that reconnects before the server notices its old connection is gone holds two sessions for a while. maxSessions doesn't limit throughput, because the work happens in the TransactionManager's sessions (unit s1), not in these threads.

In jPOS 3. QServer runs each session on a virtual thread, and its log reports a number of permits instead of a thread pool. An idle connection costs much less there, but a dead one still counts until something ends it.

The First Listener That Returns true Owns the Message

A session hands every message it reads to the <request-listener>s, in the order of the descriptor. Each one is an ISORequestListener with a single method, boolean process(ISOSource source, ISOMsg m). source is the connection the message arrived on, and source.send(response) answers on it. Returning true means "mine" and stops the chain; false passes the message to the next listener. A listener that throws ends the whole session, so catch what can go wrong inside it.

IncomingListener (unit s1) always returns true, so it comes last. A listener before it can answer cheap messages itself, as this one does for echoes:

QServer creates it with its no-argument constructor and, because it extends org.jpos.util.Log, gives it the logger and realm of its element:

An echo and a purchase from terminal 29110001, against this chain and against a server whose only listener is the EchoListener:

In the second run the EchoListener returned false for the purchase, nobody came after it, and the session dropped the message. The log holds its <receive> and nothing else. Without a listener at the end that takes everything, messages vanish this way.

Spot the Problem: The Audit Listener

Compliance wants a record of every request the server receives. Someone writes a listener and puts it first, so that nothing escapes the record:

The chain is now audit, echo, incoming. What does the terminal get?

Line (2) reads as "recorded successfully", but to the session it means "this message is mine". Nothing after the audit listener runs. The log shows each <receive> and each audit entry from line (1), and no error. The terminal times out on every echo and purchase, and the client reverses each purchase it can't confirm (unit c12).

A listener that answers a message and returns false passes it on, so the request is answered twice: by the listener and by the TransactionManager behind IncomingListener.

Return true exactly when this listener has taken charge of the message, and false for everything else. A listener that only watches, like the audit one, returns false.

A Listener Holds Up Its Own Connection


Only the session thread that called process reads that connection, so nothing more is read from it until process returns.


This listener checks each purchase against a table of blocked cards and answers it itself. Under load the query takes two seconds:



Terminal A sends two purchases back to back on its connection. At the same moment terminal B sends one on its own connection:



B's purchase took two seconds, its own lookup. A's second purchase took four: it sat unread in the connection while the session waited for A's first lookup. A terminal that sends faster than the listener answers builds a queue in its socket, where each request waits for all the ones before it. Once the wait passes the terminal's timeout, its purchases end in reversals (unit c12). The other terminals are fine, so it looks like one faulty terminal, usually the busiest.


The fix is unit s1's: the listener only hands the message off. IncomingListener puts it in a queue and returns at once, and the TransactionManager's sessions do the slow work. The same lookup as a participant, with four TransactionManager sessions:



Each purchase now takes its own two seconds. A's answers came back in a different order from its requests. A client's QMUX doesn't mind, because it matches each answer by its key (unit c12).


In the first run, A's and B's lookups ran at the same time in one CardCheckListener object. QServer creates each <request-listener> once, and every session calls that one instance, concurrently. As with participants (unit s1), a listener's fields hold configuration, and nothing about the message in hand.

A Frame the Server Can't Unpack Ends the Connection


After a firmware update, a terminal sends the amount (field 4) with 10 digits instead of 12. The frame's length is right, since the terminal counts what it sends, but the packager reads every field after field 4 from the wrong place. The terminal sends that purchase and then an echo on the same connection:



The server answered neither. The session logged <session-error> with the unpack exception (Problem unpacking field 41) and closed the connection, so the valid echo right behind the bad frame was never read. On the client side (unit c3) a channel that hits a bad frame throws and keeps its socket. A server session, by default, ends on any ISOException from receive().


The server-level property ignore-iso-exceptions changes that. It goes directly under <qserver>, not inside <channel>:



With it, the same two frames give:



The session logged the exception and read on. This is safe on a length-prefixed channel such as ASCIIChannel: the channel reads the whole frame before it unpacks anything, so the next frame still starts in the right place. The bad purchase still gets no answer and the terminal still has to reverse it, but the requests behind it survive. Without the property, every request in flight on that connection is lost with the connection, and the terminal reconnects only to send the next bad frame. On a channel with no length, such as PADChannel, nothing marks where the next message starts, so closing is the only way to get back in step.


The same log entry also holds the card number. Before it throws, the channel logs a hex dump of the frame it could not unpack:



That is the card number 4111111111111111 in clear, in a log whose ProtectedLogListener masks fields 2 and 35. It masks the fields of a message, and a frame that never became a message is only bytes to it. In 2.1.7 the channel writes this dump for every unpack failure, with or without ignore-iso-exceptions, and a broken terminal can write hundreds of card numbers into the log before anyone looks. Treat the server's log as card data: who can read it, where it is shipped and how long it is kept (unit s8 covers what a server logs).


The Server Picks the Connection for a Message It Starts


Most traffic is a client's request and the server's answer on the same connection, through the source the listener was given. Some messages start at the server: a key change, a sign-off, an echo of its own (unit s2 builds them). Which connection does such a message go out on?


QServer has a built-in way: an <in> element names a Space queue, and QServer sends whatever appears there.



Two terminals connect, 29110001 first, and each sends an echo. Then the server's code puts a key change addressed to 29110001 (field 41) in server-send:



QServer doesn't read field 41. Its <send-request> element picks the connection: the default, LAST, is the connection accepted most recently, and the others are ALL (every connection) and RR (each in turn). None of them looks at the message. That is fine with a single host connected. With terminals, the wrong device gets another terminal's key change. The terminal it was meant for keeps its old key, and the one that got it either rejects it or installs a key that isn't its own, and then its PIN blocks fail to verify.


The server already knows which connection belongs to which terminal: each request arrives with its field 41 and its source. A listener placed first can remember, for each terminal ID, the source of its latest message, and return false so the message goes on to the rest of the chain. To send, look the terminal up, check that its connection is still open (source.isConnected()), and call source.send. The same run, with the server's code calling such a listener's send instead of writing to <in>:



A terminal that reconnects arrives on a new source, so keep the latest one. A terminal with no open connection can't be reached. The server keeps the message and retries when the terminal is back, or gives up and says so, but never sends it elsewhere.

A TLS Server Checks Client Certificates Only With serverauth


TLS sits in the socket, not in the channel: QServer gets its listening socket from a <server-socket-factory>, and the channel frames and packs as before. Terminals prove who they are with a client certificate, and clientauth requires one:



What is serverauth for on a server? We gave the server a keystore with its own key and the certificate of one known terminal, and let three terminals connect: the known one, a stranger with a self-signed certificate the server has never seen, and one with no certificate.



The terminal without a certificate was refused both times; the stranger got in whenever serverauth was off. clientauth makes a certificate mandatory, and serverauth decides whether it is verified. The 2.1.7 factory builds a trust manager from its keystore only when serverauth is true. Otherwise it installs one that accepts any certificate, the same behaviour unit c3 shows on the client side.


With serverauth on, the stranger above didn't even send its certificate: the server announced which issuers it trusts, and the stranger's JDK found no match. A client written to present its certificate anyway gets the server's own verdict:



Without serverauth, anyone who can make a key pair can pass for a terminal. For mutual TLS set both, and put in the keystore the certificates, or better the CA, of the terminals you accept.


The passwords come from the environment: Q2 replaces ${KEYSTORE_PASSWORD} when it deploys the descriptor. Without the storepassword and keypassword properties, the factory falls back to the system properties jpos.ssl.storepass and jpos.ssl.keypass, whose default is the literal password.


A socket factory ignores bind-address. We added bind-address 127.0.0.1 to the TLS server above, and its listening socket was 0.0.0.0:44307, every interface. The same property on a plain QServer gave 127.0.0.1:34063. In 2.1.7 ISOServer applies bind-address and backlog only when it creates the socket itself. allow and deny are checked per connection after the accept, so they still work behind TLS.

Summary


  • Every connection holds a thread until it closes. A connection that a firewall dropped silently ends only through the read timeout. Without one, dead sessions fill maxSessions, and then the server closes its port and refuses every new terminal.
  • The first listener that returns true owns the message. A listener that returns true without answering swallows everything behind it; one that answers and returns false gets the request answered twice. A message nobody claims is dropped, with only its <receive> logged.
  • A listener holds up its own connection, because its session thread is the only reader. Slow work belongs in the TransactionManager. One listener instance serves every connection, so it keeps no per-message state in fields.
  • A frame the server can't unpack ends the connection and loses the requests behind it, unless ignore-iso-exceptions is set. Either way, the hex dump in the log shows the card number in clear.
  • The server picks the connection for a message it starts. QServer's <in> queue sends to the last connection by default. Address a terminal through the source it last used.
  • clientauth requires a certificate, and serverauth checks it. Set both for mutual TLS. A socket factory ignores bind-address.

Challenges


  1. A firewall drops idle flows after 30 minutes, your terminals echo every 10 minutes, and a few hundred of them are switched off every night without closing their connections. Choose timeout and maxSessions. How many dead sessions does the server hold at 03:00, and how long does each one last?
  2. Write the listener chain for a server that answers echoes itself, records every request for audit, and queues the rest for the TransactionManager. Which listener comes first, and what does each return? What does the audit record miss when a frame fails to unpack?
  3. The terminal directory of 3.5 lives in one JVM. You run two servers behind a load balancer. How does a key change reach a terminal connected to the other server, and what happens to it while the terminal is reconnecting?
  4. A terminal vendor can't put client certificates in its devices for another six months. What can allow, deny and the network do in the meantime, and what can't they?


Design Note: Why a Thread per Connection?


In 2.1.x each connection gets a thread that only waits in receive(). One thread reads one connection in order, so a listener never sees two messages from the same connection at once, a slow peer slows only itself, and the code is plain blocking I/O with no callbacks.


A thread is not cheap, so the pool is bounded, and the bound turns dead connections into refused ones; jPOS relies on the read timeout to end them. A thread that waits in receive() can't do anything else, so any work a listener does stops its connection; jPOS puts a queue between the listener and the TransactionManager (unit s1).


jPOS 3 keeps the model and changes the thread: with virtual threads, thousands of mostly idle connections cost little memory. A dead connection still has to be noticed, though, and a listener still holds up its connection.
