At lunchtime the card table behind your server stops answering for four minutes. Every purchase in those minutes comes back 05, "do not honour". Cardholders are told their bank refused them, and the dashboard that alerts on system errors stays green. In the same minutes one purchase is approved at the terminal although the server aborted it and kept no record of it.

Units s1, s5 and s6 made sure that a failed request gets an answer. This unit is about which answer, and about making sure it is the one that leaves: four rules, one per section heading.

Outputs come from jPOS 2.1.7, run as in unit s5: Q2 deploys the descriptors in one JVM, and unit s4's DirectTerminal hands each request to a real IncomingListener. Answer lines show the MTI, field 39 and field 11.

Each code tells the terminal, and the people behind it, what to do next. 54, 62 and 51 say the card or the account decided: don't try again. 14 and 30 say the request is wrong. 91 says the issuer couldn't be reached, and 96 says the server failed. With 05, some cardholders pay with another card and some leave, and the ones who call their bank hear that it saw nothing. Your monitoring, which alerts on the share of 96, sees four minutes of ordinary declines.

The Reason Goes to the Log, and the Response Carries Only the Code

The terminal got 54. The operator looking up STAN 000602 needs to know why. The TransactionManager's event says:

It says who aborted, not why. The reason is in the Result, which lives in the Context, and the Context is printed only in the dump that unit s1 turned off. So (2) writes one event per failure it answers, to the logger named in its <participant> element (it implements LogSource):

Each line has the transaction's id, STAN and terminal, the code sent, and the cause with the class and line that reported it. For the outage, the cause is in the PREPARE warning the TransactionManager logged (unit s6).

It is tempting to send the reason back too, in a free-text field, "so support can see it". The merchant's terminal then shows card table unavailable: connection refused, or your database's host name. The field also has a length, and a reason that doesn't fit makes the whole response unsendable (unit s6).

Write the messages without card data. ProtectedLogListener masks the fields of a message in an event, not text (unit s1), so a PAN in fail(...) or in an exception message reaches the log in clear.

On the Abort Path SendResponse Sends Whatever RESPONSE Holds

Unit s4 advised doing what can fail in prepare, while a failure can still become a refusal. So RecordApproval now writes each approval to the journal in prepare, and its abort takes the entry out again. It runs after unit s4's ReserveDailyLimit (500.00 a day) and Authorize, and before unit s5's AnswerFailures, which ran as demo.S5AnswerFailures, so the trace calls it d.S5AnswerFailures:

The journal's disk is full, so record throws on a purchase of 27.50 by a card with nothing spent today. What does the terminal print?

The transaction aborted as it should. ReserveDailyLimit gave the 27.50 back to the daily limit, and nothing is in the journal. But Authorize had already put its approval in RESPONSE. AnswerFailures, in unit s5's version, found a response and took it as an answer to a failure. SendResponse sends whatever RESPONSE holds on either path, and it doesn't read field 39.

The terminal printed an approval and the merchant handed over the goods. The server has no journal line, so settlement can't match the purchase, and the daily limit has already forgotten it, so the card can spend the same 27.50 again.

That is why the condition at (3) keeps a response only when it refuses. On the abort path an approval is replaced like a missing response, here with 96, because the exception reported nothing:

The fix works only if AnswerFailures runs after RecordApproval. Put it before, and the approval leaves again:

prepareForAbort reaches only the abort participants after the one that aborted (unit s4). AnswerFailures had already been prepared, voted NO_JOIN, and was never asked again. It belongs right before SendResponse, after every participant that can fail, and that includes the groups a selector adds.

  1. Make the ATM network's answers say what really happened

    • SendResponse sends whatever RESPONSE holds on the abort path, so an approval built before a later failure must be replaced, a refusal kept, and the answering participant must run after every participant that can fail.
    • Participants report causes in the Result and one abort participant maps them to field 39; a thrown exception or an unlisted cause is 96, never a decline.

The server approved a purchase of 42.50, and the 0210 never reached the terminal. The acquirer doesn't know the outcome, so it reverses (unit c12): an 0420, repeated as 0421 until it gets an answer. A selector sends reversals to their own group:




RecordApproval keeps each approval in the journal under the terminal (41), the STAN (11) and the transmission time (7). Reverse looks it up and gives the amount back to the daily limit:



The purchase, its reversal, the repeat, and then a reversal of a purchase the server never saw (each line shows the first 20 of field 90's 42 digits):



(1) The original's STAN is in field 90. A reversal is a new message with its own STAN and time (unit c12). Field 90 starts with the original's MTI, STAN and field 7. Look the original up by the reversal's own fields 11 and 7 instead:



Nothing was undone. The cardholder paid nothing, yet 42.50 of the day's limit stays used until the reset. With a hold on an account, the money stays held.


(2) A repeat finds nothing. An answer can be lost as well, so the same reversal can arrive several times. take removes the approval, and a repeat finds nothing to undo. Read it with find, which leaves it in the journal:



The repeat gave the 42.50 back a second time, and the card can now spend 542.50 today.


(3) Found or not, the answer is 00. A reversal asks that the original have no effect. A purchase the server declined, or never received, has none, so the reversal has done its job. A refusal would leave the acquirer with an open reversal for a purchase that never happened.

Summary


  • A response code says who failed. Participants report causes in the Result, and one abort participant maps them to field 39. A thrown exception becomes 96, never a decline.
  • The reason goes to the log. The TransactionManager's event says who aborted, not why; the answering participant logs the cause with the STAN and terminal, and the response carries only the code.
  • On the abort path SendResponse sends whatever RESPONSE holds. An approval built before a later failure goes out unless the answering participant replaces it, and it can only do that from its place right before SendResponse.
  • A reversal is answered 00, finds its original through field 90, and undoes it once, so a repeat or a reversal of nothing changes nothing.

Networks publish their own tables, and the codes your server returns are part of its interface specification.


Result in 2.1.7: fail(irc, source, format, args...) records a failure and returns the Result; its FAIL() returns ABORTED | READONLY | NO_JOIN. failure() is the first failure recorded, or null. Caller.info() gives the calling class, method and line. The Result is printed only in the Context dump.


On the abort path in 2.1.7: prepareForAbort is called on the AbortParticipants after the participant that aborted, in order, groups included. SendResponse sends RESPONSE from commit and from abort alike, unless TX is in the Context, the Result has an entry with an inhibiting code, or the source is gone.


Approval codes other than 00 exist in ISO 8583:1987 (08, 10, 11). A server that sends them must treat them as approvals at (3) too.


Networks differ. A partial reversal gives back only part of the amount; ISO 8583:1987 carries the actual amount in field 95, and some networks use field 4 instead. Some networks also match an original by fields 32 and 37.

Design Note: Why Does jPOS Report Failures Instead of Answering Them?


jPOS's stock participants (CheckFields, SelectDestination, QueryHost) report failures and build no response: CheckFields records MISSING_FIELD, QueryHost records HOST_UNREACHABLE. The codes are jPOS's own, from CMF, and they mean the same on every network.


The reason is that the response belongs to the network. Field 39 is two characters in ISO 8583:1987 and four digits in jPOS's own message format, and each network adds codes of its own. A participant that wrote field 39 itself would be tied to one network. A participant that reports a cause can run behind any of them, and one table at the end of the chain speaks the network's language.


The price is that a report alone sends no response. Without a participant that turns it into a response, the terminal waits out its timeout (unit s5), and a code missing from the table falls back to 96, the right answer for a cause nobody planned for.
