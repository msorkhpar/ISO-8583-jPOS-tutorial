A merchant's purchases start failing on the day its payment gateway is upgraded. The acquirer's host logs that it cannot unpack DE 48, and the upgrade didn't touch DE 48. The fault is in another field.

Data elements (DEs, "fields") carry what a transaction needs: the card, the amount, the terminal, the time, the result. In a message they follow the bitmap (unit 2) with nothing between them, no tags and no separators. We follow ISO 8583:1987 as jPOS's iso87ascii.xml and iso87binary.xml packagers define it; where your network's specification differs, it wins. Six rules, one per section heading.

A Field's Format Is All the Receiver Has to Find Where It Ends

Every field has a format. n6 is six digits, always six. ans8 is eight letters, digits or special characters. n..19 is up to 19 digits behind a two-digit length prefix (an LLVAR), and ans...999 up to 999 characters behind a three-digit prefix (an LLLVAR). A purchase packed with iso87ascii.xml:

Split up:

The receiver reads 16 and takes 16 digits for DE 2, then twelve for DE 4 and six for DE 11, because its packager's table says so. Nothing in the bytes marks where a field ends, so the sender's table must say the same.

DE 43, the merchant's name and location, is where the two tables most often disagree. In the 1987 edition it is fixed ans 40. The 1993 edition made it ans..99, an LLVAR. Suppose the upgraded gateway writes DE 43 the 1993 way and the host reads it the 1987 way:

The host took 40 characters for DE 43: the length prefix 23, the name, and most of DE 48. Then it looked for DE 48's three-digit length and found 77. The error names DE 48, which the gateway wrote correctly. A team that trusts the error message spends the day on DE 48, while every purchase that carries a DE 43 is rejected.

So when a receiver can't unpack field n, check the fields before n first, starting with those whose format changed between editions (the Reference marks DE 12, 22, 25, 39 and 43).

A Short Value Is Padded, a Long One Is Refused, and Nothing Else Is Checked

A fixed field always fills its width. When jPOS packs, it pads numeric fields with zeros on the left and text fields with spaces on the right. A developer sets the amount to "50", meaning fifty, and the terminal ID to "T1":

DE 4 is in minor units with no decimal point, so 000000000050 is 0.50. The merchant's fifty-euro sale goes out as a request for fifty cents, and nothing fails on the way. Set amounts as whole minor units (5000 for 50.00) and let the packager pad them.

Padding on the other side would change the value: zeros on the right would make 50 into

  1. Spaces on the right are harmless in text, but they are still there after unpacking. The receiver's DE 41 is T1 and six spaces, and "T1".equals(msg.getString(41)) is false.

A value that is too long is refused, never cut: the nested exception says Field length 16 too long. Max: 15. jPOS refuses it only when it packs, which behind a QMUX happens on the channel adaptor's thread, far from the code that set the field. Check lengths where you build the message.

Length is all jPOS checks. 123.45 went into an ASCII numeric field, dot and all, and letters would have gone in too. The host may reject the dot or misread it, and neither is the sale you meant. Validate characters before you set a field.

Practice: Unpacking data elements

A message is a single string, and the fields inside it are not separated by anything. Section "A Short Value Is Padded, a Long One Is Refused, and Nothing Else Is Checked" is the reason it can still be read: every data element has a declared format, and the format says how long it is.

A fixed-length element simply occupies its length. A variable-length one announces itself first — an LLVAR carries two digits of length before its value, an LLLVAR carries three. So a reader walks the message from left to right, and at each step it already knows how far to walk next. Get one length wrong and everything after it is garbage, which is why a malformed message usually fails somewhere other than where it is malformed.

The Packager Decides the Bytes, So Both Peers Need the Same One


n..19 says "digits, with a two-digit length". It doesn't say how a digit or a length becomes bytes. That is the packager's choice, and three are common. The same PAN through each of them:




ASCII and EBCDIC write one byte per digit, prefix included. BCD packs two digits into a byte, so its LL prefix is one byte and its LLL prefix two. The BCD prefix counts digits, not bytes: 16 announces 16 digits in 8 bytes, and 19 announces 19 digits in 10, the spare half-byte filled with 0. Whether the filler goes on the left or the right is another packager setting.


A peer that reads a BCD prefix as a byte count takes 19 bytes for that PAN instead of 10, and every field after it is wrong, as in 3.1. Agree on the packager, not only on the formats, and compare it byte for byte with the specification's sample messages. Unit c13 shows how jPOS packagers are built.


A Field's Type Decides How You Read Its Value


The letters in a format name the characters allowed (the Reference lists them).


Numeric values are strings of digits. Parse an amount into a long of minor units, never a double. DE 7, the transmission date and time, has no year, so ISODate.parseISODate picks the year that puts the date closest to now.


Track data (z) is digits plus a separator between the PAN and the expiry date. On the stripe the separator is the half-byte D; written as text it is =. A terminal application builds Track 2 with D, and the link packs DE 35 in BCD. What does the issuer receive?




The BCD packager turns = into the half-byte D and back. A D character it packs as the digit 4, so the separator is gone: the issuer receives 24 digits and no way to tell where the PAN ends. Always set = in the ISOMsg. An ASCII packager sends whichever character you set, and peers send either, so accept both when parsing.


Binary fields (b) give their length in bits: b64 is 8 bytes, as for DE 52, the PIN block. jPOS keeps them as byte[]; getBytes returns the bytes and getString returns them as hexadecimal text. An ASCII packager writes such a field as hex characters (IFA_BINARY) or as raw bytes behind a length (IFA_LLLBINARY). Check which one your specification means.


Never print a PAN, a track or a PIN block. ISOUtil.protect masks a PAN for display, and units c8 and s8 set up a logger that masks for you.


Which Fields Must Be Present Depends on the MTI and the Network


Only the MTI and the primary bitmap are in every message. Everything else depends on the message:


  • an 0800 echo test carries no PAN and no amount, only DE 7, DE 11 and DE 70;
  • an 0100 card-present authorization may carry Track 2 (DE 35) instead of DE 2, because the PAN is inside the track;
  • an 0110 must echo the fields the network lists (typically DE 3, 4, 7, 11, 37 and 41) and add DE 39.


A network's specification has a table with one row per field and one column per MTI. Each cell is M (mandatory), C (conditional: required when something else holds, such as DE 2 when there is no Track 2) or O (optional). A validator built from one list of "required fields" for every message refuses the network's own echo tests, or lets a response without DE 39 through. Build the checks per MTI from that table.


In jPOS an absent field costs no exception: hasField(n) says whether it is there, and getString(n) returns null when it isn't.

DE 55 Is a List of Tag-Length-Value Objects, Read as Bytes


When a chip card is used, the terminal sends the card's cryptogram and the data around it in DE 55, as a list of BER-TLV objects with nothing between them. Each object is:


  • a tag of one or more bytes. When the low five bits of the first byte are all ones (0x1F), the tag continues in the next byte, and it keeps going while the byte just read has its top bit set. 95 is a one-byte tag, 9F26 and 5F2A are two-byte tags, DF8101 has three;
  • a length: one byte for 0 to 127, otherwise 81 followed by one length byte or 82 followed by two;
  • the value: exactly that many bytes.


The stock iso87ascii.xml still calls DE 55 "reserved ISO" and packs it as text, with IFA_LLLCHAR. Network specifications define it as binary (iso87binary.xml uses IFB_LLLBINARY). Through the stock packager the bytes arrive unchanged, but the field comes back as a different type:




On the message you built, DE 55 is a byte[] and getString gives 46 hex characters. On the message you received, it is text, and getString gives the 23 raw bytes as characters. Code that parses hex from getString(55) passes every unit test built on set(55, bytes) and fails on the first real message. getBytes(55) returns the same 23 bytes in both cases. TLVList (in org.jpos.tlv) splits them, and refuses a list whose last object claims more bytes than are left.


The cryptogram is not a secret like a PIN, but DE 55 can also hold track-equivalent data (tag 57), so keep the whole field out of logs. Unit 18 goes through the EMV tags.


ISO 8583:2023. The 2023 edition builds several fields (among them DE 34, 43 and 104) from datasets: a 1-byte dataset identifier, a 2-byte big-endian length and the content, repeated, with BER-TLV or bitmapped elements inside. DE 55 stays plain BER-TLV. jPOS 2.1.7 reads such a field only as opaque binary; jPOS 3 reads datasets natively (unit s13). Unit 17 covers them.

Summary


  • A field's format is all the receiver has to find where it ends. One field written in the wrong format shifts every field after it, and the error names a later, correct field. DE 43 is fixed 40 in 1987 and LLVAR in 1993.
  • A short value is padded, a long one is refused, and nothing else is checked. "50" in DE 4 is 0.50, unpacked text keeps its trailing spaces, and characters are yours to validate.
  • The packager decides the bytes. ASCII, BCD and EBCDIC write the same field differently, and a BCD prefix counts digits. Peers must share the packager, not only the formats.
  • A field's type decides how you read it. Amounts as minor units in a long, = in Track 2, binary fields with getBytes.
  • Mandatory fields depend on the MTI and the network. Check each message against its column of the specification's table.
  • DE 55 is BER-TLV, read as bytes. Tags and lengths can be longer than one byte, and what getString(55) returns depends on where the message came from.

Challenges


  1. Your acquirer sends a specification with 60 fields. How would you find, before the first test message, every field whose format differs from iso87ascii.xml, and what would you do with each?
  2. A terminal sends amounts in a currency with three minor digits. Where in your system does the number of minor digits come from, and what goes wrong if only the terminal knows it?
  3. Your receiver trims trailing spaces from every text field after unpacking. Name a field where that loses information, and decide whether to trim at all.
  4. Two peers agree on n..19 for DE 2, but one uses BCD with the filler on the left and the other on the right. Which PANs come through intact, and what test would catch the others?


Design Note: Why Fields Have No Tags


ISO 8583 puts fields back to back and lets a bitmap say which are present. A bitmap of 8 bytes announces 64 fields (16 characters in ASCII), and a fixed field spends nothing on a length or a tag: the purchase in 3.1 is 64 bytes. The price is that the receiver needs a table to read the message, and one wrong entry in it spoils everything after that field, as 3.1 shows.


A tagged format, such as the BER-TLV inside DE 55, labels every value with its tag and length. A reader can skip what it doesn't know, fields can come in any order, and a new one breaks nothing. The price is two or more bytes per value, and a reader that handles tags and lengths of variable size. For open-ended data such as chip data, specifications put TLV inside one field, and the 2023 edition does the same for more fields.
