At 02:00 the terminal-management system copies each terminal's end-of-day batch into the server's batch/request/ directory, and a processor checks the totals and answers. One morning reconciliation finds that terminal 29110001's batch was accepted with 102 records. The terminal sent 412, and the copy in the archive holds all 412. The log has no error.

Files are the other way a payment server exchanges data: batch uploads, stop lists, clearing and settlement. jPOS handles "drop a file, get a file back" with DirPoll. Five rules, one per section heading from 17.2 to 17.6, cover the files and then the running node. Every output is from jPOS 2.1.7, compiled for Java 17.

A Batch Directory Under Q2

org.jpos.util.DirPoll watches a base directory, and org.jpos.q2.iso.DirPollAdaptor runs it as a QBean. deploy/60_batch.xml:

On deploy the adaptor creates six directories under the path: request, run, response, tmp, archive and bad (17.3 explains .req *). It builds a pool of up to poolSize threads and creates the processor. The <property> elements go to DirPoll and, if the processor is Configurable, to the processor too, so the processor's own settings sit in the same descriptor. A processor that is a LogSource gets the adaptor's logger and realm.

The processor reads a batch: a header H|terminal|batch, one D|amount per debit and one C|amount per credit in minor units, and a trailer T|count|net with net = debits − credits.

The adaptor creates one processor, and DirPoll runs every file through it, on as many threads as the pool allows, so per-file totals live in local variables, as in a participant (unit s1). The log line names the file and the batch, never a record: ProtectedLogListener masks fields of a message, not text (unit c8). In the runs below, a subclass of this processor also prints when each call starts and how it ends.

How the Processor Ends Decides Where the File Goes

Three files arrive together: b1.req is a good batch, b2.req has records but no trailer, and b3.req has a trailer that disagrees with its record. Where does each end up?

The polling thread lists request/, moves each file to run/, and hands it to the pool:

  • It returns bytes. DirPoll writes them to tmp/ and renames the result into response/, so whoever reads response/ never sees half an answer. The request goes to archive/ (with archive=true) or is deleted.
  • It throws a DirPollException with setRetry(true). The pool thread waits ten poll intervals, here 10 seconds, and moves the file back to request/.
  • It throws anything else, a NullPointerException included. The file goes to bad/ and the exception is logged under the adaptor's realm.

b2.req never gets its trailer, so it goes round every ten seconds, with a log event each time, until a person moves it. DirPoll keeps no count of attempts. The ten-second wait also happens on a pool thread. With poolSize 1, four good files arrive while b2.req waits:

c1.req waited eight seconds. On a night with three hundred terminal batches, one file that never completes adds up to ten seconds to every file behind it, for as long as it stays. Retry only a file that can still improve: a missing trailer, not a wrong one. Give the pool more than one thread, and alert when the same name keeps retrying.

DirPoll Takes a File the Moment It Appears, Finished or Not

The terminal-management system writes straight into request/: a quarter of the file, then, 1.5 seconds later, the rest. Here it is against a processor that sums the records it finds and doesn't look for a trailer:

DirPoll found the file at its next poll, moved it to run/ and read the 1552 bytes that were there. The move didn't stop the sender: its open file follows a rename, so it went on writing into the file in run/, and after the archive step in archive/. The answer counts 102 records and the archived copy holds 414 lines, a header, 412 records and a trailer, so the archive hides the fault.

BatchTotalsProcessor asks for a retry when the last line isn't a trailer:

The check caught it, but only because the sender writes the trailer last and finishes within ten seconds. The fix belongs to the sender: write the file in a directory of its own on the same file system, then rename it into request/. Within one file system a rename is atomic, so DirPoll sees no file or the whole file. A move from another file system is a copy, not a rename, and has the same problem.

A sender that creates the file and fills it a moment later gives DirPoll zero bytes. With a single priority, or none, DirPoll lists everything in request/, and our 0-byte b5.req reached the processor. The filter that skips empty files (unless zero-length is true) and matches the extensions runs only with two or more priorities. .req * switches it on and still accepts every name: with it, b5.req was processed once it had content.

Problem statement

Treasury reports three kinds of trouble: a run that was paid short, a run that bounced to bad/ when it only needed a few more seconds, and a run that reached bad/ only after DirPoll had tried it all night.

A Stop or a Crash Leaves Files in run/, Some of Them Already Done


Five batches wait in request/ when the node starts. The processor here also posts each batch to a ledger, which takes two seconds, and the pool has one thread; this node archives without timestamps. While b3.req is being posted, the node is killed with kill -9:



Only one file was in the processor's hands, yet four are in run/. The poller moved all five out of request/ from its first listing, and the pool queued four of them in memory behind the busy thread. Nothing moves files back from run/ at start-up: after a restart they were still there.


Of those four, b3.req was posted and the other three never started, and the directory can't tell you which is which. Leave them, and three terminals' batches are never processed. Move all four back to request/, the obvious runbook step, and the ledger shows:



Terminal 29110003's merchant is paid twice.


With SIGTERM, Q2's shutdown hook undeploys the adaptor, which stops the polling thread but doesn't wait for the pool. The pool went on taking files from its queue while Q2 shut down, finished b3.req, started b1.req and posted it, and the JVM exited before DirPoll could archive it:



So a file in run/ may have been done or never started, and the processor has to make a second run harmless. Identify the batch by what is in it, here the terminal and batch number in the header, and record that identity in the same database transaction as the postings (unit s9). A batch already recorded gets its answer again and posts nothing. Never use the file name: a terminal may send batch.req every night. The runbook then moves run/ back to request/ before starting:



In a container, the batch directory lives on a volume, or a restart discards run/ and the files in it. A longer stop grace period doesn't help DirPoll, since nothing in it waits for the pool.

A Command Sees Only the JVM It Runs In


Q2 has a command line: --cli gives an interactive q2> prompt, and -c "cmd; cmd" runs commands. With either and no -d, Q2 deploys deploy-cli/ instead of deploy/. An operator runs it on the node's machine, in the node's directory, while the node is running:



shownr lists the NameRegistrar, and it holds no MUX and no server. The command started a second JVM with its own registry (unit c1), which deployed the logger in deploy-cli/ and nothing else, and the shutdown stopped only that JVM.


To reach the running node, start it with Q2's SSH server: -s, port 2222 by default, user admin, public keys only, from cfg/authorized_keys. The same commands then run inside the node.


A command of your own is a class implementing CLICommand. What you type is upper-cased and loaded as a class under the active prefixes. In 2.1.7 the top-level prefix is fixed at org.jpos.q2.cli., but a subsystem names its own, so one small class goes into jPOS's package and the commands stay in yours:




ops:muxstat enters the subsystem, runs the command, and leaves the subsystem at the end of the line, so a later command in the same -c list needs an exit first. In a 2.1.7 command, args[0] holds the whole command line and the arguments start at args[1]. The node runs host-mux, whose link is up, and backup-mux, whose host isn't listening:



A readiness check or a runbook script built on -c reads an empty registry and reports nothing wrong while a link is down. Read the node over SSH, JMX, or a small QBean inside it.


drift Shows a Pause Only When It Covers the Monitor's Wake-Up


SystemMonitor (unit c8) sleeps for sleepTime, then measures how late it woke up and reports it as drift, in milliseconds. A late wake-up means the whole JVM was late: a garbage collection pause, or a process starved of CPU. With sleepTime 5000, we stopped the node with SIGSTOP for 3.01 seconds and then let it continue. The next dump:



The pause lasted 3011 ms, and drift says 531. The monitor was due to wake 531 ms before the process resumed. The other 2.5 seconds of the pause fell inside its sleep, where nothing measures them. With the default sleepTime of an hour, a pause shows only if it happens to cover the moment of waking.


Suppose a 3-second GC pause hits the node at noon. Requests whose timeout ran out during the pause return null (unit c12), the terminals send reversals, and the host was fine all along. The next dump says drift : 0. The record of every pause is the GC log, which the JVM writes with -Xlog:gc* (the Reference has the options). Compare its pause times with the times of the timeouts.

Summary


  • How the processor ends decides where the file goes. Bytes go to response/ and the file to archive/; a retry waits ten poll intervals on a pool thread and returns the file to request/; anything else sends it to bad/. A file that can't improve and is retried anyway stalls every file behind it.
  • DirPoll takes a file the moment it appears. A sender writing into request/ gets a partial file processed and archived complete. Senders write elsewhere and rename; processors check a trailer; .req * keeps empty files out.
  • A stop or a crash leaves files in run/, done or never started. The processor identifies each batch by its content and posts it once, so the runbook can move run/ back.
  • A command sees only its own JVM. -c starts a second Q2 on deploy-cli/; the running node is read over its SSH CLI.
  • drift shows a pause only when it covers the monitor's wake-up. The GC log records every pause.

DirPoll properties (2.1.7), as <property> elements of the adaptor:


PropertyDefaultMeaning

archive.timestamp, archive.dateformatfalse, yyyyMMddHHmmssappend . and a timestamp to the archived name, and to a name moved to bad/
archive.compressfalsezip the archived file
response.suffixnonereplace the request's extension in the response name (b1.req gives b1.rsp)
zero-lengthfalseaccept empty files; read only by the filter of two or more priorities
priority.regexfalsetreat each priority as a regular expression instead of a suffix
request.dir, response.dir, tmp.dir, run.dir, bad.dir, archive.dirthe namesrename the subdirectories
shutdown-timeout60000ms the adaptor waits for the polling thread to stop; it never waits for the pool


Adaptor attributes: path, pollInterval (ms, default 1000; a retry waits ten of them), poolSize (default 1), priorities (space-separated suffixes, * for any), processor (a DirPoll.Processor, given the name and the bytes, or a DirPoll.FileProcessor, given the File in run/, which reads it and writes any response itself).


Q2 command line (2.1.7): --cli (-i) interactive prompt; -c "cmd; cmd" run commands; -s, -sp, -su, -sa, -sh the SSH server's switch, port, user, authorized keys file and host key file. Commands in the jar include shownr [-a] [name], tmmon <txnmgr>, tail <logger>, sysmon, mem, uptime, version, tzcheck, deploy (a sub-prompt to list, enable and disable descriptors) and shutdown [--force]; man <command> prints a command's help where one ships.

Challenges


  1. Your processor posts a batch in one database transaction that takes up to 30 seconds. Choose poolSize and pollInterval for 3,000 batches arriving between 02:00 and 02:20, and work out what one file stuck in retry costs with your choice.
  2. Write the restart runbook for the batch directory as a script. Which checks does it run before it moves run/ back, and what does it do with bad/?
  3. Two nodes poll the same shared directory for availability. What happens when both scan request/ at once, and what would you put in place instead?
  4. Design a health check for a container platform that reports a link down within 30 seconds, without starting a second JVM.


Design Note: Why Directories and Renames?


DirPoll's whole protocol is a set of directory names and the rename between them. A sender needs no jPOS: any system that can write a file and rename it can talk to the server. The state of every file is visible with ls, and an operator can move it by hand.


The price is that a rename is the only atomic step. Nothing records why a file is in run/, how many times it was retried, or whether its work was committed. Everything this unit asks of the processor (a trailer, idempotent posting, a limit on retries) makes up for state the directories can't hold. A message queue or a database table would hold that state, and would cost every sender a client for it.
