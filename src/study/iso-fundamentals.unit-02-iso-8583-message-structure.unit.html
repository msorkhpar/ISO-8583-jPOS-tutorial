A terminal vendor sends its first test purchase, and the host's log says it could not unpack the message: "Problem unpacking field 42". The vendor's message has no field 42. Unit 1 showed what a message is made of: an MTI, a bitmap, and the fields the bitmap announces. To answer the ticket you read those parts by hand, bit by bit, with four rules, one per section heading. Every output below comes from jPOS 2.1.7 and its 1987 packagers, iso87ascii.xml and iso87binary.xml.

The MTI's Four Digits Say Edition, Class, Function and Origin

The four digits are read one at a time. In 0430, 0 is the 1987 edition (unit 1), 4 the reversal class, 3 an advice response (an advice reports something that already happened), and the last 0 says it comes from the acquirer. A receiver routes on the MTI before it reads any field.

A response adds 1 to the third digit, and a repeat sets the fourth: an 0420 that got no acknowledgement goes again as 0421. A repeat is answered like the original, so both get 0430. Unit 4 shows how jPOS derives these MTIs and which messages may be repeated.

Bit n Says Field n Is Present, Counted From 1 at the Leftmost Bit

The primary bitmap has 64 bits. Bit 1 is the most significant bit of the first byte, and bit 64 the least significant bit of the last. A purchase with fields 2, 3, 4, 11 and 41, byte by byte:

Fields 2, 3 and 4 are the second, third and fourth bits of the first byte, 0111 0000, which is 70 in hex. Field 11 is the third bit of the second byte, 20. Each byte becomes two hex digits, and the bitmap reads 7020000000800000. jPOS computes it from the fields you set when it packs the message, and keeps it as field -1.

Spot the Problem: The Vendor's First Purchase

The vendor's purchase carries the same five fields: the test card 4111111111111111 behind its length prefix 16, processing code 000000, an amount of 25.00, STAN 000417 and terminal 29110001. Its bitmap is 3810000000400000. Which bits does it set?

38 is 0011 1000: bits 3, 4 and 5. 10 is bit 12, and 40 in the sixth byte is bit 42. Every field moved one bit to the right, because the vendor's code counts bits from 0. The host trusts the bitmap and reads each field with the definition of the next one. A program packed the purchase correctly, swapped in the vendor's bitmap, and unpacked it field by field:

The length prefix and the first digits of the card number became a processing code, and the card number became an amount of 1,111,111,111.11. The host noticed only because it ran out of characters at field 42, which is 15 long. The last line is the same purchase with a retrieval reference number (field 37) added: it unpacks without an error, and the five characters left over raise nothing.

With a new sender, check the bitmap of its first messages by hand against the fields it says it sends.

Bit 1 Announces a Second Bitmap, So It Is Never a Field

Fields 65 to 128 need a second, secondary bitmap of 64 more bits. Bit 1 of the primary bitmap says whether it follows. An echo test carries field 70, the network management code:

82 is 1000 0010: bit 1, so a second bitmap follows, and bit 7. In the second bitmap, 04 is its sixth bit, field 64 + 6 = 70. A receiver that ignored bit 1 would read 0400000000 as field 7.

Field 64 still fits the primary bitmap, so a message whose last field is 64, often the MAC, has one bitmap.

Tables of the 1987 edition list field 1 as the secondary bitmap, and some developers set it to ask for one. In jPOS that sets bit 1 and writes no second bitmap:

B0 sets bit 1, so the receiver took the next sixteen characters, field 3 and most of the amount, as the secondary bitmap, and ran out of characters in field 4. Never set field 1: the packager sets bit 1 from the fields the message carries.

Bit 65, the first bit of the secondary bitmap, works like bit 1: on the few networks that use fields 129 to 192, it announces a third, tertiary bitmap, and field 65 carries no data.

jPOS 2.1.7's iso87 packagers stop at two bitmaps. iso87ascii.xml defines field 65 as an ordinary one-byte field and sets bit 65 only when you put something in it. A network with a tertiary bitmap needs a packager configured for one (unit c13).

Practice: Building the primary bitmap

A bitmap is how an ISO-8583 message says which fields it carries. Section "Bit n Says Field n Is Present, Counted From 1 at the Leftmost Bit" describes it as eight bytes — sixty-four bits. A binary packager sends those eight bytes as they are; an ASCII packager writes them as sixteen hexadecimal characters, and that is the form this practice builds. Bit n is set when data element n is present.

The counting is where this trips people up, and it trips them quietly. The bits are numbered from one, not from zero, and they are read most significant bit first. So data element 2 is the second bit of the first byte: 0100 0000, which is 40 in hex. Data element 11 is the third bit of the second byte. And bit 1 is not a data element at all — it is the flag that says a secondary bitmap follows, which is how a message reaches fields 65 to 128. (Bit 65 of the secondary bitmap plays the same role once more, for a tertiary bitmap, so it is not a data element either.)

An off-by-one here does not crash anything. It produces a perfectly well-formed bitmap that describes a different message, and the first thing that notices is the system at the other end of the link.

Problem statement

Make primary in practice/bitmap/Bitmap.java return the correct sixteen hex characters for the data elements it is given. The file as shipped is wrong by exactly one bit position, and its grader says so.

The Same Bits Travel as 8 Bytes or as 16 Characters


A specification lists the bitmap as b 64: 64 bits. A link sends them either as 8 raw bytes or as 16 hexadecimal characters, one character per four bits. The echo test from 2.3, packed both ways:




The binary packager writes the same bits as 8 bytes per bitmap, and the numeric fields as two digits per byte, so the message is about half as long. Nothing in the bytes says which form was used: the ASCII packager took the binary message's first four bytes as the MTI and failed on the bitmap.


Each network's specification sets the form, link by link; both packagers here are 1987. When a new link fails on its first message, compare the bitmap of a captured message with the specification before you suspect any field.

Summary


  • The MTI's digits say edition, class, function and origin. A response adds 1 to the third digit, a repeat sets the fourth, and a repeat is answered like the original.
  • Bit n says field n is present, counted from 1 at the leftmost bit. A bitmap off by one bit turns the card number into an amount, and the message may still unpack.
  • Bit 1 announces the secondary bitmap and bit 65 a tertiary one. Neither is a field: set the fields, never field 1, and let the packager set bit 1.
  • The bitmap travels as 8 bytes or as 16 characters, as the link's specification says. A receiver can't tell the other form from the bytes; it fails or misreads.

Design Note: Why Is the Second Bitmap Optional?


The 1987 edition could have given every message one 128-bit bitmap. Instead the primary bitmap covers fields 1 to 64, and bit 1 says whether a second one follows. A purchase, which rarely needs a field above 64, saves 8 bytes, or 16 characters on a hex-ASCII link, on every message. On the slow lines of the 1980s that saving was worth a bit every receiver must check first.


The price is a bit that means something different from all the others. Every reader has to branch on it before it can find the first field, and every writer has to keep it consistent with the fields that follow, which is the trap 2.3 shows when field 1 is set by hand. The 1993 edition kept the design, and the tertiary bitmap repeats the scheme at bit 65. Support for that third bitmap is rarer than for the second: jPOS 2.1.7's own 1987 packagers don't have it.
