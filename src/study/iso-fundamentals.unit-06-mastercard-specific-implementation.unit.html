A processor's Visa link works (unit 5), and the next project is a Mastercard connection. The team writes a packager for it, and every unit test passes: each message packs and reads back with the same fields. On the first session with the network's test system, the analyst on the call says the host can't read them.

Mastercard's interface specifications are confidential and go to its customers and their processors. This unit uses only what is publicly described, and the specification for your connection governs wherever it says otherwise. Four rules follow, one per section heading. Every output is from jPOS 2.1.7.

A Mastercard Message Is EBCDIC Characters Behind a Binary Bitmap

A Mastercard link is described as EBCDIC: the MTI, the numeric and text fields and the length prefixes are EBCDIC characters, one byte each, and only the bitmap is binary. In jPOS that is a GenericPackager file of IFE_ field classes with an IFB_BITMAP. This one, cfg/mastercard-ebcdic.xml, covers a small authorization with the 1987 lengths; a real file takes every field from your specification:

An 0100 for 25.00, packed by this file; the same message is also packed by jPOS's iso87binary.xml for comparison:

One column per part: MTI, bitmap, fields 2, 3, 4, 11 and 41, with the PAN's middle digits masked.

The MTI is F0F1F0F0, and the amount takes twelve bytes. The binary packager writes digits in BCD, two to a byte, so its MTI is the two bytes 01 00. The bitmap is the same 8 bytes in both. Field 41 is text in both and still differs: EBCDIC F2F9… against ASCII 3239….

Unit 5's Visa packager writes text in EBCDIC but numbers in BCD. A host that expects the layout above reads its first four bytes, 01 00 70 20, as the MTI and refuses the session's first message.

Clearing is another format. Authorizations travel online in the 1987 messages this unit packs. Mastercard's clearing files are commonly described as following the 1993 edition, with MTIs such as 1240 and 1442, so they need 1993 field definitions (unit 1). Unit 7 shows where clearing fits in the flow.

A Packager That Reads Its Own Messages Back Proves Nothing

The team in the opening built its layout from iso87binary.xml, turning each numeric IFB_ class into its IFE_ twin and keeping IFB_BITMAP. Field 41 there is IF_CHAR, which has no B to replace, so this line came through unchanged:

Their tests pack a message and unpack it with the same file. The purchase from 6.1, tested that way, then compared with the bytes of 6.1, standing in for the specification's sample:

Only field 41 differs: it went out in ASCII. The host reads those eight bytes as EBCDIC and gets control characters instead of 29110001, so its terminal lookup finds nothing for any message from that terminal.

A round trip can't catch this, because the same wrong class packs and unpacks and the two mistakes cancel. Only bytes from outside your code can: the specification's sample messages. Copy a sample's hex dump into a test and compare byte for byte:

A Frame Is a Two-Byte Binary Length, Then the Message


TCP delivers a stream of bytes, so each message travels behind its length, which belongs to the transport rather than the message (unit 1). Mastercard links are commonly described with a two-byte binary length and no other header. Here jPOS's PostChannel sends the 0100 from 6.1 to a plain socket that prints what arrives:



00 3E is 62, the length of the message alone, and the MTI follows at once. The team's domestic link used ASCIIChannel, which writes the length as four ASCII digits. Both mismatches:



An ASCIIChannel host reads 00 3E F0 F1 as four digits and refuses them. The other direction is worse: a PostChannel host reads the first two ASCII digits, 30 30, as a length of 12336 bytes and waits for bytes that never come, until its read timeout fires (two seconds in this run). Meanwhile the client gets no answer, and a purchase without an answer has to be reversed (unit 4).


jPOS has no channel named after Mastercard because none is needed: PostChannel writes two big-endian length bytes and, unless you give it a header, nothing else. Q2 deploys it like any channel, in deploy/10_host_channel.xml:



Confirm in your specification that the length counts only the message, and whether your connection puts anything else in front of it. Unit c3 shows channels in jPOS.


Field 48 Is Read Tag by Tag, and an Unknown Tag Must Not Stop the Message


Field 48, "additional data, private use", is a container on a Mastercard link. It is generally described as a one-character transaction category code (TCC), then subelements, each a two-digit tag, a two-digit length and that many characters. The tags and their meanings are in the specification. jPOS reads this shape with MasterCardEBCDICSubFieldPackager, declared inside the layout file:



Field 48 itself is IFE_LLLBINARY: an EBCDIC length, then the bytes the subfield packager has already written in EBCDIC. IFE_LLLCHAR would convert them a second time (the category code D9 goes out as FD), and the message would still read back, as in 6.2. IFEMC_TCC takes the first character as the category code (subfield 0) only when it is a letter or a space, since some messages carry none.


A field 48 with category code R and subelements 42 and 61, then the same field after a release adds subelement 33 in front. Both fields are read at 42's old offset and by the packager above (consumed counts the bytes before field 48):



The fixed-offset reader takes AB1 for subelement 42 without any error, and every decision that uses 42 is now made on another subelement's data. The packager finds 42 by its tag wherever it is, but it refuses a tag it has no definition for, and the whole message with it.


Mastercard publishes mandated changes on a regular release schedule, so plan for tags you have never seen. Declaring every tag from 01 to 99 with IFEPE_LLCHAR keeps the ones you don't use as text:



You can also declare field 48 as plain EBCDIC text and split it in your own code, keeping what you don't know. Either way, keep the meaning of each tag in one mapping between your internal format and the network's, so that a release changes that mapping and not every application behind it.

Summary


  • A Mastercard message is EBCDIC characters behind a binary bitmap. A packager borrowed from a BCD link sends an MTI the host can't read.
  • A packager that reads its own messages back proves nothing. A wrong class packs and unpacks its own bytes. Compare every message with the specification's samples, byte for byte.
  • A frame is a two-byte binary length, then the message. An ASCII length on either side gets the first frame refused or leaves the host waiting for bytes that never come.
  • Field 48 is read tag by tag. Fixed offsets misread after the next release, and a packager missing one tag refuses the whole message. Declare every tag, or split the field in code.


Reference


Fields with a Mastercard-specific role, as publicly described:


FieldRole
48additional data, private use: a transaction category code, then tag-length-value subelements
61point-of-service data: whether the cardholder and the card were present, the terminal's capabilities and location

Challenges


  1. Your specification has three sample messages, one with a field above 64. What does that third sample check that the other two can't, and which mistake in a packager would only it catch?
  2. Field 48 on your link has 40 defined tags, and you use three. Compare declaring all 99, declaring field 48 as text and splitting it in code, and declaring only your three: what does each do on the day a release adds a tag?
  3. A switch relays between a Mastercard link and an internal ASCII link. Which conversions happen at the boundary, and could any field pass through as the same bytes?
  4. Your Visa and Mastercard links each have a packager file. List what the two share, and decide whether a shared base file is worth having.


Design Note: Why Tags Inside a Bitmapped Message?


ISO 8583 announces fields with a bitmap and keeps each field's format in a table both sides hold (unit 1). The standard fixes that table, so a network can't add a field number for a new program. Field 48 is the way out. Inside one field the network defines a small format of its own, and makes it tag-length-value, so it can add a subelement in any release without touching the bitmap or the standard.


A tagged format grows safely only if every receiver skips unknown tags using the sender's length. A receiver that reads at fixed offsets, or refuses a tag it hasn't declared, turns the network's addition into an outage on release day.
