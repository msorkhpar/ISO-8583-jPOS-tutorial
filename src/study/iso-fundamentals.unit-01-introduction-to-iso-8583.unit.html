A team's authorization client has run for years against one processor. A second acquirer signs on, and its specification also says "ISO 8583", so the plan gives the new link a day. The acquirer's host rejects the first message because it can't read it.

ISO 8583 is the international standard for the messages behind card payments: purchases, ATM withdrawals, refunds, balance inquiries, and the messages that cancel or confirm them. What it promises, and what it leaves to each link, comes down to five rules, one per section heading, the last two about jPOS. The examples run on jPOS 2.1.7, an open-source Java library for ISO 8583 (section "jPOS Is AGPL: Network Users of Your Modified Version Are Offered Its Source").

A Message Is an MTI, a Bitmap and the Fields the Bitmap Announces

A message has three parts: the Message Type Indicator (MTI), four digits that say what the message is; a bitmap that says which data elements, or fields, are present; and the fields themselves, such as the card number, the amount and the terminal. The 1987 edition defines 128 fields, and this request uses seven. The bitmap has one bit per field, written here as 16 hexadecimal characters for fields 1 to 64 (bit 1 set means a second bitmap follows, for fields 65 to 128), and only the fields whose bit is set follow, in field-number order. Some fields have a fixed length: field 4 is always 12 digits, in the currency's minor unit with no decimal point, so 100.00 is 000000010000. Others vary and carry their own length, like the 16 in front of the card number.

A reader that takes field 41 from offset 72 works until the first message with a field 22, then reads the wrong terminal. To find any field, it has to read the bitmap and walk every field before it.

The program prints the card number only through ISOUtil.protect, which keeps the first six and the last four digits. Never print or log a clear PAN, track data, CVV or PIN block, even in a test program: a log that holds card numbers falls under the card industry's security rules, and so does every copy of it. Unit c8 covers how jPOS masks them in its logs.

The Standard Fixes What a Field Means, and Each Link Fixes Its Bytes

The same 0100, packed by the two 1987 packagers that ship with jPOS, and each result read by the other packager:

The ASCII message is text. The binary one, printed in hexadecimal, puts two digits in each byte (binary-coded decimal, BCD) and the bitmap in 8 raw bytes, so it needs 47 bytes. Fields 41 and 49 stay text, which is why its hex ends in 3239313130303031383430. The fields and their meanings are the same, yet neither packager can read the other's message, and the errors blame a field length rather than the encoding.

ISO 8583 defines what each field means and its format in the abstract: field 4 is twelve digits. It doesn't say how a digit is written. Each network publishes a specification, its dialect, that fixes the encoding (ASCII, BCD, binary or EBCDIC), which fields it requires, what goes in the private fields, and how a few fields differ from the standard. The transport is outside the message altogether: the TCP connection, the length header in front of each message, any network header, TLS. jPOS keeps the two apart too: a packager for the message, a channel for the transport. Unit c3 shows channels in jPOS.

The team in the opening packed ASCII for a host that expected binary, and fixing that leads to the next difference: the length header, the required fields, the private fields. Plan a link from the network's specification, not from the standard's name. What the standard does fix is meaning, so a developer who knows ISO 8583 reads a new network's specification as a list of differences.

The First MTI Digit Names the Edition, and Editions Disagree on Fields

The standard has been revised several times, and the first digit of the MTI says which edition a message follows:

MTI version digitMeaning
0ISO 8583:1987
1ISO 8583:1993
2ISO 8583:2003
3–7reserved by ISO
8national use
9private use

This course uses 1987 messages (0100, 0200, 0400, 0800) unless a section says otherwise.

A client written for a 1987 link treats 00 in field 39 as an approval, and moves to a network on the 1993 edition. Fields 24, 25 and 39 as jPOS's packagers for the two editions describe them, and a 1993 approval checked the 1987 way:

In 1993 field 39 became a three-digit action code, and 000 is an approval. Field 24 became a function code that says what a message asks for, and field 25 a four-digit reason code. The client reports every approval as a decline. The issuer has approved and holds the funds. The cashier says the card was refused, and the client sends no reversal, because a decline needs none. A cardholder who pays again with another card now carries two holds. A test that uses the 1987 packager never packs a 000, since that packager refuses it: test with the network's own field definitions.

The 2003 edition (digit 2) introduced composite fields, which hold several independent sections called datasets, beside the primitive fields (one value) and the constructed ones (fixed sub-fields) of earlier editions. The current edition, ISO 8583:2023, builds more fields as composites; unit 17 covers it. Take the version digit of a 2023 message from your network's specification.

In jPOS 3. jPOS 2.1.7 has no packager for datasets: its TLV packagers help, but your code maps the datasets. jpos.org says jPOS 3.0.2 adds packagers that read datasets as sub-fields; unit s13 lists what changes in jPOS 3.

jPOS Is AGPL: Network Users of Your Modified Version Are Offered Its Source

jPOS gives you the message model (ISOMsg), packagers that turn a message into bytes and back, and channels that frame messages on a TCP connection.

A processor patches one of jPOS's channel classes to fit its acquirer's header, and runs the result as a service that merchants' systems connect to. It never ships the software to anyone. Does it owe anyone the patch?

jPOS is licensed under the GNU Affero General Public License, version 3 (AGPL v3); the jar carries the full text as JPOS_LICENSE. The plain GPL's obligations start when you distribute copies, which this processor never does. The AGPL adds section 13: if you modify the program and users interact with your version over a network, you must offer those users its source. The trigger is the modification, not whether the service is paid: unmodified jPOS carries no such offer. The merchants' systems may be such users. If you can't meet those terms, the jPOS project offers a commercial licence. Settle it with your legal team before you ship.

Summary

  • A message is an MTI, a bitmap and the fields the bitmap announces. A field's position depends on every field before it, so a reader walks the bitmap instead of using offsets.
  • The standard fixes meanings, and each link fixes the bytes. The dialect sets the encoding and the fields, the transport sets the framing. Two "ISO 8583" systems are not compatible until one maps to the other's specification.
  • The first MTI digit names the edition, and fields change between editions. A 1993 approval is 000 in field 39, and a 1987 check reads it as a decline.
  • jPOS is AGPL v3. A modified version that users reach over a network must offer them its source, or you need a commercial licence.
  • The course runs jPOS 2.1.7. jpos.org describes 3.x, and its examples may not compile here.

Design Note: Why a Bitmap?

A message could name each field it carries, with a tag and a length in front of each value, as chip data and the 2023 datasets do. ISO 8583 instead puts one bit per possible field at the front, and each field's format lives in a table both sides hold. For a message with a dozen fields out of 128, that costs 16 characters of bitmap, or 8 bytes in binary (twice that when a field above 64 is present), and nothing per field except the length of the variable ones.

The price is that a message can't be read without the table. A reader can't skip a field it doesn't know, because only the table says how long it is, and one wrong entry misreads every field after it. That is what the two packagers in 1.2 did to each other's messages, and why each network's dialect has to be written down field by field.
