Terminal 29110001 may take 1,000.00 a day. Shortly after lunch it declines a 25.00 purchase with 61, "exceeds amount limit", and every purchase after it. The merchant has sold nothing today, yet the terminal's row in the limits table says 1,000.00 is used.

The morning's two purchases, 600.00 and 400.00, were declined with 51 because the cardholders' accounts couldn't pay. The participant that reserves the amount against the limit had already written both reservations to the database, and nothing took them back. Unit s4 kept a limit in memory and gave a declined amount back in abort. A row in a database needs more than that: six rules, one per section heading.

One Database Transaction Spans the TransactionManager Transaction

The first version of the limit check (it ran as demo.AutoCommitReserve) borrowed a connection of its own and ran a conditional UPDATE:

After it come unit s4's Authorize, set to decline anything above 200.00 with 51, and SendResponse. The terminal's day:

With auto-commit on, each statement is committed as it runs, so the reservation was permanent before Authorize voted. Unit s4's fix, joining and giving the amount back in abort, fails when that second UPDATE fails: abort can only log, and the amount stays reserved.

So we make the whole TransactionManager transaction one database transaction. Open borrows a connection, turns auto-commit off and leaves it in the Context under DB, and under TX, which tells SendResponse not to answer yet (9.4). Every participant after it writes through that connection. Close commits or rolls back. Both log failures through their own logger, for a reason 9.4 explains:

The limit check now uses Open's connection:

The same day, and the trace of the first purchase:

ReserveTerminalLimit votes NO_JOIN and has no abort: the rollback undoes its statement along with every other statement on the connection. Close is an AbortParticipant, so it is asked after Authorize aborts, and it joins whenever Open succeeded. A participant added next year that writes through DB is covered without an abort of its own. DB and TX are ContextConstants names.

Write in prepare, So the Database Can Still Say No

A colleague asks why the UPDATE runs in prepare at all. Why not check the limit there with a SELECT, and write the reservation in commit, once the purchase is certain? Terminal 29110001 has 100.00 of its limit left, and two purchases of 80.00 arrive from two of its lanes at the same moment. How many are approved?

We ran that version as demo.CheckThenReserve. A demo participant held each transaction after its check until both had checked, so that the timing came out the same on every run:

Both checks read 90000, both passed, and both reservations were written. Two sessions run the same participant at once (unit s1), and a SELECT takes no lock, so nothing kept the second check from reading the row before the first write. A write in commit has a second problem: if it fails, the transaction can't become a decline any more (unit s4).

ReserveTerminalLimit checks and reserves in one statement. WHERE used + ? <= daily_limit changes the row only if the amount fits, and executeUpdate returns 1 or 0. The row stays locked until Close commits or rolls back. The same two purchases, with a 300 ms fraud check (demo.SlowStep) between the reservation and Close:

Whichever UPDATE came second waited for the row until the first transaction committed, then found 20.00 left and changed nothing. A lock timeout or a deadlock in that statement throws in prepare and becomes a 96 decline. In commit it would be a warning after the approval had gone. Holding the lock costs time: every purchase on that terminal waits behind it for as long as the transaction runs.

The Answer Waits for the Commit


A database commit rarely fails, but it can: the connection drops, or the database fails over. Take an Open that doesn't set TX, and declare Close after SendResponse, since the commit is quick. One purchase of 25.00, against a DataSource whose commit throws:




In 2.1.7 the TransactionManager calls commit in declaration order (unit s4), so the approval left before the database had committed. Then the commit failed, and the reservation went with it. The terminal approved the sale, and the server has no record of it. No reversal will come to clean it up, because the terminal got its answer.


Now with Open as shown, which also puts the connection under TX, and Close before SendResponse:




Close committed first, failed, and left TX in the Context (1). SendResponse won't send while TX is set. The terminal times out and sends a reversal for a purchase the database never recorded. On the abort path Close removes TX after the rollback, even a failed one (2), because nothing was committed and the decline is true.


SendResponse notes the refusal, *** PANIC - TX not null - RESPONSE OMITTED ***, in the Context's log, which is printed only when debug-context is on (unit s8). So Close, Open and ReserveTerminalLimit log failures themselves. They extend Log, and the TransactionManager gives each the logger named on its element.


With TX set and Close declared after SendResponse, no purchase is answered at all, approved or declined, because SendResponse always runs while the transaction is open. The first test purchase shows the mistake.


In jPOS 3 the documentation describes commit and abort in reverse declaration order. Check where Close has to stand on your version: it must commit before SendResponse sends.


A Transaction Holds Its Connection From Open to Close


The server now asks the card's issuer before it approves (unit s4's QueryIssuer, which pauses). The question sits between ReserveTerminalLimit and Close, so that an issuer's decline rolls the reservation back:



The TransactionManager runs four sessions, and the pool has four connections, one per session, with a connection-timeout of 1000 ms. Eight purchases from eight terminals arrive within 40 ms, and the issuer takes two seconds over each. How many are approved?



PAUSE gave each session back while the issuer worked, so four more transactions started. Their Open asked for a connection, but the four paused transactions held all four: a paused transaction keeps its Context, and the Context keeps the connection. After a second the pool gave up, and Open answered 96. With a pool of 16 all eight were approved after 2000 ms.


Size the pool to the number of transactions that can be between Open and Close at the same time. Without PAUSE that is max-sessions (which defaults to sessions). With PAUSE the sessions don't limit it, so count the paused transactions too, or cap them: in 2.1.7 the TransactionManager's max-active-sessions limits the transactions in flight, paused ones included, and queues the rest again for later (with a persistent journal they come back without the request and are never answered: unit s15). Add whatever else borrows from the pool, such as reports. Keep the pool's connection-timeout well under the terminal's timeout. A starved pool then answers 96 quickly. A wait longer than the terminal's would leave every queued purchase unanswered, and each would come back as a reversal.


The row lock lasts as long as the connection. A second purchase on terminal 29110011 would wait out the issuer's two seconds, as the second purchase in 9.3 waited out the fraud check.


A Decline Is Recorded Outside the Transaction That Rolls It Back


Disputes and monitoring need a row for every transaction, approved or declined, in the transaction log tranlog. A first version writes it through Open's connection, from an abort participant declared before Close (demo.LogInTransaction), so that the row commits together with the reservation. Five purchases, two of them too large for the account. How many rows?



The two declines were written, then rolled back with everything else Close undid. When the cardholder disputes the 250.00 decline, the server has no record of it, and a monitor that counts declines in the tranlog counts none.


RecordOutcome writes the row on a connection of its own, with auto-commit on, from commit and abort. It is an AbortParticipant declared after SendResponse, so it hears both outcomes, and its insert doesn't add to the terminal's wait:




The same five purchases:



record never throws. A failed insert is logged without card data, and the outcome stands. Give RecordOutcome a small pool of its own, a second DataSourceService under another name: on the shared pool of 9.5, each of the four 96 declines would have waited for a connection again in abort and lost its row.


A Stored Card Number Can Be Found Only With a Key


Support must find every transaction on a card that a cardholder reads out over the phone. The tranlog needs a value per PAN that is the same every time, so it can be indexed, and that tells nothing to someone who has a copy of the table. A SHA-256 of the PAN is the same every time. Is it safe?


Suppose a copy of the table leaks, with a SHA-256 column next to pan_last4. The first six digits are the card's range, printed on receipts and listed in public BIN tables: 411111 for this test card. That leaves six unknown digits (demo.Reverse):



The check digit rules out nine in ten of the million combinations, and one thread hashed the rest in a quarter of a second. Every other card in the table can be recovered the same way.


pan_hmac is an HMAC-SHA-256 under a secret key. Equal PANs still give equal values, but computing a candidate's value takes the key, and the key isn't in the database. The PAN itself is stored encrypted with AES-GCM under a second key, with a new IV for each row:



The keys are made once, outside the application, with the password read from the environment:



Keep the file out of the repository and off the database host (unit s7 covers keys in a security module). A search by card computes lookupKey(pan) and binds it to WHERE pan_hmac = ?, so the PAN never appears in SQL or in the database's log. The authorization path never decrypts. Decrypting is for disputes, in a separate component whose use is audited.

Summary


  • One database transaction spans the TransactionManager transaction. Open turns auto-commit off and puts the connection under DB and TX; Close, an abort participant, commits or rolls back and always closes. With auto-commit, a declined purchase keeps its reservation.
  • Write in prepare. A conditional UPDATE checks and reserves in one statement and locks the row until Close. A check in prepare with the write in commit lets two purchases pass the same check, and a failed write can't decline any more.
  • The answer waits for the commit. Close stands before SendResponse, and TX keeps the approval back until the commit succeeds. A failed commit becomes a timeout and a reversal, never an approval without a record.
  • A transaction holds its connection from Open to Close. Paused transactions hold theirs too. Size the pool to what can be in between at once, with a timeout under the terminal's.
  • A decline is recorded outside the transaction that rolls it back, by an abort participant after SendResponse, on its own auto-committed connection.
  • A stored card number can be found only with a key. An unkeyed hash of a PAN is reversed in a quarter of a second; store an HMAC to search by and an AES-GCM ciphertext.

Challenges


These have no single answer.


  1. The server dies after ReserveTerminalLimit ran and before Close. What happens to the reservation, and to the terminal's purchase?
  2. The issuer call in 9.5 holds the terminal's row for up to ten seconds. Reserve before the call in a short transaction of its own, and give the amount back if the issuer declines. What can now go wrong that couldn't before?
  3. Your peak is 300 purchases a second and the issuer answers in 400 ms, sometimes in 8 seconds. How big is the pool with PAUSE, and what does the database server say about that many connections?
  4. The HMAC key leaks, but the AES key doesn't. What can an attacker with the table do now, and what does rotating the HMAC key cost?


Design Note: Why Hold the Database Transaction So Long?


Open and Close keep one connection, and every lock taken through it, for the whole TransactionManager transaction. The alternative is a short transaction per participant, each committed at once, with a compensating write in abort. Locks are brief and the pool can be small. But each compensation is one more write that can fail where failure can only be logged, and each participant has to remember to write one. One rollback needs neither.


So this unit holds the transaction, and pays for it with row locks held across the issuer call and a pool sized for the slow cases.
