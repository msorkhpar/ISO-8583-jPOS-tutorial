A release adds CutoverService, a QBean that closes the business day at the time its descriptor names:

On the new production machine nobody set CUTOVER_TIME. Q2 logs deploy: for the file, the service starts, no warning appears, and the day closes at midnight instead of 23:00. An hour of purchases that belong to the next business day goes into today's settlement, and reconciliation is off on two days.

As far as Q2 could tell, nothing was wrong. What follows is what Q2 checks when it deploys a QBean, what it leaves to you, and where your own checks go so that a mistake shows up at deploy time and not at 23:00. The deploy order and the sources of ${name} values are in unit c1.

A Deploy Directory You Can Inspect

Every example in this unit runs Q2 in the same JVM, on a scratch deploy directory, and asks two questions about each descriptor after Q2's first pass: what is the file called now, and what state is its QBean in? Q2 registers each QBean with the JVM's MBean server as Q2:type=qbean,service=<name>, so the state is one JMX read away:

A file name with .BAD added means Q2 gave up on the file (.DUP and .ENV are in the Reference). The state is what QBeanSupport reports: Started, Failed, Unknown for a bean whose init never completed, or - when nothing is registered under that name.

A Value Nobody Set Is Absent, and Absent Means the Default

The service closes the day grace-seconds (default 30) after its time. The first version gave the time a default too:

@Config is jPOS 2.1.7's field injection: before Q2 calls setConfiguration, it sets every annotated field whose property the descriptor has, and leaves the others as they were initialised. We deployed this version four times, with these time properties:

  • a: value="23:00";
  • b: value="${CUTOVER_TIME}", with the variable not set;
  • c: the same 23:00, but under the name cutover-time;
  • d: value="${CUTOVER_TIME:23:00}", a default after the colon.

Which of them close the day at 23:00?

All four started. In b the variable resolved to nothing and there was no default after the colon, so the value counts as absent. In c the descriptor has no property called time. Q2 treats both the same way: the field keeps its initialiser. For a value that doesn't resolve, the Configuration that setConfiguration receives returns the caller's default, and get(name) returns "":

Q2 can't tell a value left out by mistake from one left out on purpose. A descriptor names only what differs from the defaults, so absence has to be allowed. Only the code knows which values have a safe default. Grace can default to 30 seconds, but no cutover time suits every network, so time gets no default. Leave such a field null and refuse to run without it. A misspelt name then fails at deploy too, not at 23:00.

A Configuration Refused in setConfiguration Renames the File; Refused Later, It Only Logs

The service, with no default for time:

The check could also go into initService, and a colleague's version puts it there:

Four descriptors in one pass: CutoverService with CUTOVER_TIME unset, the colleague's version with the same descriptor, CutoverService with time set to 23.00, and a bean whose startService throws while the system property settlement.dir is missing:

Q2 builds and configures a QBean while it deploys the file. Anything thrown up to and including setConfiguration makes Q2 unregister the bean and rename the file, with the reason in the deploy: event:

init and start are different. QBeanSupport catches what initService and startService throw, logs a warning (unit s1) and records the outcome in the state. Unknown means init never completed. start() returns at once in that state, so startService never runs. Failed means startService threw, and start() may be called again. We then set settlement.dir and called start on both beans through JMX:

The colleague's version is also harder to notice and to fix. Its file keeps its name, so ls deploy/ and a monitor that looks for .BAD files show a clean directory. The bean can't be started from JConsole either. Only the one warning in the log says that the day will never close, and only a redeploy of the file brings it back.

So a configuration error is refused in setConfiguration, with a ConfigurationException. startService is for what can only be checked at that moment, such as a resource that may be down. A failure there leaves a bean that can be started again once the resource is back.

(2): QBeanSupport keeps the configuration in its protected cfg field. An override that doesn't call super.setConfiguration leaves cfg null, and the first cfg.get in startService throws a NullPointerException.

Participants are different. The TransactionManager configures its participants inside its own init, so a participant's ConfigurationException shows up as the TransactionManager's init warning, as in unit s5, and 30_txnmgr.xml keeps its name.

<attr> Is Set Through JMX, So Its Setter Belongs in the MBean Interface


On busy nights operations want to give terminals more grace before the cutover, without a release. QServer reads its port from an <attr> element (unit s1), so they add one to 60_cutover.xml:





<attr> isn't another way to write a <property>. Q2 capitalises the name and asks the MBean server to set the attribute GraceSeconds on the registered bean. The MBean server knows only the attributes of the bean's MBean interface. CutoverService has none of its own, so JMX sees what QBeanSupportMBean declares, and that has no GraceSeconds. An unknown attribute fails the deploy, and the file is renamed.


The interface is named after the class with MBean added, and it extends QBeanSupportMBean:



CutoverService declares implements CutoverServiceMBean and gets the getter and setter for its graceSeconds field. Deployed with the descriptor above as 61_cutover_jmx.xml, then changed through JMX, then redeployed:



Use <attr> for a value an operator changes on a running server, from JConsole or any JMX client, with no redeploy. The change lives only in the object, so the next redeploy or restart puts back the descriptor's value. Write the change into the descriptor as well. A value read only at start needs no interface: use a <property>.


Nothing Is Started Until Everything Is Initialised, So a QBean Looks for What It Needs in startService


A settlement job writes the settlement file every night from the transaction database. It needs ds.txn, the connection pool that unit s9's DataSourceService registers when it starts, from 15_datasource.xml. The first version finds the pool in initService:



In the runs below a small QBean stands in for DataSourceService: it registers a DataSource under ds.txn in startService, with no database behind it.


The developer tested the job by copying 70_settlement.xml into the deploy/ directory of a running server:



After the Sunday restart:



with one warning, init and NotFoundException: ds.txn. Can you see why only the restart broke it?


Unit c1 showed the order of a pass: Q2 initialises every new file, then starts them. Copied in later, the job got a pass of its own, and the pool had started in an earlier one. After the restart both files are in the first pass. When the job's init runs, the pool has been initialised but not started, and it registers ds.txn only in startService. A lower prefix doesn't help: it orders the inits among themselves and the starts among themselves, and never puts a start before an init. So Monday has no settlement file, and the job is Unknown, which JMX can't start (14.3).


The job looks for the pool in startService instead:





(1) waits up to two seconds for the pool, which helps less than it seems. Q2 calls the starts one after another on its own thread, in file order. A pool with a lower prefix has finished its start before the job's begins, so the wait returns at once. Renamed to 80_datasource.xml, the pool sorts after the job:



The job waited its two seconds on Q2's thread, and the pool's start could only begin after that. So the job failed, and every file after it started two seconds late. The wait only helps with a provider that becomes ready on a thread of its own, such as a pool that connects in the background, and every later start waits with it, so keep it short. A missing provider leaves the job Failed, which the log and JMX show, and once the pool is up the job can be started again (14.3).


(2) is unit c1's rule: look a component up each time you use it, because a redeployed pool is a new object.


In jPOS 3. An eager-start="true" attribute starts a QBean right after its own init, for a provider that another bean needs during its init (jpos.org blog, October 2024). 2.1.7 does not have it.

Q2 Deploys Whatever It Finds in deploy/, Even Half a File


A switch creates one channel descriptor per row of its configuration table and writes each into the deploy/ directory of the running server. Q2 watches the directory (unit c1), and a new file starts a pass right away. We tried it with the cutover descriptor: we wrote the first 60 characters of 60_cutover.xml, flushed them, and wrote the rest a moment later:



Q2 parsed the file as soon as it appeared, failed at character 61, and renamed it. The writer then finished its work in the renamed file. So the .BAD file holds a complete, valid descriptor, and whoever opens it to find the error finds none. A large descriptor copied with cp, or written by a slow script, can be read half-written in the same way.


Write the file in a directory outside deploy/ on the same file system, and move it in. Within one file system a move is a rename, so Q2 sees either no file or the whole one. With ATOMIC_MOVE, a move that would have to copy across file systems throws AtomicMoveNotSupportedException instead:




Q2 has a method for writing a descriptor, deployElement(element, fileName, encrypt, isTransient). It writes the JDOM element in place with a FileWriter, so it has the same exposure once Q2 is watching: call it before q2.start(), or write and move the file yourself. With isTransient true, it adds the running Q2's instance id to the root element and deletes the file when the JVM exits. If the JVM dies before it can, the next Q2 finds an id that isn't its own and deletes the file instead of deploying it, so a crash can't leave yesterday's channels behind for the next start. Summary


  • A value nobody set is absent, and absent means the default. A missing property, a misspelt name and an unresolved ${...} all leave a @Config field at its initialiser and make get return "". A value with no safe default gets no default, and the code refuses its absence.
  • Refuse a configuration in setConfiguration. Q2 then renames the file .BAD. Refused in initService, the bean stays Unknown, can't be started, and only one warning shows it. A Failed start can be retried.
  • <attr> is set through JMX. Its setter belongs in the bean's MBean interface, or the file is .BAD. A value changed over JMX lasts until the next redeploy.
  • A QBean looks for what it needs in startService. Within one pass every init comes before every start. The file order decides which start comes first, and a wait holds up every later start.
  • Q2 deploys whatever it finds. Write a descriptor elsewhere and move it into deploy/. Transient descriptors carry the instance id and don't survive their run.

running() is true in Starting and Started; a loop in your own thread tests it (unit c11).


@Config in 2.1.7: fills String, int/Integer, long/Long and boolean/Boolean fields, in the class and its superclasses, private ones included. A field of another type, a double for instance, is left alone without a word. A value that doesn't parse (count="seven" for an int) fails the deploy with NumberFormatException, so the file is .BAD. The TransactionManager configures participants the same way, so @Config works on them too.


Booleans: true and yes, in any case, are true; everything else is false.


${...} forms: ${name} and ${name:default} (the lookup order is in unit c1), $env{name} the environment only, $sys{name} system properties only, $cfg{name} the environment file only, $verb{text} the text as written. After a ${...} resolves, a value starting file:: is replaced by that file's content (file::/run/secrets/db-password) and one starting obf:: is de-obfuscated. Obfuscation is not encryption. A literal file::... that isn't the result of a ${...} stays as it is.


Repeated properties resolve once. getAll writes the resolved values back into the stored array, so the first call fixes them, and an entry that didn't resolve then is dropped for good.


Other sources of configuration:

Deploying from code and from jars: deployElement (14.6); descriptors on the class path under META-INF/q2/deploy/ are deployed as transient services at start-up, so a jar can start services you didn't write; a file containing <shutdown/> stops Q2.


Challenges


These have no single answer.


  1. Write a check, run in your build, that deploys every descriptor of deploy/ with an empty environment and fails when any QBean is not Started. Which beans can't pass it without a database or a host, and what do you do about them?
  2. The settlement job needs the pool and the cutover service, and the cutover service needs the pool. Choose prefixes and waits, and say what happens on a restart when the pool's descriptor is .BAD.
  3. An operator raised graceSeconds through JMX on one of two nodes. How do you find out that the two nodes now close the day at different times, and what would make that impossible?
  4. Your switch generates 40 channel descriptors at start-up from a table. Compare transient descriptors written before q2.start() with descriptors kept in the repository. What does each cost when a row changes during the day?


Design Note: Why Does Q2 Keep Running When a QBean Fails?


A Spring application context that can't create one of its beans refuses to start at all. Q2 does the opposite: it deploys every file it can, renames the ones it can't, and leaves a bean that fails in init or start with a warning and a state.


Q2 is built for servers that change while they run. Files are added, touched and removed in deploy/ without a restart, and each change is a pass of its own. If a broken descriptor stopped Q2, one bad file copied into a running switch would take every link down with it. So a failure stays with its own file and its own bean, and the channels, servers and transaction managers beside it keep working.


You pay for that with the checking. Q2 can't know that a missing time is fatal for one bean and harmless for another, so only your code can make the difference visible, by refusing early (14.3). A server that started can still have .BAD files and beans that are not Started; after every deploy, look for both, as DeployRun does.
