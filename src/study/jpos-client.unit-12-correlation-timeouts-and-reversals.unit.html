A terminal sends a 0200 for 50.00 and waits. Ten seconds pass and nothing comes back. The cardholder is still at the counter, and the merchant asks: did the bank take the money?

Nobody knows. The request may not have arrived, or the host declined it, or the host approved it and the answer got lost. What jPOS does while you wait for an answer, and what you must do when the wait ends with nothing, comes down to six rules, one per section heading from 12.2 to 12.7.

A Host You Can Break

QMUX never touches a socket. It writes each request to a Space queue (<out>) and reads responses from another one (<in>). The ChannelAdaptor of unit c4 moves messages between those queues and the wire. Put something else on the far side of the two queues and QMUX can't tell the difference.

A Response Finds Its Request Through a Key

QMUX has sent the 0200 for terminal 29110001 with STAN 123, and a thread is blocked in request. A message arrives on <in>. How does QMUX know that this is the answer?

It turns the message into a string, the key, and compares it with the string it made from the request. Here is mux.getKey(m) for five messages, all for terminal 29110001:

The 0200 and the 0210 give the same string. From left to right: the out queue and a dot, three digits of the MTI, field 41 padded to 16 characters, field 11 padded to 6 digits. Because of the padding, a host that echoes 000123 for a STAN sent as 123 still matches.

A request and its response differ in the MTI, so QMUX keeps only what the two have in common:

  • The fourth digit gives the message's origin and whether it is a repeat, so it is dropped. An 0421 has the same key as its 0420.
  • The third digit is 0 for a request and 1 for its response. QMUX maps both to the even value before building the key, so 0200 and 0210 meet. A 0220 (an advice, see 12.5) keeps its 2, so it never answers a 0200. The mapping is <mtimapping>, and you almost never change it.
  • The out queue is part of the key, so two links never confuse each other's traffic.

A message with none of the key fields can't be matched, so QMUX refuses to send it. Here is an 0800 echo with only field 70 set:

Give every network message a STAN.

QMUX computed its key, found nobody waiting, and handled it like any message it never asked for, such as the host's own 0800. It offered the message to its <request-listener>s and, since none took it, put it on the <unhandled> queue, where it expires after two minutes. With neither configured, the message is silently dropped.

The host approved that purchase, and the program was told null. Section "No Answer Means You Don't Know" deals with that.

Only One Request per Key Can Wait

Suppose two requests with the same key were waiting at once. A response arrives and matches both. QMUX can't tell which one it belongs to, and one cardholder's approval could be reported on another's purchase.

So QMUX checks before it sends. While a request waits, QMUX keeps a marker for its key (the key plus .req), and a second request with the same key is refused and never sent:

The exception isn't the bug. The bug is whatever made two live requests share a key. Because the refused request was never sent, it is safe to give it a fresh STAN and send it again.

Spot the Problem: The Gateway at Lunchtime

A gateway accepts purchases from three hundred terminals and forwards them to the acquirer's host through one QMUX. The host knows the gateway as a single terminal, so the gateway puts its own ID in field 41:

It passes every test. In production, around noon, the log fills with Duplicate key and a few terminals time out. Can you see why?

With field 41 the same on every message, line (1) reduces the key to the MTI and the STAN, and the STAN is still the terminal's own. Every terminal counts its STAN from 1, so sooner or later one of them sends a STAN that another terminal's request, still waiting, already uses. A test lab with one terminal never sees it.

On the upstream link the gateway is the sender, so the gateway numbers the messages: one STAN sequence per outbound link. It replaces the terminal's STAN on the way up and puts it back into the response on the way down. The other option is to add a field to the key that is unique per transaction and that the host echoes, such as the retrieval reference number: <key>41, 11, 37</key>.

Other ways to get the same collision:

  • a STAN counter per thread or per terminal, when several of them share one link;
  • network messages without field 41 that share STANs with each other;
  • a repeat (0421) sent while the previous attempt is still waiting. That one is covered in 12.7.

Choosing the Key Fields

<key> sets the fields for every MTI. <key mti="08"> sets them for every MTI that starts with those two digits. Whatever you choose, the host must echo each key field unchanged. A field it rewrites or drops gives a response that matches nothing, and every request times out.

Every Timeout Guards a Different Wait


A customer asks for links that never time out. Their network is reliable, they say, and disconnects only cause trouble.


Between you and the host sits a firewall that silently drops sessions after 15 idle minutes: neither side receives anything.


  • On the client, jPOS still believes it is connected. The next purchase is written into the dead connection and never arrives. The ChannelAdaptor has already taken it off its queue, so it is not sent again, even after a reconnect. request returns null, and you are in the situation of 12.5: a purchase whose outcome you don't know.
  • On the server, the terminal reconnects on a new session. The old session stays open forever, because nothing will ever arrive on it and nothing is waiting to notice. Every quiet night adds a few more. Weeks later the QServer reaches its session limit and refuses new connections, and only a restart brings it back.


A read timeout (the channel's timeout property) closes dead sessions on the server and makes the client reconnect before the next purchase. An echo every few minutes (unit c11) keeps a healthy but quiet session from looking dead, and from being dropped by the firewall. So: echo interval < read timeout < firewall idle time, for example an echo every 5 minutes, a read timeout of 6 and a firewall at 15.


The request timeout, the second argument of mux.request, guards a different wait: the cardholder's. Size it from the outside in: whoever calls you (the terminal, the upstream switch, a REST client) has a limit of its own, and your timeout must end first. If the terminal gives up at 30 seconds and you wait 45, a host approval at 40 seconds becomes a payment the terminal has already shown as failed.


The Reference lists every setting with "timeout" or "alive" in its name, what it waits for and what happens when it fires.

No Answer Means You Don't Know


When request returns null, one of three things happened, and the client can't tell which:


  • the request never reached the host;
  • the host received it and declined it;
  • the host approved it, moved the money, and the answer was lost or arrived too late.


The obvious fix is to send the 0200 again. Against a host that answers the first try 1.5 seconds late:




The cardholder paid twice. The test host, like many real ones, doesn't look for duplicates, so the second 0200 is just another purchase. A host that does check might decline it as a duplicate, and then you have told the cardholder "declined" for a purchase that went through.


The safe move is a reversal: a message that says "if you approved this, undo it". If the host never saw the original, or declined it, the host acknowledges the reversal and nothing changes. If the host approved it, the money comes back. A resend double-charges in exactly the case a reversal fixes: reverse, never resend.


What gets reversed depends on what the message did:


  • 0100 and 0200 ask for permission and move money or place a hold. When their outcome is unknown, they are reversed.
  • Advices (0120, 0220, 0420) report something that has already happened. There is nothing to undo, so they are repeated (0121, 0221, 0421) until the host acknowledges them.
  • 0800 network messages change no balance. Just send a new one.


Once the purchase is reversed, the late approval from 12.2.1 needs nothing more.


A Reversal Points Back at the Original


A reversal must tell the host which transaction to undo. In ISO 8583:1987 that is field 90, Original Data Elements. A builder, with the per-link STAN sequencer it uses:




We reverse the purchase from 12.5, which went out as STAN 000125 at 1105143000 from acquirer 123456, with a track 2 in field 35:



Field 90 is easier to read split up:



The reversal has its own STAN (000126), because it is a new message on the link. If it carried the original's STAN, a host that detects duplicates by terminal and STAN would take it for a second copy of the original. The original's STAN is in field 90, where the host looks for it.


It copies only what the host needs. Track 2, the PIN block and the chip data (fields 35, 52 and


  1. don't belong in a message that may sit in a queue for hours.


The builder works from the original request, so store each request before you send it.


Networks differ. Some want 0400 instead of 0420, some want the original STAN in field 11, and many want a reason code. These change the builder; the rules of this unit stay the same.

A Reversal Must Outlive the Process and Wait Its Turn


A reversal that exists only in memory disappears with the process, and the cardholder's money stays with the merchant until someone notices. It also can't be sent just once: the link may be down, or the host may not answer. It needs a store-and-forward queue (SAF), here on a Space queue:



We queue two reversals and let the host drop the first two attempts:




(1) Stored first. The reversal goes into the queue before the payment service reports "reversed" to anyone. In production the space is persistent (je:saf is the Berkeley DB space that ships with jPOS). Here one process queues a reversal and exits, and the next one reads it:



(2) Read, don't take. The reversal stays in the queue while it is being sent. If the process dies in the middle of request, the reversal is still there after the restart. Take it out first (inp), and a crash at the wrong moment loses it for good.


(3) One try at a time. request returns only when this attempt is over, and synchronized keeps a second sender out. So the next attempt, an 0421 with the same key as the 0420, never overlaps the previous one, which would be a duplicate key (12.3).


(4) A repeat only after a real attempt. The MTI becomes 0421 only after an 0420 has actually gone out. When the link was down, nothing was sent, and the reversal is still a first attempt.


(5) Push, not out. The repeat goes back to the front of the queue. With out it would go to the back, and the reversal for 000127 would overtake it. During a long outage the oldest reversal, the one a cardholder has been waiting for the longest, would keep being pushed back.


In most networks any answer acknowledges the reversal, whatever field 39 says, because the host has seen it (check your network's spec for codes that ask for a retry). Don't quietly delete a reversal the host never answers: alert someone when it has been retrying longer than the network allows. The queue holds PANs, so protect it like the transaction database.

Summary


  • A response finds its request through a key made of the out queue, the MTI without its last digit (with the response digit mapped down) and the key fields. A field the host doesn't echo unchanged breaks every match.
  • Only one request per key can wait. "Duplicate key" means something upstream let two live requests share a key. The usual cause is a STAN that isn't numbered per outbound link.
  • Each timeout guards its own wait. The request timeout must end before the caller gives up. Servers need a read timeout, and echoes must come more often than it fires.
  • null means unknown, and unknown means reverse. Resending turns a lost answer into a double charge.
  • A reversal is a new message with its own STAN, pointing at the original through field 90.
  • A reversal is stored before anyone is told, read rather than taken while it is sent, repeated only after a real attempt, and kept at the front of the line.


Reference

<mtimapping> has three strings, one per MTI digit. The default is 0123456789 0123456789 0022446689.

Challenges


These have no single answer. Work them out on paper or with the test host.


  1. Your network requires an answer to a 0200 within 25 seconds, your terminals give up after 30, and the host occasionally answers at 28. Pick a request timeout. What happens to the purchases the host answers between your timeout and second 28, and who pays for them if nothing is done?
  2. Run the duplicate-key example with 300 terminals behind the gateway, each picking a random STAN for each purchase, and 20 purchases in flight at any moment. How often does a collision happen? Compare your measurement with the birthday problem.
  3. Two gateway instances share one upstream link and both send through it. How do you keep their STANs unique without a shared counter, and what does your scheme cost when one instance restarts?
  4. The SAF stores whole reversals, PANs included. Design a SAF that stores only a reference to a row in the transaction database. What gets simpler, and what new way of failing did you add?


Design Note: Why Not a Transaction ID?


Many systems give each transaction a unique ID and pass it everywhere. ISO 8583 doesn't. A message identifies itself by who sent it (fields 32 and 41), a short sequence number (11) and a timestamp (7). Everything in this unit follows from that choice: keys built from several fields, duplicate keys when the sequence repeats, and field 90 to point back at an original.


A transaction crosses several institutions that share no database and no clock, over links each of them operates separately. A global ID would need an authority that all of them trust to hand IDs out. A six-digit counter per link needs nothing: each sender numbers its own messages, and the link plus the date make the number unique enough. Terminals with very little memory could do that, and nobody had to agree on anything beyond the format.


The price is paid at every hop that relays messages. A switch has to renumber each message for its own outbound link and remember the mapping to restore the original numbers on the way back. That is the gateway problem from 12.3.1, and the fix there was the standard's own answer.


Field 37, the retrieval reference number, is the closest the 1987 standard comes to a transaction ID, and the acquirer assigns it. Networks add their own trace identifiers in private fields. You will meet both. Neither replaces the per-link STAN for correlation.
