Your server authorizes Visa purchases. Next month it takes Mastercard as well: Mastercard purchases must carry fields 48 and 61, they go to another host, and the Visa path, which works, must not change. The quick way is an if on the card number in each participant that differs. A year later six participants have one, one of them tests pan.startsWith("5"), and every Mastercard that starts with a 2 is declined at the counter with 15, "no such issuer".

jPOS puts brand rules in the descriptor instead. A participant called a group selector names a group of participants declared in the TransactionManager, which runs that group for this one transaction. Six rules, one per section heading, route each card to its brand's checks and network.

Networks differ. The field lists here illustrate the mechanism. The real requirements are in each network's specifications.

Every output comes from jPOS 2.1.7 run as unit s4 runs its server: Q2 deploys the unit's descriptors in the same JVM, and unit s4's DirectTerminal hands each request to a real IncomingListener, with no socket. The purchases come from terminal 29110001. An answer line names the request, then shows the answer's MTI, response code (39) and STAN (11).

A Selector Names a Group, and the Group Runs Where the Selector Stands

The server's TransactionManager:

The <group> elements don't run on their own. A participant that implements GroupSelector names them, with one method more than a plain participant:

After the selector's prepare, the TransactionManager calls select, puts the named group's participants into the chain right after the selector, and carries on with the rest of the chain. The selector here is jPOS's Switch. It reads the Context entry named by txnname, here DESTINATION, and returns the property of that name, or the unknown property when there is none. SelectDestination, one step earlier, set DESTINATION by comparing the card number with its <endpoint> ranges (5.2). Approve stands in for unit s4's authorizer and approves whatever reaches it. Decline answers every request with its rc. RequireFields (5.4) declines a request that lacks one of its fields, and AnswerFailures (5.5) answers failures that other participants only reported.

Six purchases, one at a time:

In what order did the participants run for the second purchase, the Mastercard without field 61?

The group ran where Switch stands, before Approve, although the file declares it at the end. RequireFields:mastercard aborted, so Approve never ran (after an abort only abort participants are asked, unit s4), and SendResponse sent the 30 that RequireFields had put in the Context. The name after the colon is the descriptor's realm, which tells the Visa and Mastercard instances of RequireFields apart in the log.

A selector may return several names, separated by spaces or commas, and their groups run in that order. With <property name="visa" value="visa contactless"/> and a contactless group holding one more RequireFields:

The selector also selects on the abort path. The card with a bad check digit:

CheckFields aborted, so neither SelectDestination nor Switch was prepared. The TransactionManager still called Switch's select, because its call-selector-on-abort property is true unless you set it to false. With no DESTINATION in the Context, Switch fell back to unknown. The Decline in that group is a plain participant, so it was skipped, and the 14 came from AnswerFailures. Abort participants in the selected group would have been asked, which is what the setting is for: a brand's group can carry its own work for failed transactions. A selector you write can therefore have select called when its own prepare never ran, and must cope with a Context that holds nothing it put there.

The BIN Table Is Configuration, and the Most Specific Range Wins

The leading digits of a card number, the BIN (bank identification number), say which network and which issuer it belongs to. SelectDestination maps them to destinations: 4 means every number that starts with 4, 51..55 every number that starts with 51 to 55. The opening's bug as configuration is <endpoint destination="mastercard">5</endpoint>:

The test card 2223000048400011 is a Mastercard: Mastercard also issues numbers from 2221 to

  1. With the range written as 5, the card is unknown and is declined with 15 before any issuer sees it. It works in every other shop, the bank has no record of the attempt, and your log shows an ordinary decline.

The ranges come from the networks' BIN tables, and they overlap. Say the acquirer also issues BIN 411111 and handles its own cards in-house ("on us"): <endpoint destination="onus">411111</endpoint> beside the 4. At deploy, SelectDestination logs its table in the order it tries it:

Each range is widened to 19 digits, and the number in front is 19 minus the digits you wrote, so the range written with the most digits is tried first, whatever the order of the <endpoint> lines. "Most specific" means exactly that: 4000..4999 is tried before 41, although 41 is the narrower range. The test card 4111111111111111 now goes to onus:

It was declined with 15 all the same: Switch has no onus property, so it fell back to unknown. A new destination needs an <endpoint>, a Switch property and a group.

A Name With No Group Behind It Runs Nothing

A month after Mastercard went live, the network's monthly report lists your approvals that carried no field 61, which the mastercard group requires. The production descriptor's Switch:

The trail of a Mastercard purchase without field 61:

The TransactionManager looked up a group named mastercad, found none, and added nothing: no deploy error, no exception, no abort. The one sign is the WARNING inside the transaction's event, and a server that sets debug to false to keep the log small logs no event per transaction. With debug off, the same purchase was approved with 00 and left no line in the log.

Skipped checks cost the network's fees or rejections, and a skipped forwarding step means the purchase never reaches the network.

To prevent it:

  • Make the warning mean a bug. Back every name you intend with a group, an empty one if nothing should run. Then any not configured line is a mistake, and a log alert can look for it.
  • Test each brand through the real descriptor. A test that sends each brand a request missing one of its fields, and expects a refusal, fails the day the typo is made.

A Stock Participant Reports a Failure, and an Abort Participant Has to Answer It


CheckFields, first in the chain, checks the request against two lists, mandatory and optional, of field numbers and names such as CARD or PCODE, and puts what it parsed into the Context (the Reference lists the names). When something is wrong it records the failure in the Context's Result (ctx.getResult()) and votes ABORTED, but builds no response. SelectDestination works the same way, and so does QueryHost when its MUX is missing or not connected.


Without AnswerFailures in the chain, the card with a bad check digit and the Visa purchase with field 12 get this:



Unit s1's rule, that a refusal must leave a response in the Context, applies to jPOS's own participants too, and they leave that response to you. Each terminal waits out its timeout, often 30 seconds at the counter, then treats the purchase as unknown and reverses it (unit c12).


One abort participant near the end of the chain answers whatever the stock participants reported:



It does nothing when an earlier participant has already answered, as RequireFields and Decline do. In 5.1 it gave bad-check-digit its 14 and visa-with-12 its 30. Unit s10 grows this mapping into the server's error handling.


The 30 for visa-with-12 comes from allow-extra-fields, which is false unless you set it: a field in neither list is a failure (EXTRA_FIELD). A field listed by number is checked only for being there, never for its format; only named entries such as PCODE get a format check. Field 12, the local time, is in neither list above, so a terminal update that starts sending it turns every purchase from those terminals into a 30. The strict lists catch garbage, at the price that a terminal change needs a server change first: add 12 to optional.

A Network That Doesn't Answer Has Not Declined


So far the server decides by itself. An acquirer forwards each purchase to its brand's network instead, from the brand group. jPOS's QueryHost sends REQUEST through the MUX registered as mux. plus the DESTINATION, and puts the answer in the Context as RESPONSE. A forwarding server's visa group:



Approve is gone from the main chain, and a QMUX named visa is deployed beside the TransactionManager. Unit c12's test host sits on that QMUX's queues in place of the Visa network. It answers the first purchase and drops the second. With continuations at its default, true, QueryHost waits with PAUSE (unit s4), so no session is held while the network decides.



The second purchase's trail:



It matches the first purchase's trail line for line; only the event's elapsed, 2005 ms instead of 8, differs. When the two seconds ran out, QueryHost recorded HOST_UNREACHABLE in the Result and resumed the transaction, still PREPARED, so nothing aborted. AnswerFailures does nothing on the commit path, and SendResponse found no RESPONSE, so it sent nothing.


The network got the purchase and may have approved it. If it did, the issuer holds the amount on the cardholder's account for a purchase the terminal showed as failed, and the cardholder has paid another way.


A missing answer has to fail the transaction. One participant after QueryHost in the group does it:



With it, first with the network silent, then with the network's link down (the QMUX has a <ready> element, and nothing ever sets that key):



Every purchase without an answer gets 91, "issuer or switch inoperative", from AnswerFailures. For the network the two cases differ. A silent network received the purchase, and only a reversal (unit c12) undoes an approval it may have given. With the link down, QueryHost waited a second for it, recorded the same HOST_UNREACHABLE and voted ABORTED without sending anything, so there is nothing to reverse. CheckHostAnswer is a plain participant, so with QueryHost's defaults it runs only after the request was actually sent, and its ABORTED branch is the place to queue the reversal. (With ignore-host-unreachable set, QueryHost lets a request it never sent go on as prepared, and that no longer holds.)


Keep QueryHost's timeout (2 seconds here) below the terminal's (6), as unit c12 requires. QueryHost never waits less than one second.


Forwarding as is. QueryHost sends the terminal's message unchanged and returns the network's answer unchanged. A real acquirer renumbers each message for its upstream link and restores the terminal's fields on the way back, as the gateway of unit c12 does.

Summary


  • A selector names a group, and the group runs where the selector stands, before the rest of the chain. select is called on the abort path too, where only the group's abort participants run.
  • The BIN table is configuration. SelectDestination tries the most specific range first. A table that says Mastercard is 5 declines every 2-series card with 15.
  • A name with no group runs nothing. The TransactionManager warns inside the transaction event, which debug off removes. Give every name a group, and test each brand through the descriptor.
  • Each <participant> element is its own instance. Its configuration belongs in instance fields. A static field lets the last element configured set the rules for all of them, and an empty list must stop the deploy, not check nothing.
  • Stock participants report; an abort participant answers. Without one, a refused card leaves the terminal waiting until it reverses.
  • No answer from the network is not a decline. With continuations, QueryHost resumes a timed-out transaction as prepared. Fail it after QueryHost, answer 91, and reverse what was sent.

Challenges


  1. Your acquirer adds Maestro, whose BINs overlap some Mastercard ranges, and Maestro purchases need a PIN. Write the <endpoint> lines, the Switch properties and the groups. Which test tells you the overlap went the right way?
  2. Write a startup check that fails the deployment when a Switch property names a group the TransactionManager doesn't have. What can it read, and from where?
  3. Visa and Mastercard want different response codes for the same failure. Where does the difference go: in AnswerFailures, in a group's abort participant, or somewhere else? What does each choice cost when a third brand arrives?
  4. The network answers at second 2.5, after QueryHost gave up at 2. Trace that answer through the QMUX of unit c12 and decide what your server should do with it.


Design Note: Why Groups in the Descriptor?


The brand rules could live in Java, as one participant with a switch on the brand. In the descriptor, operations can read which checks run for Mastercard without reading code, and a new network reuses participants that are already tested.


The price is that the descriptor is a program the compiler never sees. In Java, a misspelt brand name in a switch is at least a constant a search can find, and a missing class doesn't compile. In the descriptor, a Switch property that names nothing is accepted and does nothing (5.3), so the checking moves from the compiler to tests that run the real descriptor, one brand at a time.
