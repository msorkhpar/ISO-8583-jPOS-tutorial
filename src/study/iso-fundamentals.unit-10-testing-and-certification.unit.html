Your acquirer has booked two three-hour sessions on the card network's test host and sent the network's script: 52 cases, from an approved purchase to the reversal of one whose answer never came. In the first session case 9 fails. The analyst says your amount arrived as 000000015.00. Your log says 15.00. Who is right, and what should have been true before the session started? Six rules, one per section heading.

Networks own their certification programmes and change them. This unit covers what most host certifications share and reproduces no network's specification; your network's current documentation and your acquirer contact decide what you must test.

Certification Proves One Host Link Against One Network's Specification

Three things get certified:

  • The terminal and its chip software. EMVCo approves the card reader (level 1) and the EMV kernel (level 2). Each network then tests the terminal together with the acquirer's host behind it, using its own test cards (level 3).
  • The host interface. An acquirer, processor or switch shows that its messages follow the network's specification: the fields each MTI carries, how they are encoded, how reversals and advices behave, and how sign-on, echo and key exchange work. This is the certification an ISO 8583 developer usually takes part in.
  • Security. PIN handling, key management and the systems that hold card data are assessed under separate PCI programmes, such as PCI PIN and PCI DSS (unit 13). None of them tests messages.

A processor whose terminals run an approved EMV kernel, and which passed its last PCI DSS assessment, is about to connect to a second network. Does any of that count?

None of it covers the new link. The kernel approval is about the terminal, the assessment about how card data is kept. Even a host certification with the first network says nothing about the second, because each hop is a link of its own with its own specification (unit 7): its own header, private fields and encodings (units 5 and 6). The network switches on live traffic only after its own script has passed on its own test host.

Your Own Suite Runs Every Case Before the Test Host Sees One

A host certification usually runs like this:

  1. The network sends its message specification and a test script: cases such as "approved purchase", "purchase with wrong PIN", "reversal of an approved purchase", "echo test", each with what you send and what must come back.
  2. You connect to the network's test host, over a VPN or a leased line, with test keys and test cards the network supplies.
  3. You run the cases, often while an analyst watches the network's side, and you keep the evidence of each one (10.5).
  4. The analyst reviews the results. Failed cases are fixed and run again, in a later session.

A bug found in a session costs a second session. Sessions are booked weeks ahead and last a few hours, and the test host is sometimes down or behaves differently between sessions. A packager error found with the analyst watching ends the useful part of the session; every later case waits for the next booking.

So the whole script runs against your own simulator of the network, on every build, before the first session. Unit c10 shows this in jPOS with stand-ins inside the tests, unit c16 with a simulator that runs beside the system and grades every field of each case, and unit s11 for the server side. When the simulator and the test host disagree, the test host's answer is the one that counts: find out why, then fix the simulator.

A functional suite proves that each case gets the right answer. It says nothing about a few hundred transactions a second against a slow database. Load tests are a separate job (unit c10).

A Case Is a Request Template and Every Field Its Answer Must Carry

A case from a script, written as data a program can run:

It has four parts. The setup names what the case needs: a card the host declines, a host that answers late. The request is a template, and the fields that must be unique per message are generated each time it runs. The expectation grades the answer field by field: the MTI, field 39, the fields that must come back unchanged (11, 37, 41), and the fields that must be there or must not (38 present on an approval, absent on a decline). The side effect is what has to happen next, here a reversal.

Keeping each case as a recorded message and replaying it unchanged fails on the second run: the STAN and field 7 repeat what the host already saw, and a host that checks for duplicates answers 94, duplicate transmission. The case then tests the duplicate check instead of the purchase.

Grading on field 39 alone fails too. Say the host you certify is an issuer's, and it answers an approval with a STAN of its own instead of the request's. Field 39 says 00, and your suite passes. In production nothing pairs that answer with its request (unit 4): the acquirer times out and reverses a purchase your host approved.

A Test Card Is Issued for Testing, and the Luhn Check Only Says It Is Well Formed

The network issues its own test cards for certification, sometimes physical chip cards, with keys and expected results that match its test host. For your own suites this course uses two numbers that payment processors publish for testing, 4111111111111111 and 5555555555554444.

Both pass the Luhn check: the last digit is computed from the others, so that one mistyped digit, or most swaps of two neighbours, can be refused before the number goes anywhere. jPOS computes that digit with ISOUtil.calcLUHN, and a number is valid when its last digit is the one computed from the rest:

The check digit says nothing about who the card belongs to: real cards pass it too.

A made-up number usually fails the check, and the host answers 14, invalid card number, before anything the case was meant to test has run. A number generated under a network's prefix with a correct check digit passes, and it may be a real cardholder's. Your own card, used "just once" to see whether the link works, is worse: once a real card number is in a log, a hex dump or a ticket, every copy of it is card data under PCI DSS (unit 13).

    • Only cards issued for testing go to a test host; the Luhn check digit only catches typing errors, and a real card number in a log puts every copy under PCI DSS.

The Evidence Is the Bytes That Left, Kept as Text and Found by STAN


The code that built case 9, cut down to the fields that matter, then what the team's masked log kept and the bytes that left:




The analyst is right. The log shows the message as the program built it, and the packager padded the short value to twelve characters on the way out without checking that it holds digits (unit 3). The network's host read 000000015.00 as an amount and refused it with 13, invalid amount.


So keep a hex dump of every message, from every session, as text. Text can be pasted into a ticket and read back into bytes (unit c17 does it in jPOS); a screenshot can't. Number the messages with one increasing STAN per link, wrapping after 999999 (unit c12), so that the analyst's "STAN 000731" finds the same message in your logs.


The dump also shows field 2 in clear. Masking applies to the log, not to the bytes, so a dump is safe to hand over only because the card in it is a test card.


The Certified Build Is the One That Goes Live


A month after certification, a team upgrades its ISO 8583 library and changes the definition of one field in its packager, "to tidy it up". Neither touches the business logic. Must the network know?


The network certified bytes, and either change can alter them. Unit 1 packed one message with two packagers and got two different messages. A field that is now padded on the other side, or whose length prefix now counts bytes instead of characters, goes live untested, and the network rejects every message that carries it. Your own suite may not notice: a simulator built on the same library changes with it.


Certify a specific build, and deploy that same build to the test host and to production; only the host, the port and the keys differ, in configuration kept per environment. After a change to the library version, a packager definition or the channel, ask the network whether you must certify again.


Summary


  • Certification proves one host link against one network's specification. An EMV approval, a PCI assessment or another network's certification does not cover it, and the network switches on live traffic only after its own script passes.
  • Your own suite runs every case before the test host sees one. Test-host sessions are scarce, and a bug found in one costs another session. A functional suite is not a load test.
  • A case is a request template and every field its answer must carry. A replayed message repeats its STAN and tests the duplicate check; a case graded on field 39 alone passes answers nothing can pair with their requests.
  • A test card is issued for testing. The Luhn check only catches typing errors. A real card number in a log or a dump puts every copy of it under PCI DSS.
  • The evidence is the bytes that left, kept as text dumps and found by STAN. The log shows what the program built, not what the host received.
  • The certified build is the one that goes live. A library, packager or channel change can change the bytes, so ask the network before you ship it.

Challenges


  1. The network's script has 52 cases and you get two three-hour sessions. Which cases would you run first in the first session, and why?
  2. Your simulator approves a purchase that the network's test host declines with 05. Before you change the simulator, how do you find out whether the simulator or your reading of the specification is wrong?
  3. A tester needs 2000 distinct card numbers for a load run against your own simulator. Where do they come from, given what 10.4 says about generated numbers?
  4. Your team ships a new build every week. Which changes would you agree with the network to announce, and which would you treat as needing a new certification?


Design Note: Why the Network Tests Your Messages


The network publishes its specification, so why doesn't it trust you to read it? Because the specification is prose and tables, and two careful teams read it differently: whether a length counts bytes or characters, whether an optional field may be absent or must be sent empty, what an advice's answer must echo. Each reading is reasonable, and only one matches the network's own code. A test host that runs that code settles the question once, before thousands of members send live traffic to it.


The price is that the test host becomes the only judge, and it is scarce. That is why the script belongs in your own build: the session can only confirm what your simulator already shows, and the simulator is right only as far as you have read the specification right.
