A purchase on terminal 29110001 was declined, and a support engineer attaches the host's log line to a ticket for the terminal vendor. It holds field 2, the card number, in full; field 35, the card's track 2; field 52 as sixteen hex digits; and field 64. The vendor replies that field 52 is encrypted, so nothing secret is in the ticket, and asks what field 64 is for when the link already runs TLS.

The vendor is wrong on both counts. What protects a card message, and what each protection leaves open, comes down to seven rules, one per section heading.

Track Data, PIN Blocks and Security Codes Are Never Kept, and a Card Number Only Unreadable

A card message carries two kinds of card data. The card number identifies an account. The track, the card security code and the PIN block prove that the card, or its holder, is present. Once the purchase is answered, the second kind has done its job and is deleted. The card number may be kept in a form nobody can read, encrypted for example, and is shown only masked:

ISOUtil.protect keeps the first six digits, which name the issuer's range, and the last four, which the cardholder recognises. On a track it also blanks everything after the =, the expiry date and service code included.

FieldHoldsAfter the answer
2card number (PAN)keep only unreadable (encrypted, truncated or tokenised); show masked

55chip data (may hold the PAN, and track-equivalent data in tag 57)keep only what clearing needs, never tag 57

Why delete what is encrypted? Track 2 is enough to write a working magnetic stripe. Copied with it into a new magnetic-stripe purchase, the encrypted PIN block of the same purchase can pass the issuer's PIN check without anyone knowing the PIN, until its key changes. The ticket holds both, and under PCI DSS, the card industry's security standard (unit 13), it is card data, as are its backups, the mail that announced it and every other copy.

jPOS can mask these fields in its log (unit c8). Unit s9 stores a card number so that it can be found again without being readable.

A PIN Block Mixes the PIN With the Card Number Before It Is Encrypted

Field 52 is 8 bytes. The PIN pad builds them from the PIN and the card number, as ISO 9564 format 0 says, and encrypts the result at once:

  • the PIN field: 0 for the format, the PIN length as one hex digit, the PIN, and F up to 16 digits;
  • the PAN field: 0000 and the 12 rightmost digits of the card number, without its last digit, the check digit;
  • the block is the PIN field XOR the PAN field.

PIN 2468 on the two test cards, before encryption:

The same PIN gives a different block on each card. To read it, the issuer's hardware security module (HSM, 8.4) decrypts the block, XORs in the PAN field of the message's card number, and checks for a 0, a length from 4 to 12, that many digits and F fill. A block moved to another card's message fails the check or yields another PIN.

Format 0 Gives the Same Block Every Time, So Format 3 Adds Random Fill

Encrypting takes a key. This class does triple DES on one 8-byte block, with a double-length key:

The same cardholder enters PIN 2468 on card 5555555555554444 for two purchases. Under the test key 0123456789ABCDEFFEDCBA9876543210 (the X9.24-1 test key of 8.5, used here as a PIN key), what does field 52 carry each time?

A format 0 block depends only on the PIN and 12 digits of the card number, so under one key the same PIN on the same card always sends the same field 52, and so do two cards whose 12 digits agree. Whoever learns the PIN behind one block, or watches field 52 in a log, recognises it in every equal block without the key.

  • Format 3 fills the PIN field with random digits from A to F instead of F, so every purchase sends a different block. The reader ignores the fill, beyond checking that it is A to F.
  • Format 1 fills with random digits and leaves the card number out. It is for devices that don't know the card number, and its block isn't tied to a card.

The PIN pad and the receiver must agree on the format; after decrypting, the receiver checks the first digit before it reads anything else.

Format 4. For AES keys, ISO 9564 adds format 4: a 16-byte block in which the PIN field and the card number are combined by encrypting, XORing and encrypting again. Field 52 holds 8 bytes, so a network that adopts it says where the block goes.

In jPOS 2.1.7. The security module reads ISO formats 0 and 1 under its own constant names (FORMAT01 is ISO format 0), and has neither format 3 nor 4. Unit c7 shows this in jPOS.

Problem statement

The certification lab runs a test issuer. Its software security module decrypts each field 52 and passes the clear block, with the card number of the message, to PinBlockReader.pin, which returns the PIN the cardholder typed. The issuer then compares that PIN with the test card's own.

The lab's devices are a mix: the older PIN pads send ISO format 0, the new ones format 3, and one ATM vendor's test machine sends format 1, often without knowing the card number. Nothing else is in use, and a block in any other format is refused.

A reader that gets a block wrong does one of two things, and both cost certification time. It returns a PIN where it should have refused the block, so a wrong PIN can be approved; or it refuses a PIN the cardholder typed right, and the vendor goes hunting for a bug in a pad that works.

Every Key Is Encrypted Under the Key Above It, and Known by Its Check Value


No whole key, whether for PINs, for MACs (8.6) or between institutions, is ever stored in clear. Each is kept encrypted under the key one level up:


  • the LMK (local master key) sits at the top, inside a hardware security module (HSM), and never leaves it. Every other key the system stores is a cryptogram under the LMK, usable only by handing it back to the HSM;
  • key-encrypting keys protect keys in transit: a ZMK (zone master key) between two institutions, a TMK (terminal master key) between a host and one terminal;
  • working keys protect the data and change often: a ZPK or TPK for PIN blocks between institutions or with a terminal, a ZAK or TAK for MACs;
  • a BDK sits at the top of its own branch: DUKPT (8.5) derives PIN keys from it.


A ZMK is created once, in a key ceremony. Two or three people each bring one clear component, and the HSM XORs them into the key, so no single person ever knows it. Working keys then travel under the ZMK, usually in an 0800 key-change message; the field depends on the network.


How do two parties check that they hold the same key, without showing it? Each computes its check value (KCV): a block of zeros encrypted under the key, of which the first 3 bytes are kept.



Our ceremony, and the same one with the third digit of the first component typed as 3 instead of 2:



jPOS's software security module, given the same components, accepted both and reported the same two check values; only the check value shows the difference.


If nobody compares ABBBE6 with the other institution's D8F119, every working key imported under this ZMK is wrong, and every PIN purchase fails at the issuer with a PIN-block error. Compare check values after every ceremony and key change, never the key's bytes: under two HSMs' LMKs the same key has different bytes.


DUKPT Gives Every Purchase Its Own Key, Derived From a Serial Number Sent Beside the PIN


An acquirer with a hundred thousand PIN pads would need a hundred thousand PIN keys, each loaded and changed separately. DUKPT (Derived Unique Key Per Transaction, ANSI X9.24-1) needs one secret per group of pads, the base derivation key (BDK).


Each pad is loaded once with an initial key, derived from the BDK and the pad's key serial number (KSN). The KSN is 10 bytes: a key set ID, the pad's ID, and a 21-bit counter that the pad advances for every PIN. Each PIN is encrypted under the key that belongs to the current counter value, and the KSN travels with it, in clear. The host's HSM derives the same key from the BDK:



Three purchases with PIN 1234 on one pad, using the standard's published test BDK 0123456789ABCDEFFEDCBA9876543210 and test card number 4012345678909:



These are the standard's test vectors, and jPOS's software security module, given the BDK and each KSN, reads 1234 from all three blocks.


The same clear block went out under three keys, so DUKPT also hides equal PINs. The KSN is no secret: without the BDK it yields nothing. Each step is one-way, so a key taken from a pad today doesn't give the keys of its earlier purchases. The BDK, though, unlocks every pad loaded from it, so it exists only inside HSMs: the acquirer's, and the one at the facility that loads the pads.


Networks differ. The network decides where the KSN travels: field 53, a private field or a chip tag. AES DUKPT (ANSI X9.24-3) derives AES keys with another algorithm and a longer KSN.


A MAC Proves the Bytes Were Not Changed, and Hides None of Them


A message authentication code (MAC) is 8 bytes computed from the message and a key that the sender and receiver share (a ZAK or TAK). The receiver computes it again; if the two differ, the message was changed or came from someone without the key. It goes in the message's last field: field 64, or field 128 when a secondary bitmap is present (unit 2).


With triple-DES keys most networks use ISO 9797-1 MAC algorithm 3, the ANSI X9.19 retail MAC:



The data is padded with zero bytes to a multiple of 8. Each 8-byte block is XORed into the result so far and encrypted with single DES under the key's left half (1), so the result depends on every byte. Steps (2) and (3) bring in the right half once, at the end, so the MAC depends on all 16 bytes of the key while the long chain runs at single-DES cost.


The X9.19 test vector first, then a purchase of 45.00, packed as ASCII ISO 8583:1987 (unit 3), and the same purchase after someone on the way changed field 4 to 450.00:



Without the key, whoever changed the amount can't compute the matching MAC, so the receiver refuses the message. Without a MAC, the altered message is well-formed and the host approves 450.00.


The last line shows the bytes the MAC was computed over, with the card number masked for print. A MAC hides none of them.


Compare a received MAC with MessageDigest.isEqual, which takes as long whether the MACs differ in the first byte or the last. A comparison that stops at the first difference tells an attacker how many leading bytes they got right.


Networks differ. Each network's specification says which bytes are MACed (often the packed message up to the MAC field, with the MAC's bit already set), how they are padded, and how many bytes of the MAC are sent.

TLS Protects One Connection, and the PIN Block and the MAC Protect the Message


TLS encrypts one connection. At its end, often a load balancer in front of the host, the bytes come out in clear, and the message is logged, queued and passed to the next link in clear.


The PIN block stays encrypted throughout: each party translates it from the incoming key to the outgoing key inside its HSM, and the clear PIN exists only in there. The receiving application checks the MAC with the key it shares with the sender, which proves that no load balancer, queue or program in between changed the message. TLS adds what those two lack: the rest of the message, the card number included, is unreadable on the wire. A link to a network typically uses all three; units c3 and s3 set up TLS in jPOS.


In the opening's ticket, fields 35 and 52 together let someone repeat the purchase with its PIN check, field 2 had to be masked, and field 64 tells the host that the message is the one its sender MACed.

Summary


  • Track data, PIN blocks and security codes are never kept, and a card number only unreadable. An encrypted PIN block kept beside a track lets a copied purchase pass the PIN check.
  • A PIN block mixes the PIN with the card number before it is encrypted. Format 0 XORs the PIN field with 12 digits of the card number, check digit excluded; a PAN field shifted by one digit breaks PIN purchases on almost every card.
  • Format 0 gives the same block every time. Equal PINs on a card show as equal field 52 values to anyone without the key; format 3 adds random fill.
  • Every key is encrypted under the key above it and known by its check value. Compare check values after every ceremony and key exchange; a mistyped component is otherwise accepted.
  • DUKPT gives every purchase its own key. The host derives it from the BDK and the KSN in the message, so the BDK must stay inside HSMs.
  • A MAC proves the bytes were not changed, and hides none of them. Compare it in constant time.
  • TLS protects one connection. The PIN block and the MAC keep protecting the message where TLS has ended.

Challenges


  1. Your log must help support find a purchase without holding card data. Which fields would you keep, in what form, and how would support find all purchases on one card?
  2. Your terminals send format 0 and the network asks for format 3. Where can the conversion happen, and what does each party need to change?
  3. Your PIN pads are loaded from one BDK. Estimate how many pads, and how many years of PINs, depend on it, and decide when you would replace it and how.
  4. A partner proposes MACing only fields 2, 4, 11 and 41 instead of the whole message. Which changes to a message would then pass unnoticed, and do any of them matter?


Design Note: Why the Keys Live in a Box


Everything on this page could run in the application: the triple DES, the XOR and the derivation are a few dozen lines of Java. The standards put them in an HSM instead, a device built to erase its keys when tampered with, and let the application hold only keys encrypted under the HSM's LMK.


The application then reads no PIN at all; it asks the box, through a narrow set of commands: translate this block from key A to key B, check this MAC, import this key. A breach of the application yields cryptograms that are useless without the box.


Every PIN and every MAC is then a call to the HSM, which needs capacity and a spare. Each HSM model has its own commands, so the application needs an adapter per vendor; jPOS has one interface for all of them (unit c7). And the keys at the top of the hierarchy enter the box only through ceremonies with people, components and check values.
