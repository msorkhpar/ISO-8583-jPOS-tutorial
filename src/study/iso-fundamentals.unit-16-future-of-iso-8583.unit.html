A new partner processor offers three ways to connect: its ISO 8583:1987 link, "the same messages as JSON" over a socket, and ISO 20022 "in the coming years". The team likes JSON. A colleague adds that with a request/response API the reversal queue can go. The bank behind the partner asks when the card link moves to ISO 20022. Five rules, one per section heading. Every output is from jPOS 2.1.7.

Another Syntax Changes the Packager, Not the Messages

One 0800 echo goes out three times: through XMLChannel and ASCIIChannel with jPOS's XMLPackager, then through ASCIIChannel with the 1987 ASCII packager. A socket prints the bytes that arrive:

The packager turns the message into bytes; the channel only marks where one message ends. XMLChannel reads lines until the closing </isomsg>, and ASCIIChannel puts a length, four digits by default, in front of whatever the packager produced, XML included. A partner who wants XML behind a length header needs no new code, only a different pair in the channel's configuration (unit c3). jPOS 2.1.7 ships XMLPackager and XMLChannel but no JSON packager. JSON on a link means one class that implements ISOPackager, paired with a channel whose framing the partner agreed to.

A JSON 0200 means what it meant in unit 4: with no answer, its outcome is unknown. A team that drops the reversal queue because the new API "answers every request" resends or forgets that purchase on the first timeout, and the cardholder pays twice, or pays for a sale the merchant reported as failed. Reversals, advices, the response codes of unit 9 and the certification of unit 10 depend on the messages, not the syntax. That is why JSON lives at the edges: a web API in front, ISO 8583 to the network, and a gateway that maps between them (unit 12).

Editions. The 2023 edition keeps the MTI, the bitmap and numbered fields, and builds more fields from datasets (unit 17). The edition of a link is a packager definition, chosen from the network's specification; jPOS 3 adds dataset packagers (unit s13).

JSON Has No Type for Fixed-Width Text or Raw Bytes

Your host sends its 0210 answers to the partner as JSON, written by a mapping that types every all-digit value as a JSON number. The partner's parser reads each number back as text, and its system packs the result for the 1987 link to its terminals:

A JSON number has no width, so its leading zeros are gone before the message leaves. The numeric fields 3, 4 and 11 come back only because the 1987 packager pads numbers with zeros on the left. Fields 37, 38 and 39 are alphanumeric, padded with spaces on the right. The response code 00 arrives as 0 , which is in no network's table, so the terminal shows a decline while the issuer holds the funds. The retrieval reference number no longer matches the one in your records, and a reversal or a dispute that quotes it finds nothing.

A PIN block put into a JSON string as text is corrupted:

Six of its eight bytes don't form valid UTF-8 sequences, and each became the three-byte replacement character. The host's security module gets 20 bytes where it expects 8, and the PIN can't be verified.

So every value travels as a JSON string, character for character, and a binary field as hex with a marker the other side reads, such as a b after the field number, the convention of an unfinished JSONPackager kept in the jPOS 2.1.7 sources. Build the text with an encoder that escapes " and \: a merchant name with a quote in it otherwise ends the string early.

Problem statement

A partner processor takes your authorization requests and sends its answers as JSON over a socket, one object per message. Its system reads each object with an ordinary JSON parser and packs the fields for its own 1987 link to the networks, so whatever a field holds when it leaves you must be exactly what the partner's side reads, for every field a 0100 or a 0110 can carry. Both sides' test messages use the same kinds of value as production, including PIN blocks, chip data and merchant names as merchants type them.

JsonPackager in src/main/java/com/example/practice/JsonPackager.java is a working ISOPackager: it writes one member per field and reads such an object back with a small JSON parser of the same kind the partner uses. Three methods are left, marked TODO:

  • name: the member name a field travels under;
  • jsonValue: the value written after the colon;
  • put: setting one member that was read back into the message.

The partner already sends text fields as members named by the field number, as the first test shows. About fifteen lines in total.

An XML Parser That Accepts a DOCTYPE Reads Files for the Sender


jPOS 2.1.7 has two XML packagers. XML2003Packager extends XMLPackager, reads field 72 as binary, and changes three settings of the XML parser. A partner sends this echo request, and each packager unpacks it on a host where a file called keys.properties sits in the working directory:



Can you see what happened? The first line declares an entity whose value is the content of a file, and field 48 refers to it. XMLPackager refuses any document with a DOCTYPE. XML2003Packager turns that check off in its constructor, "for backward compatibility", so the parser opens the file and puts its content into field 48. A server that answers echoes by cloning the request sends field 48 back to the sender. An entity can point at an internal URL just as well.


Message text is input from another system, even on an authenticated link, so the parser has to refuse DOCTYPE declarations and external entities. Use XMLPackager, and if you need another format, subclass it without turning those features back on.


In jPOS 3. Version 3.0.2 stops XML2003Packager from re-enabling DOCTYPE declarations and external entities (unit s13).


ISO 20022 Models the Business First, and It Carries Account-to-Account Payments


ISO 20022 isn't a message format but a method for defining financial messages. It has a business model of the parties, accounts and amounts involved, message definitions built from that model, and syntaxes that represent them: mostly XML, with JSON and ASN.1 also defined. A registration process adds new messages and elements, and the same dictionary serves payments, securities, trade and cards. A message names its parties, the purpose of a payment and its remittance information in structured elements, where ISO 8583 has numbered fields of fixed meaning and private fields for the rest.


It has become the main standard for account-to-account payments in most high-value and real-time gross settlement systems, instant payment schemes, and cross-border payments between banks, which have largely moved off the older SWIFT MT messages. ISO 20022 also defines card messages, from the acceptor to the acquirer and from the acquirer to the issuer. Card authorization between acquirers, networks and issuers is still overwhelmingly ISO 8583. This changes faster than course material, so check the networks you connect to.


A card platform planned around an ISO 20022 link that your networks don't offer needs a translation layer you can't certify with them.


A Bridge Between the Standards Decides, Field by Field, What the Other Side Lacks


A gateway that receives both standards translates between them. Amounts are the easy part. ISO 20022 writes an amount as a decimal with the alphabetic currency code:



ISOCurrency gives both the number of decimals (unit 12) and the alphabetic code. The other direction is harder. An ISO 20022 message names the merchant in structured elements; the 1987 field 43 has 40 characters for the name and location:



The packager refuses the message on the first merchant with a long name. Someone has to decide what to cut, and how the network wants the name, the town and the country laid out in 40 characters. Going the other way, a translation into ISO 20022 has to find data that an ISO 8583 message never carried, such as a structured address, or decide to leave it out.


Write the mapping field by field with the other party. Map through your internal format so each side needs one mapping (unit 12). Test it with real messages from both sides, then certify it like any other interface.


Carrying instead of translating. Version 3 of the jPOS Common Message Format, an early draft at the time of writing, reserves field 114 for a complete ISO 20022 document carried beside an ISO 8583 message, so a switch can pass both without a translation layer.

Summary


  • Another syntax changes the packager, not the messages. In jPOS the packager encodes and the channel frames; reversals, advices, response codes and certification come along unchanged.
  • JSON has no type for fixed-width text or raw bytes. Digit fields typed as numbers lose their zeros, so 00 arrives as 0 ; bytes put in as text are corrupted. Every value is a string, and binary fields travel as hex.
  • An XML parser that accepts a DOCTYPE reads files for the sender. XML2003Packager in 2.1.7 resolves external entities; XMLPackager refuses them.
  • ISO 20022 models the business first and carries account-to-account payments. Card authorization between acquirers, networks and issuers stays on ISO 8583 for now.
  • A bridge decides, field by field, what the other side lacks. The packager refuses what doesn't fit; the mapping, agreed with the other party, decides what is cut or added.

Challenges


  1. A partner wants your messages as JSON over HTTP instead of a socket. What does HTTP give you that a channel doesn't, and what does a timeout on POST mean for a 0200?
  2. Design the JSON names for a message with a nested field, such as a field 127 with subfields. How does a reader tell a subfield from a field, and a binary value from a text one?
  3. Your switch must accept XML from a partner whose messages carry a DOCTYPE they won't remove. What would you accept, and where would you check it?
  4. Pick one ISO 20022 element that has no ISO 8583 field, such as a structured remittance reference. Where could a 1987 link carry it, and who has to agree?


Design Note: Why ISO 8583 Outlives Its Replacements


ISO 8583 has often been called obsolete. Its syntax was never what kept networks on it. A card network is a contract between thousands of institutions about what an approval, a reversal and an advice mean, how long each side waits, and who pays when an answer is lost. Every member has built and certified systems against that contract, and a new syntax would make each of them do it again for little new behaviour.


ISO 20022 was adopted where it brought something the old formats lacked, such as structured data about the parties of a credit transfer. Card authorization already had its answers in ISO 8583, extended by private fields and now by datasets. The cost is the translation between the two standards, paid by each gateway and bank that works in both.
