  16. Design Note: Why a Packager Is Built From Small Parts

The acquirer's new link is binary: numbers travel as BCD, two digits to a byte. You took the acquirer's field table, copied jPOS's iso87binary.xml, changed the rows that differed, and wrote round-trip tests. They all pass. On the first day of certification every keyed purchase goes through, but swiped purchases are declined for some cards with "invalid card data". The same cards work on the old ASCII link, and nothing on your side reports an error.

The seven rules, one per section heading, cover how a packager turns a message into bytes, how to build one from a specification, and how to find the wrong field when the bytes disagree. Every output is from jPOS 2.1.7.

The Bytes Carry No Field Boundaries, Only the Packager Knows Them

A packager is a list with one field packager per field number. To pack, it writes the MTI with entry 0, the bitmap with entry 1, then each field that is present with its own entry, in ascending order, back to back. The acquirer's echo test, written as that list in Java:

The bytes 00 00 01 at offset 0x17 are field 11. How would the host know that?

The bitmap says which fields are present, not where they start. The host finds field 11 at 0x17 only because its own list says that field 7 is ten BCD digits, five bytes. A host whose list differs in one field reads every field after it from the wrong place (13.7).

The format is all in the packager, and the two ends of a link agree on it only by building the same list from the same specification. jPOS's stock Java packagers (ISO87APackager, ISO87BPackager and the others) fill such a list in a constructor like the one above.

A Field Packager's Name Spells Out the Specification's Row

A specification describes each field in one row: n 12 for a twelve-digit amount, n..19 LLVAR for a PAN of up to 19 digits behind a two-digit length, b 64 for eight bytes, plus a note on how digits and characters travel. jPOS has a class for almost every combination, and its name spells it out: IF, the encoding, _, the length rule, the type. Four values, each packed by the classes a specification might ask for:

The PAN, a terminal ID and a PIN block are packed the same way as the amount.

  • The letter after IF is the encoding. A writes ASCII digits, characters and lengths, one byte per digit; bytes behind an ASCII length (IFA_LLLBINARY) stay raw bytes. B writes BCD for numbers and lengths, two digits per byte. E writes EBCDIC, where 0 is F0 and a space is 40. A plain IF_ copies characters as they are, with no length prefix.
  • The middle part is the length rule. Nothing means fixed length, padded to it (zeros on the left for numbers, spaces on the right for text). L, LL, LLL and LLLL mean a variable length with a prefix of that many digits.
  • The last part is the type: NUMERIC or NUM for digits, CHAR for text, BINARY for bytes.

B means BCD, not "binary data". Bytes are the BINARY part, and IFA_BINARY writes them as hex text: the eight bytes of a PIN block become sixteen characters. The stock iso87ascii.xml does this with field 52 (unit c6). A host whose specification says b 64 for field 52 reads the first eight characters as the PIN block, and every field after it from the wrong place.

Classes Are Combinations, and You Can Make Your Own

Most of these classes are three small parts put together: a padder that fills a fixed field, an interpreter that turns characters into bytes, and a prefixer that writes the length. In the 2.1.7 sources, IFB_LLNUM is NullPadder + BCDInterpreter + BcdPrefixer.LL, and IF_CHAR is RightTPadder.SPACE_PADDER + LiteralInterpreter + NullPrefixer.

When no stock class has the combination a specification asks for, combine the parts yourself. Say a host wants the merchant's city as variable text with a BCD length and EBCDIC characters:

04 is the BCD length and D6 E2 D3 D6 is OSLO in EBCDIC. The no-argument constructor is for the XML: GenericPackager creates the class named in class= with it, then sets the length and name from the attributes.

A Length Prefix Counts Digits or Bytes, and Only the Specification Says Which

The PAN row says n..19 LLVAR, BCD length. IFB_LLNUM writes the sixteen digits of 4111111111111111 as 16 followed by eight bytes: the prefix counts digits. IFB_LLCHAR writes the same PAN as 16 followed by sixteen ASCII characters: there the prefix counts bytes. Both have a BCD length, and both look right to someone reading "LLVAR, BCD length".

Suppose our packager picked IFB_LLCHAR and the host uses IFB_LLNUM. The host unpacks a purchase for 25.00:

The host read 16, took sixteen digits (eight bytes) as the PAN, and started field 3 in the middle of our PAN, so its amount is 313131313100 and its STAN 000000. Nothing threw. unpack stopped after the last field in the bitmap and returned 39 of 47. The eight bytes left over produce only a log warning, and only if the packager has a logger.

On a real host this purchase fails the PAN check and comes back as a format error or an invalid card, so someone notices. When the misread fields pass the checks, the host records a value you never sent.

A prefix also limits the length. A field packager for text or numbers refuses a value longer than its length (unit c2). One for bytes doesn't:

Three hundred bytes of chip data go out in a field limited to 255. A hundred bytes behind a two-digit BCD prefix go out with the length 00, and the host reads an empty field followed by a hundred bytes of nonsense. In the 2.1.7 source, ISOBinaryFieldPackager.pack checks the length only for fixed fields. Check variable binary fields yourself before you set them.

An Odd Number of BCD Digits Needs a Filler, on the Same Side at Both Ends

BCD puts two digits in a byte. 301 has three, so it needs two bytes and one filler nibble, and the filler can go on either side: 03 01 or 30 10. The class name doesn't say which; the pad argument does (pad="true" in the XML puts the filler on the left).

Our layout had pad="true" on field 35, the track 2 data, which is what declined the swiped purchases. The acquirer's has pad="false", as iso87binary.xml does. Two cards, packed by us and read by the host:

A track 2 with an even number of characters has no filler, so that card works. One with an odd number gets the filler in front. The host expects it at the end, so it reads our filler as the first digit and drops our last digit. The card number it sees is the seventeen digits 05555555555554444, and it declines. Whether a track 2 has an odd length depends on what the issuer wrote on the stripe, so it looks like a card problem, not a packager problem.

On a fixed field the mistake is just as quiet. Field 70 301, packed with the filler on the right and read with the filler on the left, arrives as 010:

In the stock binary layouts, fixed numeric fields put the filler on the left and variable ones (the PAN, track 2) on the right. Your specification decides. Only values with an odd number of digits show it, so a twelve-digit amount never will.

BCD has no letters. BCDInterpreter turns each character into a nibble by subtracting the character 0. The track 2 separator = gives the nibble D, as the specifications intend. A letter gives a number too big for a nibble, which can change its own digit and the one next to it. A literal D in a track 2 string from a terminal becomes 4:

The separator is gone, with no error. Normalise track 2 to = before you set it. jPOS's GenericValidatingPackager has a validate method that checks field contents against validators declared in its XML, but in the 2.1.7 source pack never calls it, so your code would have to.

A Round Trip Can't Check the Layout; the Specification's Sample Can

The test that passed before certification day:

It uses the 33-character track 2 that the host misread. Why did it pass?

Line (1) compares what our packager wrote with what our packager read. A packager that puts the filler on the wrong side puts it there both times, and reads it back correctly. A round trip catches a packager that can't read its own output, not one that departs from the specification, because the specification isn't in the test.

Most specifications include sample messages as hex, the specification's own bytes. A test built from one checks your layout against theirs:

Both tests, run once with the acquirer's layout and once with ours:

The sample test:

  • reads bytes someone else wrote, so a wrong prefix or filler shows up as a wrong value;
  • checks that the whole sample was used. unpack returns the number of bytes it read, and 13.3 showed a misread that leaves bytes over without an error;
  • packs the message again and compares the bytes, which catches a difference that reading hides, such as a different filler value.

To build a packager for a new link:

  1. Copy the closest stock layout (iso87ascii.xml, iso87binary.xml, iso93ascii.xml or iso93binary.xml, all inside the jPOS jar) into your project under a new name.
  2. Change every row whose encoding, length rule, length or filler differs from the specification.
  3. Write one test per sample message, before you connect to anything. If the specification has no samples, ask the host for a hex trace of each message type you send and receive.

  1. Coding practice

    Build the regional switch's layout from its field table

    • An odd number of BCD digits carries a filler nibble whose side is the pad setting, and both ends must agree; only odd-length values are affected.
    • A field packager's class name gives the encoding, the length rule and the type of a specification row; B means BCD, and IFA_BINARY sends bytes as hex text.
    • A BCD length prefix counts digits for numeric fields and bytes for text and binary fields, and the wrong choice can misread a message without an error.
    • A round trip can't find a wrong layout because the packager reads back what it wrote; a test from the specification's sample bytes, checking values, bytes used and bytes repacked, can.

The XML Names the Same Classes, and Is Read From the Classpath


GenericPackager reads the list from an XML file. Each isofield names a field packager class and its arguments, so the XML says what the Java constructor in 13.1 says and packs the same bytes. The acquirer's layout, cut down to the fields this unit uses:



Prefer the XML for a real link. It can be compared with the specification's table row by row, and changing a row needs no Java.


Field 48 is the sub-field form from unit c6, with a bitmap of its own: sub-field 0, named by bitmapField="0", is an eight-byte bitmap, so sub-fields can be left out. A message with sub-fields 1 and 3 and no 2:



Field 48 is 0012 (twelve bytes follow), the bitmap A000000000000000 (bits 1 and 3), ECM, then 06. With emitBitmap="false", as in unit c6, every sub-field is always written, in order.


Where the File Comes From


The name you give GenericPackager (or the channel's packager-config property) is read in one of two ways. With the jar: prefix, the rest is a resource on the classpath: the stock files inside the jPOS jar, or yours under src/main/resources/packager/. Without it, the name is a file path, relative to the directory the JVM was started in. The same layout loaded both ways, from the project directory and then from /, the way a service manager often starts a process:




On a server that starts the process from somewhere else, the plain path fails, the channel can't be configured in Q2, and the link never comes up. Use jar: and ship the layout inside your jar, versioned with the code that depends on it.


GenericPackager validates the file against the DOCTYPE, so it is required. Its http address is never fetched: jPOS resolves it to a copy of the DTD inside its own jar, so loading works offline.


An Unpack Error Points Past the Field That Is Wrong


When the host's answer won't unpack, the exception names a field, and that field is usually fine. Two echoes in the stock ASCII layout, whose sender wrote field 11 with five digits instead of six, then with seven:




The first error names field 70, which is fine. Field 11 took six characters, the five it had and the first digit of field 41. Field 41 started one character late, and field 70 ran out of bytes. The fields read before the failure are still in the message, and the first one with a wrong value, field 11, is where the fault is.


The second echo raises no error. Every field after 11 is read one character early, field 70 comes out as 130, and one byte is left over. Your code gets an echo with code 130 and answers it as an unknown code.


When an unpack fails, or succeeds with odd values:


  1. Find the first wrong value among those read, in field order. Ignore the field the exception names.
  2. Check that field's row against the specification: encoding, length rule, length, filler.
  3. Compare the bytes used with the bytes received. Bytes left over mean a misread even when nothing threw.
  4. Turn the bytes into a test (unit c17 shows how to get them from a dump or a log) and fix the layout until the test reads every field as the specification says.


If the first bytes don't look like an MTI, look at the channel first. A length header or a TPDU that the channel didn't strip (unit c3) shifts every field, the MTI too.

Summary


  • The bytes carry no field boundaries. A packager is a list of field packagers, and the receiver finds each field only by applying the same list. One differing field misreads every field after it.
  • A field packager's name spells out the row: the encoding (A, B, E), the length rule and the type. B means BCD, not binary data, and IFA_BINARY sends bytes as hex text.
  • A length prefix counts digits or bytes. In jPOS a BCD prefix counts digits for the NUM classes and bytes for CHAR and BINARY; the specification says which the host means. The wrong choice can unpack without an error and leave bytes over. Variable binary fields don't check their maximum.
  • An odd number of BCD digits has a filler, and its side is the pad setting, the one part of a row the name leaves out. A wrong side breaks only values with an odd number of digits, so it looks like a problem with particular cards.
  • A round trip can't check the layout, because the packager reads back what it wrote. A test built from the specification's sample bytes, checking every value, the bytes used and the bytes packed again, can.
  • The XML names the same classes and packs the same bytes. Load it with jar: from the classpath, because a plain path depends on where the process was started.
  • An unpack error names a field after the wrong one. Find the first field whose value is wrong, and treat bytes left over as an error.

What a field packager checks in 2.1.7: text and numeric fields refuse a value longer than their length. Fixed binary fields refuse any other length. Variable binary fields check nothing, and a BCD prefix too short for the length silently drops its high digits. None of the field packagers on this page checks content: a letter in a BCD field becomes a digit.

isofield attributes: id (field number; 0 the MTI, 1 the bitmap), length (fixed length, or the maximum of a variable field; for a bitmap, its largest size in bytes), name (shown in logs and errors), class (the field packager), pad (BCD filler on the left when true), token (for tagged-field packagers). isofieldpackager adds packager, usually org.jpos.iso.packager.GenericSubFieldPackager, and takes the isopackager attributes for the inside of the field.


Packagers that are not wire formats: XMLPackager writes a message as the <isomsg> XML that dump prints. It suits simulators, test fixtures and links between your own components, never a card network.


Challenges


These have no single answer.


  1. Your specification has no sample messages and the host team takes a week to send traces. What can you test about your layout in the meantime, and what can't you know until the traces arrive?
  2. Take iso87binary.xml and the acquirer's table, and decide for each difference whether a sample with typical values would reveal it. Which differences need a sample built for the purpose (an odd-length field, a maximum-length field, every optional field present)?
  3. A host sends EBCDIC text but BCD numbers, and one of its fields is a BCD length followed by EBCDIC text. Write that layout. Which rows need a class of your own, and how do you test that class on its own?
  4. A gateway reads messages from terminals with one layout and sends them to the host with another. Which fields can change their bytes on the way through without changing their value, and which values can't survive the trip at all?


Design Note: Why a Packager Is Built From Small Parts


jPOS could have described a field with data, {encoding: BCD, length: LL, type: numeric}, and interpreted it. Instead each combination is a class, and most classes are three small objects put together: a padder, an interpreter and a prefixer. A network that does something odd, like a BCD length in front of EBCDIC text, costs one small class and no change to jPOS. The same parts are reused across a hundred combinations, and a field packager keeps no per-message state, so one packager can serve every channel and thread.


The price is in the names. There are more than a hundred IF* classes in 2.1.7, and a name gives the encoding, the length rule and the type, but not the side of a BCD filler, which is a constructor argument, or whether a binary field checks its maximum, which is only in the source. A layout can look right row by row and still be wrong in a way that only bytes from the other side reveal.
