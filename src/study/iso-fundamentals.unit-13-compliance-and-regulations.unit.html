A gateway team prepares for its first PCI DSS assessment and lists the systems that hold card data: the jPOS switch and the transaction database. The assessor asks how the list was made, and then asks for the files behind the reversal queue. Every reversal from last night was answered, and the queue is empty. Is that disk part of the assessment, and was the list right?

What the card industry's standard and the data protection laws ask of a jPOS system comes down to seven rules, one per section heading.

Who decides. This unit is not legal or compliance advice. The PCI Security Standards Council (PCI SSC) publishes the standard and its guidance; those documents, your acquirer and your Qualified Security Assessor (QSA) decide what applies to you. The jPOS project publishes a free PCI DSS 4.0.1 compliance guide for jPOS-based systems on jpos.org, useful beside the council's documents.

PCI DSS Covers Every System That Touches Card Data, and Every System That Can Reach One

The Payment Card Industry Data Security Standard is written by the PCI SSC, which the card schemes founded, and the schemes enforce it through their contracts: your acquirer requires it of you. It applies to the cardholder data environment (CDE), the systems that store, process or transmit card data, and to every system that is connected to the CDE or can affect its security.

Pause on the team's list. The switch sends its log to a central log server. Administrators reach the switch through a jump host. A CI server builds and deploys it. Which of these are in scope?

All three. The log server receives whatever the switch logs, card numbers included if the masking is wrong. The jump host and the CI server hold no card data, but whoever controls them controls the switch: the CI server can ship a build that copies every card number it sees.

The team counted only systems that store card numbers, so the other three got no controls: no multi-factor login, no patching deadline, no log review. An attacker who takes the CI server takes the switch, and an assessor who finds the three reports a gap in the scope.

Every system in scope must meet every applicable requirement, so the most a developer can do for compliance is keep card data out of systems:

  • mask card numbers before a log line leaves the process (unit c8);
  • replace card numbers with tokens wherever the number itself isn't needed (unit 14);
  • cut the network paths, so that a system that holds no card data also can't reach one that does. The assessor will want to see that this separation was tested.

Card data that crosses an open network must be encrypted: unit 8 shows what TLS protects, and units c3 and s3 set it up in jPOS, where 2.1.7 checks certificates only when serverauth is set.

Versions. At the time of writing PCI DSS 4.0.1 (June 2024) is in force. Version 3.2.1 was retired in 2024, and the requirements that 4.0 introduced as "future-dated" apply since 31 March

A Card Number Is Recognised by Its Length and Its Check Digit

Teams know where card data is meant to be; a search finds where it is. A card number has 13 to 19 digits, and its last digit is the Luhn check digit of unit 10, which ISOUtil.calcLUHN computes:

Seven lines from logs and files, each with what the scan reported:

The masked number in the first line is no longer a run of digits. The request body kept by a retry store holds a card number. So do both tracks: the run ends at = or ^ and starts after the B of track 1. A pattern written with word boundaries (\b) would miss track 1, because B and 4 are both word characters. The order number has 16 digits and fails the check digit.

The last two lines are a retrieval reference number and a STAN run together, and one passes: the check digit passes one random run of digits in ten, and unit 14's tokens pass by design. A scan's hits are places to look at, not verdicts, and it reports them masked so that the report doesn't become one more store of card numbers.

Card Data Ends Up Where Nobody Meant to Store It


Unit 8 says what may be kept once a purchase is answered: track data, security codes and PIN blocks never, not even encrypted; the card number only in a form nobody can read.


The reversal queue of unit c12 runs on a persistent space, Berkeley DB (je:), so that reversals survive a restart. We built one reversal by cloning the whole purchase, and one from the fields a reversal needs, as unit c12's builder does. Each was queued and then taken out, as when the host answers. Then we scanned the store's data file with PanScan, once as it is and once with the top bit of every byte flipped, and also searched it for the track's expiry and the PIN block's bytes:



The queue is empty both times, and the file still holds the reversal; the clone shows two card numbers, field 2 and the one inside track 2. Berkeley DB appends to a log: taking an entry out appends a deletion, and the old bytes stay until its cleaner deletes the file. It does that only once most of the file is dead records, and never to the file being written, so a small queue in one file can keep them for a long time. Every backup taken in the meantime has them as well.


The plain scan found nothing because Berkeley DB's persistence API, which the je: space uses, stores a byte array with the top bit of each byte flipped, so that negative byte values sort before positive ones: the digit 4 (0x34) is written as 0xB4. A scan that reads only text would have reported this file clean. Scan each store in the form it writes, and test the scanner on a store you have filled yourself.


The cloned reversal kept track 2 and a PIN block on disk after the authorization was over, which unit 8 forbids, in a file nobody had listed, and in its backups. The reversal built from listed fields left only the card number, and that still has to be unreadable at rest, so the queue's disk and its backups are in scope either way.


The same thing happens wherever a message is kept "just for a moment": a retry store that keeps the request instead of its outcome (unit 12 keeps only the outcome), a log, a heap or core dump of a process that held messages, a capture from certification testing. The Reference lists them.


A Stored Card Number Names the Key That Opens It


Unit s9 stores card numbers encrypted with AES-GCM and finds them through an HMAC under a second key. Keys are replaced when your key policy's period ends, and at once when one may have leaked or a person who could reach it leaves. What happens to the million rows already encrypted under it?


If every row is encrypted under "the key", a rotation means re-encrypting every row at once, or leaving rows that no key opens. So each record carries the id of its key:



A card stored under pan-2025, then a rotation to pan-2026 and a second card stored under it. Each record is opened by the key its label names. Then a mislabelled record is simulated by giving the old record the new label, and finally the old record is re-encrypted under the new key:



New records use the new key at once, and old ones keep opening through their label while a background job re-encrypts them. When no record names pan-2025 any more, that key is destroyed, unless your policy keeps it for decryption only. Once it is gone, the old records in backups can no longer be read, which is also a way to erase them. A record under the wrong label is refused, because GCM checks a tag, so it never yields wrong digits. The HMAC lookup key is separate and doesn't change with the data key, so the index of unit s9 survives the rotation. Rotating the lookup key means computing every lookup value again.


Key management also needs:


  • Keys are never in code, in configuration in the repository, or in logs. Use an HSM or a key management service; otherwise a keystore whose password comes from the environment (unit s9).
  • PIN keys live only in an HSM, and the clear PIN only inside it (unit 8).
  • The keys that protect other keys need two or more people to rebuild, from separate components (unit 8): split knowledge and dual control.
  • A process holds its data keys in memory. Turn off core dumps and swap on the hosts in the CDE, and treat a heap dump as card data.

A Scanner Finding Is a Question, and the Answer Is Written Down


PCI DSS expects you to find and fix vulnerabilities in your code and in the libraries you ship. Two weeks before a certification, the dependency scanner marks a library that jPOS pulls in as critical. Do you upgrade tonight?


The scanner answers whether the component can be vulnerable somewhere, under some conditions. You need to know whether this system is exposed. Work through the finding in order:


  1. Is it confirmed? The scanner may have matched the wrong artifact or version.
  2. Is the vulnerable code reachable from your application at all?
  3. Is it exposed? Who can reach it from the network, and with what privileges?
  4. What does exploiting it require, and are those conditions present in your deployment?
  5. Which controls already apply: network separation, input validation, no untrusted XML?
  6. What does the change itself risk, close to a certification or a peak season?


Then decide. A finding that applies is patched now, or patched soon by overriding the vulnerable version in Maven's dependencyManagement instead of waiting for a jPOS release. When triage shows the finding doesn't apply to this system, it is deferred, with a written risk acceptance that names an owner, a review date and the event that would reopen it; closing it instead means nobody looks again when the exposure changes. A critical patch for a finding that applies is expected within about a month of its release, and a risk acceptance doesn't lift that.


A rushed upgrade or override can change serialization, TLS defaults or the classpath in the payment path a few days before certification. A deferral that lives only in someone's memory ("we never call that parser") is what an assessor writes up as a finding.


Every Identity in the CDE Is Personal and Limited, an AI Agent's Too


PCI DSS asks for a unique identity for every person and every process with access, rights limited to what each needs, and multi-factor authentication for all access into the CDE, for administrative access other than at the console, and for remote access from outside. On a jPOS node:


  • operators log in with personal accounts, never shared ones, and service accounts are separate from human accounts, with only the rights the service needs;
  • management interfaces (JMX, the Q2 command line, any web console) listen only on a management network and require a login;
  • the files under deploy/ and cfg/ are readable only by the service account and its administrators, because they name keys and endpoints;
  • every administrative action is logged, in logs that can't be changed afterwards.


An operator sets up an AI agent to read the switch's log every night and restart the channel adaptor when the link hangs. It runs on the operator's laptop, with the operator's SSH keys and VPN session. One night it reads a support ticket whose text tells it to copy a file to an outside address. Whose rights does it act with?


The operator's, all of them. Any text an agent reads can carry instructions (prompt injection), so an agent holding a person's credentials puts all they can reach within an attacker's reach. PCI DSS 4.0.1 says nothing specific about AI agents; its requirements still apply if you treat one as a privileged system component:


  • it runs on a dedicated host, with its own identity on each system it uses;
  • its credentials are read-only wherever possible, and a person confirms every change to production;
  • every tool call is logged with its time, tool, parameters (masked) and outcome;
  • the tool servers it calls, such as MCP servers, are software in scope: inventoried, scanned, and checking their inputs;
  • the model provider and the chat channel that carries its instructions become third-party service providers, and card data is masked before it reaches a model.


Data Protection Law Covers the Same Records and Can Ask for the Opposite


PCI DSS is enforced by contract; data protection laws are law, and cover all personal data, a transaction history included.


Under the EU's GDPR, a cardholder asks an acquirer to erase everything it holds about them. The card schemes, accounting law and anti-money-laundering rules require transaction records to be kept for years. Do you delete the rows?


Deleting them breaks the retention obligations; refusing the whole request may break the law. Deciding what is erased, and what is kept under which obligation, is the job of your legal and compliance team. The system's job is to be able to carry out their decision:


  • find every piece of data about a person, in logs, queues and backups too. The keyed lookup of unit s9 finds a card's encrypted records without storing its number in clear. A masked number can't: its six and four digits are shared by many cards;
  • keep identifying data apart from transaction data where you can, and pseudonymise with keyed values, not plain hashes, which unit s9 reverses in a quarter of a second;
  • make retention periods configuration, not code;
  • export a person's data, and erase what no retention obligation covers.


GDPR also asks you to keep only what a stated purpose needs: a switch rarely needs the cardholder's name once the purchase is answered. The Reference lists other laws; most share this core, and some countries also require payment data to stay within their borders.

Summary


  • PCI DSS covers every system that touches card data and every system that can reach one. A scope drawn around storage alone leaves the log server, the jump host and the CI server without controls; keeping card data out of systems is what makes scope small.
  • A card number is recognised by its length and its check digit. A scan confirms the scope, its hits are places to look at (one random run in ten passes), and its report is masked.
  • Card data ends up where nobody meant to store it. A reversal taken out of a Berkeley DB queue stays in the file and its backups, in a form a plain text scan misses; build reversals from the fields they need.
  • A stored card number names the key that opens it. New records use the new key, old ones open through their label until they are re-encrypted, and the lookup key rotates separately.
  • A scanner finding is a question, and the answer is written down. Triage it, then patch, override, or, when it doesn't apply, defer with a risk acceptance an assessor can read.
  • Every identity in the CDE is personal and limited. An AI agent gets its own host, identity and read-only rights, because whatever it reads can instruct it.
  • Data protection law covers the same records and can ask for the opposite. Legal decides between erasure and retention; the system must be able to find, export and erase a person's data.

Challenges


  1. Draw your own system's scope: the CDE, the systems that store, process or transmit card data, then every system that can reach it or affect its security. Which single change would take the most systems out of scope?
  2. Run a scanner like PanScan over a day of your logs and over a copy of each persistent store. How many hits are card numbers, and how would you cut the false ones without missing tracks?
  3. Your data key is rotated yearly and a table holds 200 million encrypted card numbers. How long does the background re-encryption take, and what does it lock while it runs?
  4. A cardholder's erasure request arrives for data that is also in last month's backups. What can be erased now, what only when the backup expires, and how do you show that it happened?


Design Note: Why the Standard Is Drawn Around Scope


PCI DSS doesn't ask whether a company is secure. It asks which systems are in scope and checks every requirement on each of them. That makes the work countable: an assessor can sample a system, look at its controls and write down what is missing. It also makes architecture a control: a system that never sees a card number, and can't reach one that does, needs none of the requirements.


The cost lands on the few systems that remain. A token vault holds every card number of every merchant behind it, and a network separation that keeps the rest out of scope has to be tested, because one forgotten route brings everything behind it back into scope.
