A shop's new terminals go live behind our client on a Monday morning. Purchases without a PIN are approved. Every purchase where the cardholder typed a PIN comes back declined with 39=55, incorrect PIN, and the cardholders insist they typed the right one:

The client copies field 52 from the terminal's request into the request it sends to the host. That field holds the PIN encrypted under a key that only the terminal and our client share, and nothing in the message says which key was used. The host tries its own key, gets nonsense, and declines.

What a client must do with PINs, keys, MACs and card data comes down to six rules, one per section heading. TLS on the link itself is unit c3's subject.

A Security Module on Your Desk

PINs and keys are handled by a security module. In production it is a hardware security module (HSM), a tamper-resistant box that holds the keys and does the cryptography itself. Your code talks to it through one jPOS interface, org.jpos.security.SMAdapter. jPOS's software implementation, JCESecurityModule, lets you develop and test without the hardware.

Three kinds of key appear below: a TPK (terminal PIN key) shared with a terminal, a ZPK (zone PIN key) shared with the host for PIN blocks, and a ZAK (zone authentication key) shared with the host for MACs. The module keeps every key encrypted under its own master key, the LMK. Here the software module is loaded with published test keys, so every output can be reproduced:

The host side is a test acquirer with its own module. It knows each test card's PIN, checks the MAC when the link requires one, and answers 00, 55 (incorrect PIN) or 63 (security violation). It signs its responses with the client's MacService from 7.5 and reads PINs with calls 7.2 and 7.3 explain:

Every output comes from jPOS 2.1.7 with no network. All but the Q2 deployment use these two classes, and messages carry the course's iso87ascii.xml packager. The opening's purchases went to a TestAcquirer that did not require MACs.

A PIN Block Means Nothing Without Its Key and Its Card Number

Field 52 is 8 bytes: the PIN, mixed with the card number, then encrypted.

The usual layout is ISO 9564 format 0. Write the PIN as 16 hex digits: 0, the PIN length, the PIN, and F padding. Write the card number as 0000 followed by its 12 rightmost digits without the check digit. XOR the two:

The clear block is then encrypted under a PIN key. PIN 1234 on the first card under the terminal's key and under the host's, and on the second card under the terminal's key:

The host holds only its own key. Which of the three can it read? Only the second. Recovering the PIN takes both the key and the card number. The module checks the decrypted block's structure (the leading 0, which its errors call the check digit, a length from 4 to 12, digits, F padding), so a wrong guess for either one usually fails outright:

The opening's host was in the last case: right card, wrong key, so its module found no valid PIN and it declined.

Mixing in the card number makes a block copied from one purchase useless on another card, and gives two cards with the same PIN different blocks. Someone who collects encrypted blocks can't match them up to find the cards whose PIN is 1234.

TLS can't do this job. It encrypts a connection, and at each end the bytes are decrypted into the process that receives them, which logs them, queues them and passes them on. A PIN block stays encrypted through all of that, past every hop, until it reaches a security module that holds the key.

Formats differ. Format 0 is the most common for terminals that read the card number, but the host's spec decides. ISO format 1 (SMAdapter.FORMAT05 in jPOS) uses no card number at all; ISO format 3, which adds random fill to format 0 and which PCI now prefers for new deployments, has no constant in 2.1.7's SMAdapter.

The Client Translates the PIN and Never Sees It

The client turns a block under the terminal's key into one under the host's key without decrypting the PIN itself. It asks the security module to translate the block: the module decrypts it, rebuilds it and encrypts it under the second key, all inside, and returns only the new block.

EncryptedPIN carries the block together with its format and the card number, from which it keeps the 12 digits format 0 uses. translatePIN takes the source key, the destination key and the destination format, which here stays format 0 (FORMAT01 in jPOS: the numbers in the constant names are not ISO's format numbers). The opening's two PIN purchases, on 4111111111111111 and 5555555555554444, translated:

The client's SecureDESKey objects are keys encrypted under the module's LMK: the client can store them and pass them around, but only the module can use them. With a hardware module, the clear PIN and the clear keys never exist in your process. The software module does the same work inside your JVM, which is why it is for development only.

  • Don't decrypt the PIN in the application and encrypt it again "because it is simpler". That puts clear PINs in your heap, your exception messages and your heap dumps. The card schemes' PIN security requirements allow a clear PIN only inside a secure device, so this fails a PIN audit.
  • Don't send the purchase without field 52 when translation fails. A block the module can't translate means the terminal and the client disagree about the key, or the block is damaged. Remove field 52 and the request becomes a purchase without a PIN, which the host may approve on a stolen card. Refuse the purchase locally instead and tell the terminal it failed.

Many terminals use DUKPT. Instead of one fixed PIN key per terminal, each PIN is encrypted under a key derived from a base key and a serial number the terminal sends along. SMAdapter has a translatePIN that takes the KeySerialNumber and the base derivation key; the rest of this section stays the same.

Keys Live Under the Module's Master Key and Are Known by Their Check Value


In a Q2 deployment, the security module is a QBean. org.jpos.q2.security.SMAdaptor creates the implementation named in impl, passes it the properties, and registers it under its name. Save this as deploy/05_hsm.xml, so it is deployed before the channels:



It names no logger: the module would log every call with its PIN blocks, keys and card numbers in hex, which ProtectedLogListener does not mask (unit s7). Code finds it with NameRegistrar.get("hsm"). With a hardware module, impl names the vendor's adapter class and nothing else in your code changes, because your code only sees SMAdapter.


On Java 17 the provider line is required. Without it, JCESecurityModule loads com.sun.crypto.provider.SunJCE by class name, which the JDK no longer lets outside code do. We deployed the descriptor twice in one Q2, once without the line:



The second one logs Unable to load jce provider whose class name is: com.sun.crypto.provider.SunJCE once, as a warning while Q2 starts. Q2 carries on deploying everything else, so the client connects and looks healthy. The first lookup of the module, typically in the first PIN purchase, throws NameRegistrar.NotFoundException. Opening the package with --add-exports java.base/com.sun.crypto.provider=ALL-UNNAMED gets the module started, but SunJCE doesn't have the module's default MAC algorithm, so every MAC fails instead:



Bouncy Castle comes with jPOS 2.1.7, so name it.


lmk is the file holding the software module's master keys, the LMK (local master keys). You create it once per development environment by starting a JCESecurityModule with rebuildlmk set to true, which overwrites any file already there. Keep it out of the repository, and never let a software LMK near real cards.


Two Modules, One Key, Different Bytes


A working key such as the PIN key you share with the host exists in two modules, yours and the host's, each under its own LMK. The same clear key loaded into two modules:



The bytes differ because they are encrypted under different master keys. What matches is the check value (KCV): the first three bytes of a block of zeros encrypted under the clear key. It identifies a key without revealing it. When the host's operations team reads you a key's check value, compare that, never the bytes.


A Key Exchange Is Checked Before It Is Used


The PIN key shared with the host is not typed in. The host generates it and sends it encrypted under a zone master key (ZMK), which both sides loaded once in a key ceremony: two or three people each enter one clear component, and the module XORs them together. Each new key arrives with its check value, and you import it under your copy of the ZMK:



Suppose one person at our ceremony typed one hex digit wrong, 1F3E… instead of 1F2E…:



The ceremony's own check value, F271B6 instead of 4BE3CA, already gives the typo away if anyone compares it. The import fails the DES parity check, which the last argument of importKey asks for. With that check off, the module imports a key that is not the host's, and its check value catches the typo whatever the parity says. If nobody compares it, every PIN block you send is encrypted under the wrong key, every PIN purchase is declined 55, and for days it looks like a wave of forgetful cardholders.


Matching ZMK check values only say the ceremony went right. They say nothing about the key that arrives next, which may be damaged, stale or not the one announced, so compare each new key's own check value too.


A MAC Covers the Bytes as Sent, So It Is the Last Thing You Add


Many hosts require a MAC (message authentication code) on every message. It is a short cryptographic checksum computed with a key both sides share, the ZAK. The receiver recomputes it; if it matches, the message wasn't changed on the way and came from someone who holds the key.


The host's specification sets what is MACed. A common rule, and the one this unit's host uses: the packed message up to, and not including, the MAC field, with the MAC's bit already set in the bitmap.



The client translates the PIN and signs the message. Does the order matter? A PIN purchase both ways, and one more whose MAC was computed over the message packed before field 64 existed:



Signing before translating covers a field 52 that the host never receives. Packing without field 64 covers a bitmap that ends in …1000, while the host's copy ends in …1001:



So macInput sets a placeholder in field 64 before packing (2), and cuts off exactly the MAC field's packed length (3): with iso87ascii.xml the 8 MAC bytes travel as 16 hex characters. It works on a clone (1) because the same method verifies responses, whose field 64 must stay as it arrived. Sign last, after the PIN is translated, the STAN is set and every other field is in place: any change after signing, however harmless it looks, makes the host reject the message.


SMAdapter in 2.1.7 has no MAC verify method, so you compute and compare. MessageDigest.isEqual compares in constant time, so it doesn't leak how many bytes matched.


Networks differ. Some MAC a list of fields rather than the packed message, and some use field 128 when a message has a secondary bitmap (fields above 64). macInput is the one method to change; the rule "sign last, over what is sent" stays.


A Response That Fails Its MAC Is an Unknown Outcome, Not a Decline


The host signs its responses too, and the client verifies every one.



The host approved four purchases. We left one response alone, changed two on the way back and dropped the fourth:



In all three bad cases the host approved the purchase, and the client can't know it: anyone on the path could have written the response it holds. That is the situation of a request with no answer, and unit c12 settles what follows: the purchase is reversed, never resent.


If the client reports a bad MAC as a decline, the second line above becomes a real customer: the issuer approved and holds the funds, the terminal printed "declined", and the cardholder paid again with another card. If it reports it as an approval, anyone who can change bytes on the path can approve purchases. A missing MAC counts as a wrong one: stripping the MAC is the easiest attack there is.


A run of MAC failures means your key is out of step with the host's, or someone is changing messages. Either way, alert someone.

Card Data Crosses the Client Intact and Stays Nowhere


A client handles card numbers and track data in every purchase. It is allowed to move them, not to keep or show them.


A developer who wants the card number out of the logs sometimes masks it in the message itself, with ISOUtil.protect. jPOS packs the result without complaint:



The host receives a card number it can't authorize, and declines. Masking is for what people read: the log, with ProtectedLogListener configured to protect fields 2, 35 and 45 and wipe fields 52 and 55 (unit c8), and anything you print, with ISOUtil.protect. The message you send carries the card number the way it came.


  • Track data, CVV and PIN blocks are never kept after the purchase is answered: not in a database, a queue, a retry file or an exception message. The reversal builder of unit c12 copies neither field 35 nor 52 for this reason.
  • A card number you must keep, to refund later for example, is stored encrypted, with a key from a key store or the HSM, and looked up by a keyed hash. Unit s9 shows the server side of this.
  • Keys and passwords never appear in code or configuration, published test keys like DeskHsm's aside. Keys come from the module, under its LMK. Passwords come from the environment, as unit c3 showed for the key store.

Summary


  • A PIN block means nothing without its key and its card number. Format 0 mixes the PIN with 12 digits of the card number before encrypting it, so a block is readable only with both. A block relayed unchanged reaches a host that doesn't hold the key, and every PIN purchase is declined.
  • The client translates the PIN and never sees it. translatePIN re-encrypts the block inside the module. When translation fails, the purchase is refused, never sent without field 52.
  • Keys live under the module's master key and are known by their check value. Deploy the module as an SMAdaptor with the Bouncy Castle provider. Compare check values whenever a key is loaded or exchanged; the encrypted bytes always differ between modules.
  • A MAC covers the bytes as sent. Sign last, with the MAC's bitmap bit set, over exactly what the host's spec names. One change after signing and the host answers 63.
  • A response that fails its MAC is an unknown outcome. A wrong or missing MAC is handled like no answer: reverse, and alert someone.
  • Card data crosses the client intact and stays nowhere. Mask in logs and displays, never in the message; keep no track data, CVV or PIN blocks.

Challenges


  1. Your host rotates the PIN key every day at 02:00 with an 0800 carrying the new key under the ZMK. Purchases are in flight at that moment, some with blocks translated under the old key. What do you keep, for how long, and what does the host need to do for this to work?
  2. A MAC failure on a response triggers a reversal. The reversal is MACed with the same key. If the key is out of step with the host's, what happens to that reversal, and to the next hundred purchases? Design the alert and what it should stop.
  3. Your test suite uses JCESecurityModule, and production uses a hardware HSM through its vendor's adapter. List the behaviours your tests can't see, such as error codes, timeouts, and a busy HSM, and say how you would find out about each one before go-live.
  4. A colleague proposes dropping the MAC because the link already runs TLS with serverauth=true. What does each one protect against that the other doesn't, on this client's link?


Design Note: Why the PIN Is Re-encrypted at Every Hop


A PIN travels from the PIN pad to the issuer through the terminal, the acquirer's client, the acquirer's host and one or more networks. It is not encrypted once for the issuer: each pair of neighbours shares a PIN key, and every hop translates the block from the key it came in under to the key it goes out under.


The alternative, one key from terminal to issuer, would need every terminal to hold a key for every issuer, or one key shared by everybody. Neither survives a single compromised terminal. With keys per hop ("zones"), each party manages only its neighbours' keys, a leaked key exposes one link, and a key can be replaced between two parties without telling anyone else.


The cost is that every hop needs a security module, a key ceremony with each neighbour, key exchange, check values, and staff who know how to run them. The opening's client skipped that cost by copying field 52. MACs follow the same pattern: a MAC key per link, so a message is re-signed by each party that forwards it.
