An acquirer's switch takes purchases from its terminals and forwards each one to the card's network. A purchase of 42.50 is approved, and the 0210 is lost on its way back to the terminal. The terminal reverses, as unit c12 taught it: an 0420 whose field 90 names the purchase. The switch forwards the reversal, the network answers 00, and the terminal is done. A week later the cardholder calls the bank, because the 42.50 is still held. The network never found the purchase the reversal named: it had never seen the STAN the terminal gave it.

A switch is a server toward its sources and a client toward its destinations. Unit s5 forwarded requests unchanged, and unit c12's gateway renumbered them for one link. The switch between them follows four rules, one per section heading.

Every output comes from jPOS 2.1.7 in one JVM. Q2 deploys the switch, unit s4's DirectTerminal plays the terminals, and two QMUXes, visa and onus (the bank's own issuer system), have a scripted destination on their queues, like unit c12's test host. The destination holds every amount it approves until a reversal names the purchase; its code is in the Reference. Unit c12's SAF sender delivers the switch's queued reversals, and the switch's records (16.2) are registered as switch-records before Q2 starts. Each run starts with empty spaces, and the 90= columns show the first 20 of field 90's 42 digits: the original's MTI, STAN and field 7.

The Destination Gets a Copy Numbered by the Switch, and Every Answer Starts From the Source's Request

The switch's TransactionManager:

SelectDestination (unit s5) picks visa or onus from the card number, and each QMUX is named after its destination, so QueryHost finds it as mux.visa. SelectByMti and AnswerFailures are unit s10's: reversals run the reversal group, and AnswerFailures has one more line in its table, DO_NOT_HONOUR answered 05. In the purchase group, PrepareOutbound builds the message the destination receives, QueryHost sends it, and MapResponse (16.3) turns the answer into the terminal's reply.

QueryHost sends whatever is under its request key. Why build a copy, when the switch could set fields 11 and 32 on REQUEST and send that? Two purchases from terminal 29110001, one approved and one whose approval is lost on the way back, first with REQUEST renumbered in place, then with the copy:

Renumbered in place, both answers carry the switch's STAN. Every participant that answers the terminal starts from REQUEST, as unit s2 requires: MapResponse for the approval, AnswerFailures for the 91. The terminal's QMUX matches neither (unit c12), waits out its timeout, and reverses a purchase the network approved. Unit c12's gateway restored the terminal's STAN in its one answer; here several participants answer, on both paths, and each would need that step.

(1) A copy. clone() keeps what the destination needs, track data included, and drop removes what only the source reads, here field 48. A real switch also translates the PIN block (52) from the terminal's key to the network's, in its security module (unit s7).

(2) The switch numbers the link. Upstream the switch is the sender, so the STAN comes from its own sequence per destination (unit c12's StanSequencer, key stan.visa), whatever the terminals sent. Field 32 names the switch as the acquirer. In production the space is persistent (je:switch), so the sequence survives a restart.

  1. Coding practice

    Forward a terminal's request as the switch, and answer it as the terminal's

    • The destination receives a copy of the source's request; every answer to the source, approval, decline or 91 alike, is built from the unchanged request, so renumbering the request in place breaks every answer.
    • On each upstream link the switch is the sender, so the copy carries a STAN from one sequence per destination link and the switch's own identifiers.

A Source's Reversal Finds What the Destination Saw Only Through the Switch's Record


The terminal's purchase is approved, and the terminal reverses it anyway, as it would if the 0210 had been lost, then repeats the reversal. With the reversal forwarded like any request:



What does field 90 of the forwarded 0420 name? The terminal's purchase: MTI 0200, STAN 000741, sent at 1106121530. Visa saw that purchase as STAN 000001, found nothing to undo, and answered 00, which is how a reversal of an unknown purchase is answered (unit s10). The 42.50 stays held.


Only the switch knows which upstream message carried the terminal's purchase, so it keeps a record of each one, written before the message leaves:



PrepareOutbound's line (3) calls remember with the source's request and the copy. The reversal group holds one participant, which finds the record by the terminal ID and by the STAN and time in field 90:



The same three messages:



The switch queued an 0420 naming STAN 000001; unit c12's SAF sender delivered it, and visa released the amount.



(1) Taken, not read. inp removes the record, so the repeat finds nothing and queues nothing. inp is atomic (unit s12), so two sessions can't both take the same record.


(2) The link's own sequence. The upstream reversal is a new message on the visa link (unit c12). Its STAN comes from stan.visa, in the space PrepareOutbound numbers from.


The record is written before the request leaves, because the purchase that most needs it is the one whose answer never came (16.4). It holds a PAN, so it is kept like the transaction database: no track data, PIN block or chip data, and a lease a little longer than the time a source may take to reverse.

A Destination's Code Becomes a Cause, and Each Source's Table Answers It


The terminals and visa speak ISO 8583:1987, with two-character response codes. onus was built on jPOS's Common Message Format (CMF) and answers with four-digit action codes: 0000 approved, 1016 not sufficient funds. Here the destination's field 39 goes into the reply as it is, and each answer is packed with the terminal link's packager, as the server's channel would pack it:



iso87ascii.xml gives field 39 two characters, so no answer from onus can be sent, approvals included. SendResponse catches the exception and notes it in the Context, which the log shows only when debug-context is true. The terminal waits out its timeout and reverses.


Translating code to code needs a table for every pair: with three sources and four destinations, twelve. The switch instead turns each destination's code into a cause, one of the CMF names that unit s10's participants report, and one table per source turns the cause into that source's code. That is seven tables, and a new destination adds one:



(1) The destination's table is in the descriptor, one property per code: visa.51 and onus.1016 both name NOT_SUFFICIENT_FUNDS.


(2) A decline is reported as a cause, and AnswerFailures, the source's table, answers it from the source's request. An approval is built here, from the same request. It copies only field 38 from the answer, so the destination's STAN, its field 32 and its private fields stay out of the reply.



The CMF names are jPOS's internal result codes. CMF is also a complete message format, based on ISO 8583:2003, and the 2.1.7 jar has its packager as jar:packager/cmf.xml. A purchase packed and unpacked with it:



Field 4 unpacks as an ISOAmount that carries its currency and its number of decimals, field 11 has twelve digits and field 39 four. By CMF's convention the MTI starts with the version digit 2 (2200); the packager doesn't check it. This switch keeps 1987 messages inside and uses CMF only for its codes. A switch that adopts the whole format translates every message into it at the edge, and saves tables the same way.


A Code the Table Lacks Is Like Silence, and the Switch Reverses What It Sent


Visa answers a purchase with 08, and visa's table has no line for it. With an unlisted code taken for a decline:



08, "honour with identification", is an approval (unit s10). The terminal shows a decline, the cardholder pays another way, and visa holds 42.50 for a purchase nobody completed. A code the switch can't read tells it no more than silence does: the destination may have approved. MapResponse handles both alike: unknownOutcome reverses what was sent and fails, and AnswerFailures answers 96 (SYSTEM_ERROR) or 91 (HOST_UNREACHABLE).


The same 08, then a purchase visa approves but whose answer is lost, then the terminal's reversal of that purchase:



Both reversals name the switch's STANs: 000001, then 000003, because the first reversal took 000002 from the same sequence. The terminal's 0420 found no record, since unknownOutcome had taken it, so visa gets one reversal per purchase.


MapResponse is a plain participant, so it runs only while the transaction is prepared. With QueryHost's continuations at their default, true, a timeout comes back prepared (unit s5). With false, QueryHost votes FAIL on a timeout and MapResponse never runs. The terminal still gets its 91, so it has nothing to reverse, and the silent purchase above stays held with nobody reversing it. When the link is down, QueryHost fails before sending, and the record waits out its lease. A reversal from the terminal then queues one for a purchase visa never saw, which visa acknowledges.


A late answer lands on visa-unhandled (unit c12). Its reversal is already queued, so it needs only a log line, without card data.

Summary


  • The destination gets a copy numbered by the switch, and every answer starts from the source's request. Renumber REQUEST itself, and the approval and the 91 alike carry the switch's STAN, match nothing at the terminal, and turn into reversals.
  • A source's reversal finds what the destination saw only through the switch's record. Forwarded as it came, it names a STAN the destination never saw, is answered 00, and undoes nothing. The record is written before sending, taken once, and kept without card secrets.
  • A destination's code becomes a cause, and each source's table answers it. Passed through, a code from another format can make the reply unsendable. One table per endpoint is n + m tables instead of n × m.
  • A code the table lacks is like silence: the outcome is unknown, so the switch reverses what the destination was sent, once, and answers 96 or 91. Taken for a decline, an unknown approval holds the cardholder's money.

Design Note: Why Causes, and Not Code-to-Code Tables?


A table from each destination's codes straight to each source's codes says exactly what the two parties mean, and nothing is lost on the way. It also has to be written, tested and kept up to date for every pair, and the business rules in between have to be written against every dialect.


Translating through causes puts one vocabulary in the middle. jPOS's stock participants already report in it (unit s10), the switch's own rules read it, and each endpoint needs one table. The price is that a cause is coarser than either code. Two destination codes that mean slightly different things may map to one cause, and the source then hears one code for both. A network's code with no cause to map to has to wait for one, and until then it is an unknown outcome (16.4). The loss matters less than it sounds, because a terminal acts on few codes. The real work is in the codes that fit no cause, and a switch should log them where someone will read them.
