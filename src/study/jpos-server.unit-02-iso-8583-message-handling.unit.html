A new server goes live with one acquirer's terminals. Its log shows an 0210 with 39=00 going back for every 0200, yet every purchase fails at the counter: the terminals' client waits its full timeout, gets null, and sends an 0420 reversal (unit c12). By evening the server has approved and then reversed every sale of the day.

The answers reached the client but matched no waiting request and went to its unhandled queue, because nothing in them said which request they answered. This unit's five rules, one per section heading, cover the messages a server reads, answers and starts.

A Client You Can Point at Your Code

Only the client's QMUX can judge your server's answer, so the test bench is that QMUX, in the same JVM, joined to your code only by the wire format:

Requests are packed with the client's packager and unpacked with the server's, and answers go the other way. The QServer and its socket are unit s3's. The Server Reads With Its Packager, the Client With Its Own

In a Q2 server your code doesn't create the packager: the QServer's descriptor names one, and each connection's channel uses it to unpack requests and pack responses:

Your code receives what that packager read. The client set fields 4 and 11 without padding:

The client's packager padded both on the wire (unit c2), so store and compare what the server got, not what the client set. The answer carries 000731 back, and QMUX pads the client's field 11 the same way in its key (unit c12), so the two match.

Now the server's descriptor names iso93ascii.xml, the 1993 layout, while the clients keep the 1987 one. Does the server read the next purchase?

It does, field for field: the two layouts encode every field this purchase carries (2, 3, 4, 7, 11, 14, 35, 41, 42 and 49) into the same bytes. They differ elsewhere, including field 39: two characters in 1987, a three-digit action code in 1993. The request has no field 39, but the response does, so the server packs 000, the client reads 00, and the leftover 0 shifts every later field. Field 41 comes back as 02911000, the answer matches nothing, and the client gets null, then reverses.

The server's log looks clean, because it logs what its own packager read and wrote. Only the client sees the damage, so test what the client gets back, as this rig does, or compare the bytes with the specification's samples (unit c13). Both ends must agree on every field either of them sends.

ISOMsg.setResponseMTI() computes the response MTI from the request's:

It adds one to the third digit and keeps the fourth digit's origin but drops the repeat flag, so the 0421 repeat of a reversal gets an 0430. The client's key uses only the MTI's first three digits (unit c12), so the 0430 matches the 0421.

A participant (unit s4) written for purchases often sets the MTI by hand. Then an advice arrives:

The second line is from a responder that copies fields 0, 11 and 41, sets 39 and forgets the MTI:

The client keyed its 0220 with 022, and an 0210's key starts with 020, so it matches nothing even with every field echoed. A Response Copies What Identifies the Request, and Leaves the Request Alone

The two shortcuts are to clone the whole request and change what differs, or to turn the request itself into the response. In a Q2 server the request object is the one the IncomingListener put into the TransactionManager's Context under REQUEST (unit s4):

A full clone sends the card back. Field 35 is track 2 from the stripe, and field 14 the expiry date. Both cross the link into the client's logs and stores, and while your server's logger may wipe track 2, the client's may only mask the PAN. A PIN block (52) or chip data (55) would go back too, and none of them helps the client match or act on the answer.

Answering in place destroys the request. The Context's REQUEST becomes an 0210 with a response code, so the transaction log records a response where the request should be, and a later participant checking for a purchase sees 0210. The card data goes back as well.

A response is a new message built from a short list:

clone(int...) copies into a new message only the listed fields the request has, so a request carrying something unexpected can't leak it. The approval code (38) goes only with an approval. A decline with response code 51 comes out as:

Many networks' lists include the PAN (field 2), which goes back in clear: the message carries the real value, and only the log masks it (units c2 and s8).

  1. Coding practice

    Answer every request the terminals send

    • The client finds an answer by its key fields, so a response must carry each of them unchanged; a response built from scratch or renumbered by the server matches nothing.
    • setResponseMTI turns any request into its response MTI, while a hand-written MTI leaves other kinds of request, such as advices, unanswered.
    • A response is a new message holding only the listed fields, so card secrets stay behind and the request in the Context stays a request; the approval code goes only with an approval.

A Message the Server Starts Is a Fresh Copy, Numbered by the Server


Messages with no request to start from, such as an echo to a quiet client or a new working key, take their constant fields from a template. The tempting version uses one 0800 template, with field 70 naming the network message:



echo() is the same with 70=301 and no field 48. The server sends a key change, then an echo:



Line (1) hands out the template itself, so the echo, and every later 0800, carries the key change's field 48. The two are also one object: a key change still queued when the echo is built goes out as an echo, and the key never changes. Under load, two threads fill in the same object at once.


Each message is a copy of the template, with the varying fields set on the copy. clone() copies the field map, so a field set on the copy never reaches the template:




Here the server is the sender, so it numbers the message from its own sequence, as a client does (unit c2). All kinds share one sequence per link, because the client answers each with the same STAN, and two messages in flight with one number could not be told apart. The clock is passed in so a test can fix it, and field 7 is in GMT.


Networks differ. The field 70 codes (301 echo, 161 key change here), where a new key travels (field 48, 53 or 96) and which fields every network message carries are the network's choice.


To put such a message on a connection, a 2.1.7 QServer with an <in> element sends whatever arrives on that Space queue to the last connected session by default (<send-request> chooses LAST, ALL or RR).

Summary


  • The server reads with its packager, the client with its own. Fields arrive padded to full width. A layout that differs only in fields the requests don't carry reads every request correctly and garbles every answer, so test what the client gets back.
  • The client finds the answer by the fields you echo: the mapped MTI, field 41, field 11 and any key field it adds. A response built from scratch or renumbered by the server matches nothing, and the approved purchase ends as null and a reversal.
  • setResponseMTI answers every kind of request, repeats included. A hand-written 0210 leaves every advice unacknowledged.
  • A response copies a short list of fields into a new message. A full clone sends track 2 back, and answering in place overwrites the Context's request.
  • A message the server starts is a copy of a template, numbered from the server's own sequence for the link. A handed-out template collects every message's fields.

Challenges


  1. Your network's specification lists the fields to echo for 0100, 0200, 0220 and 0420, and the lists differ. Where do the lists live in your code, and how does a test catch a message type that has none?
  2. A client configures its QMUX with <key>41, 11, 37</key>, and your server assigns field 37 for requests that arrive without one. What does the client's key look like for its request and for your answer, and what do you change?
  3. The 1987 and 1993 layouts agree on every field your terminals send today. A new terminal model sends field 12. What does the server read, and what test would have caught the wrong packager-config on the first day?
  4. Two threads build server-initiated messages from one ServerMessages. Which of its parts are safe to share, and which would break if the space were a plain HashMap counter?


Design Note: Why Does the Response Repeat the Request?


An ISO 8583 response has no "in reply to" field. It repeats enough of the request for the sender to recognise it. The responder needs no memory of what it was asked, so any thread of the server can answer, as long as the answer goes back on the connection the request came in on.


The price is that the protocol can't tell a wrong answer from a missing one. A response with one field dropped or renumbered raises no error on either side. It shows up as a timeout on the client, in someone else's log.
