  15. Design Note: A Simulator Built From Your Own Parts

Certification with the acquirer is booked for two slots of three hours each. The acquirer's script has forty cases. Card 5555555555554444 must be declined with 05. A purchase over 500.00 must be declined with 51, and one of exactly 500.00 approved. For 777.00 the acquirer's test host stays silent, and the client has to reverse the purchase before the case passes. 888.00 is approved after 1.5 seconds. Each failed case costs slot time, and a third slot costs money.

Before the first slot the team runs the same cases every night against a simulator on 127.0.0.1, and they pass. In the first slot the silent-host case fails: the client never sent a reversal. The simulator had answered 777.00 with 51 every night, so the reversal path had never run.

A simulator, a proxy or a test harness can disagree with the real host while the build stays green. This unit's five rules:

  1. A simulator's rules are data, and the first rule that matches decides.
  2. A listener runs on the session's thread, so a late answer is scheduled, never slept.
  3. The simulator is a witness: ask it what the client sent.
  4. A proxy may answer only for a request that never left.
  5. A scripted case grades every field and reports every failure.

Unit c10's stand-ins live inside the test. The tools here run beside the system while you develop and certify it. Every output comes from jPOS 2.1.7, with the simulator, the client's host-channel and its host-mux deployed by one Q2 in one JVM.

A Simulator's Rules Are Data, and the First Rule That Matches Decides

A simulator that a team shares gets a new case every week. If its behaviour is code, each new case waits for a developer, a build and a redeploy. If it is a table in the deploy descriptor, the tester adds a line.

The team's nightly table has one rule per line: conditions, an arrow, actions.

Amounts are in minor units, as in field 4, and a range includes both of its ends. Which rule answers a purchase of 777.00?

The simulator tries the rules from the top, and the first match answers. 777.00 is inside 50001-99999999, so the second rule answers 51 and the third never runs. Six requests, against that table and then with the silent rule moved to the top (card's first digits, field 3, field 4, answer):

The first run is the nightly one: it answers every request, so the silent case never happens.

Why not let the most specific rule win? A tester can't check "most specific" by eye: is a card rule more specific than an amount range? First-match can be checked by reading from the top. So put exceptions first, ranges after them, and any last.

The simulator is an ISORequestListener, like unit c10's LoopbackHost. QServer creates it with its no-arg constructor and hands it its <property> elements through Configurable:

The answer is a clone, so the request the session holds is unchanged (unit c10 showed what a stand-in that answers with the request itself hides). A silent rule returns true: handled, by saying nothing. When no rule matches, process returns false and ISOServer offers the message to its next listener, so end the table with any.

Amounts are compared as numbers: field 4 is twelve zero-padded digits and the bounds are not, so as text 000000077700 would sort below 50001.

A rule that can't be read stops the deploy. Suppose a tester types amout= in the over-limit rule. A parser that skips unknown words reads the rule as "every 0200 gets 51". One that skips the whole rule approves every purchase over 500.00, and the nightly run stays green until the over-limit case meets the real host. parse refuses instead:

Each rule is one repeated rule property, and cfg.getAll("rule") returns them in descriptor order:

The rest of the unit runs this simulator, saved as deploy/50_host_simulator.xml. With amout= in it, Q2 deploys the file and the QServer fails to start:

Nothing listens on the port, the client's link never comes up, and the client reports isConnected: false. The nightly run fails at its first case, with the rule's text in the log.

Use the real host's channel class and packager. A simulator with an easier wire format hides the framing and packing problems you most want to find before certification.

    • A simulator's behaviour is an ordered table: the first rule that applies answers, so exceptions go above ranges and the catch-all goes last.
    • A rule the simulator cannot read stops the configuration instead of being skipped, so a typo fails the deploy rather than quietly changing the answers.

The acquirer doesn't send its test cases as rules. It sends a sheet, one case per line:

The columns are the case, the MTI, the PAN, the amount from, the amount to, and the response code. A blank column means "any". A Listener Runs on the Session's Thread, So a Late Answer Is Scheduled


For the slow 888.00 case, the obvious simulator sleeps:



The client, with a one-second timeout, sends the 888.00 purchase and, while it waits, a purchase of 120.00 on the same connection. When does 120.00 get its answer?



Both timed out. ISOServer gives each connection a session. The session reads one message, calls the listeners on its own thread, and reads the next only when process has returned. While the listener sleeps, 120.00 sits unread in the socket, and its answer leaves after the first, 1.5 seconds late too.


The same two purchases against RuleHost, whose rule for 888.00 is late=1500:



process hands the late answer to a scheduler and returns, so the session reads 120.00 at once. The answer to 888.00 still arrives after 1.5 seconds, and QMUX, with nobody waiting for it, puts it on host-unhandled (unit c12).


With the sleep, one slow case became two unknown outcomes. A client that reverses on null (unit c12) sends two reversals where the script expects one, and the failing case is 120.00, which had nothing to do with the slow host. In a load run (unit c10) every session that meets a slow case stops reading, so the run measures the simulator instead of the system. Keep sleeps out of a simulator's listeners.


Two other faults:


  • Every answer slow. jPOS 2.1.7's org.jpos.iso.filter.DelayFilter sleeps for its delay property, in milliseconds, each time a message passes. On the simulator's channel, outgoing, it delays every answer. It sleeps in the sending thread, on a server the session's, so it blocks the session as Thread.sleep does. Use it to size timeouts against a uniformly slow host, and late rules for one slow case.
  • The connection drops mid-purchase. In process, the ISOSource is the session's channel, so a drop action is ((ISOChannel) source).disconnect() followed by return true.



With this channel in the simulator, both purchases above came back null at 1000 ms.

Problem statement


A late=1500 rule is fine for a person trying things by hand, but an automated test that needs an answer to arrive after the client gave up depends on the machine being fast enough. On a loaded build server the test fails now and then. QA wants the host to keep an answer back until the test says "now", whatever the clock does.


HoldingHost in src/main/java/com/example/practice/HoldingHost.java approves every request, and it is given the STANs whose answers the test wants to hold. Two methods are TODO:


  • hold(client, answer): keep the answer until the test releases it.
  • release(): the test calls it from its own thread. It sends the answers held so far and returns how many reached a client.


process is called the way ISOServer calls it. A test may hold several answers, from several clients, before it releases them, and a client may disconnect while its answer is held. The tests call process and release from different threads. About 12 lines in total.

The Simulator Is a Witness: Ask It What the Client Sent


A test that checks only what the client reports can pass a client that does the wrong thing. Two clients each send a 0200 with a one-second timeout. When no answer comes, the first sends the same 0200 again:



The second, reversing, sends an 0420 that points at the purchase through field 90, as unit c12 builds it. Both run against the 888.00 rule. Then the test takes the next two requests the simulator received from its seen queue:




The retrying client reports APPROVED. When the first request returned null, QMUX released its key, so the resend was accepted and sent. It has the same key, so the first attempt's approval, arriving at 1.5 seconds, matched the resend, which was still waiting. The host received two purchases and approved both. The cardholder paid twice, and a test that asserts "approved" passes.


Only the simulator knows what crossed the wire, so the test asks it. RuleHost writes a clone of every request it receives to the queue named by its seen property, in the default Space. A test in the same JVM takes them in arrival order.


  • Take with a timeout. sp.in(key, 2000) returns null after two seconds when the client sent nothing, so the test fails instead of hanging.
  • Let the records expire. Each clone goes in with a lifetime of 60 seconds, so a simulator that runs all week doesn't keep every request it ever saw. The clones hold clear test PANs and live only in memory.


A Proxy May Answer Only for a Request That Never Left


To see what your client and the acquirer's test host say to each other, put a recording proxy between them: a QServer your client connects to, whose listener forwards each request through a QMUX to the test host, relays the answer, and logs both.


Spot the Problem: The Proxy That Helped


A first version has no answer to relay in two situations, and answers both the same way:



The client waits three seconds and the proxy one. What happens to the 888.00 purchase, which the host approves after 1.5 seconds?



The client was told 91 at one second, a decline. Half a second later the host approved the purchase, and its approval landed on the proxy's upstream-unhandled queue, where nobody reads it. At a real counter the cardholder is told the payment failed, pays another way, and finds both payments on the statement. The client got an answer, so it has nothing to reverse.


The mistake is at (2), which treats two situations as one. When the link is down, (1) sent nothing, the host knows nothing of the purchase, and 91 is true. When request returns null, the purchase has left, and the proxy knows as little as a client whose request timed out (unit c12). It must not answer, so that the client's own timeout fires and the client reverses.


RecordingProxy keeps the two apart:




It is still not right with a one-second wait:



The client now reverses, which is safe. But the approval came at 1.5 seconds, while the client was still waiting, but after the proxy had given up. A purchase that would have gone through became a reversal. The client decides how long to wait, so the proxy must wait at least as long:



What the proxy records is not what it forwards. The host needs the PAN, and the client needs the answer exactly as the host sent it, so (3) relays the host's message untouched. The record is the LogEvent, which carries the ISOMsg objects themselves, so the ProtectedLogListener at the front of the Q2 logger (unit c8, with protect covering field 2) masks a copy before any writer sees it. The request shows as outgoing because the event is logged at the end, after the upstream channel has sent the same object on:



Masking field 2 in the forwarded message instead would make the host decline every purchase as an invalid card. Logging the message as a string would put the PAN in clear on disk.


Toward the test host the proxy is an ordinary client: a ChannelAdaptor named upstream-channel with queues upstream-send and upstream-receive, like unit c1's host-channel, and this QMUX:

One QMUX Serves Every Client of the Proxy


Two testers point their clients at one proxy. Both use the lab's terminal ID, 29110001, and both number STANs from the start of the day. While the first tester's 888.00 purchase waits for the host, the second sends a purchase with the same STAN:



The proxy's QMUX builds its key from the MTI and fields 41 and 11 (unit c12), and it can't tell the two clients apart. It refused the second request, and the proxy logged the exception and sent nothing. The second tester sees a host that didn't answer.


A recording proxy shouldn't renumber STANs the way unit c12's gateway does, because then what it records is no longer what the client sent. Give each client its own terminal ID, or run one proxy per client.


mux.request also blocks the session thread (16.2), so requests on one connection are answered one at a time. Separate clients don't wait on each other, since each connection has its own session.


Test links only. A proxy on a production link holds every PAN that crosses it, and it falls under the same card-data controls as the systems on both sides.

A Scripted Case Grades Every Field and Reports Every Failure


A certification case is data: a request, and what its answer must carry. The answer can fail in several fields at once, and the analyst reading the report has one slot to fix them in. A test that asserts field by field stops at the first failure. A grader that collects every difference reports them all in one run.


The expected values take four forms: a literal (00), * for "present, any value" (38 on an approval), - for "absent" (38 on a decline), and = for "the request's value echoed" (11, 41):



The script sends each case through the client's host-mux to the simulator of 16.1, and takes every STAN from one counter, so no case repeats a key and each one can be found in both logs:




Each Case holds a name, the card, field 3, field 4 and the expectations. The last case is wrong on purpose: it expects an approval, and the Visa PAN in field 2, for the card the table declines. The report lists all three differences in field order, and the card numbers in it are protected, because reports get pasted into tickets.


A null response is one failure, no response, not one line per expected field. A case that expects silence, like 777.00, runs outside this loop: it passes when the simulator's seen queue shows the reversal (16.3).


Run the same script against the simulator on every build, and against the acquirer's test host in the certification slot. When the two disagree, the simulator is the one to fix.

Summary


  • A simulator's rules are data, and the first rule that matches decides. Put exceptions above ranges and any last. Compare amounts as numbers, and refuse a rule you can't read, so a typo fails the deploy instead of quietly approving.
  • A listener runs on the session's thread. A sleep delays every later request on the connection. Schedule a late answer, use DelayFilter for a uniformly slow host, and keep the simulator out of a load run's measurements.
  • The simulator is a witness. A client can report the right outcome and still double-charge. Assert on what the simulator received, take with a timeout, and let the records expire.
  • A proxy may answer only for a request that never left. 91 when the link is down, silence when the host didn't answer, a wait at least as long as the client's, the host's answer relayed untouched and only the log copy masked. Its one QMUX needs distinct keys from all its clients.
  • A scripted case grades every field and reports every failure, in field order, with card numbers protected and a missing answer as one failure.

Challenges


  1. The acquirer's script has a case in which the host answers after 25 seconds and your client waits 20. Write the rule, then say what the case's expected result is: the answer, the reversal, or both, and how the harness checks each.
  2. Your QA team wants the simulator to decline the third purchase of the day on any card. What state does RuleHost need for that, where would you keep it so that two sessions agree, and what does a restart of the simulator do to the case?
  3. The simulator runs from a descriptor that QA edits. How would you stop a table whose any rule is not last from deploying at all, and is a rule that can never match always a mistake?
  4. A partner asks you to put the recording proxy in front of their certification endpoint for a week. List what it holds in memory and on disk, and what you would change before agreeing.


Design Note: A Simulator Built From Your Own Parts


The simulator is built from the same jPOS pieces as the client: a QServer, the channel class and packager from the acquirer's specification, and a listener. That makes it cheap: there is no second tool to learn.


It also shares the client's blind spots. If the packager you copied into the simulator misreads a field, the client and the simulator misread it the same way, and every case passes (unit c13 showed a round-trip test failing the same way). The same holds for anything else the two share: a misunderstanding of the specification written into the rule table is checked only against itself. It finds faults in the client's behaviour (declines, silence, late answers, reversals), not differences between your reading of the specification and the acquirer's.


So keep two sources of truth. The specification's sample messages, packed and compared byte for byte, check the packager. The acquirer's test host, in the certification slot, checks everything else once. The simulator sits between them and makes the slot short, because every case has already run every night.
