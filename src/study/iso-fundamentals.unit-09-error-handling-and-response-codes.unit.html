A prepaid card with 50.00 left on it pays for 80.00 of groceries. The issuer answers with an 0110 whose field 39 is 10. The terminal prints APPROVED, and the cashier bags all of it. Was that right? What field 39 says, and who has to act on it, comes down to five rules, one per section heading.

Several Codes Approve, and a Partial Approval Covers Only Part of the Amount

In the 1987 edition the issuer's decision is field 39, the response code, two characters. Four common codes approve:

CodeMeaningWhat the acquirer must do
00approvedcomplete the sale
08honour with identificationcomplete it once the cashier has checked the cardholder's ID
10approved for a partial amountcollect the rest some other way
11approved (VIP)complete the sale

10 is the grocery case: the issuer approved 50.00, and the cardholder owes 30.00 more (which field carries the approved amount depends on the network). Read as a full approval, the merchant hands over 80.00 of goods and is paid 50.00. Read as a decline, the cashier asks for another card while the issuer holds 50.00 that no sale will use, until the hold expires or a reversal (unit 4) releases it. Asking the issuer again for the full 80.00 doesn't help: the card has nothing more to give. If the cardholder walks away from a partial approval, reverse it.

08 read as a decline is the same trap for the whole amount: the issuer has committed the funds, the goods stay in the shop, and nobody reverses, because a decline needs no reversal.

A Decline Is Final for Its Request, and Its Code Says Who Could Change the Answer

A terminal resends any declined purchase once, "in case the network hiccupped". The issuer answers 55, incorrect PIN. What does the resend achieve?

The same request gets the same decision. With 55 it also costs something: the issuer counts each wrong PIN it checks, so the resend is one more failed try, and at the issuer's limit the answer is 75 and the PIN is blocked. Only a new attempt, with a new STAN, can get a different decision, and the code says whether one makes sense:

  • the cardholder: 51 insufficient funds, 54 expired card, 55 incorrect PIN, 61 and 65 withdrawal limits. Another card, another amount or the right PIN may succeed;
  • the merchant: 04 and 07 pick up card, 41 lost card, 43 stolen card. Decline, and keep the card if the acquirer's procedure says so;
  • a phone call: 01 and 02, refer to card issuer. The issuer wants the merchant to call before it decides;
  • nobody: 05 do not honour, 57 not permitted to the cardholder.

An Error Code Reports a Failure, Not a Decision About the Card

Some codes say the request could not be decided, and whose failure that was:

  • the sender's message: 30 format error, and often 12 invalid transaction and 13 invalid amount. Sent again unchanged, it fails again; a developer has to fix the mapping;
  • the other side's systems: 91 issuer or switch inoperative, 96 system malfunction. The card may be fine, and a new transaction a minute later may be approved;
  • the keys: 63 security violation. It can mean keys out of step after a key change, or an attack. Alert whoever manages the keys (unit 8), and don't retry.

Read as declines, these hide what went wrong. After a release that breaks one field, every purchase comes back 30, cardholders blame their cards, and no alert reaches the people who could fix it.

A response with no field 39, or with a code that is not on the network's list, decides nothing. Treat it like no answer: unit c9 reverses it.

Later Editions Put the Category in the First Digit

Field 39 in jPOS's packagers for 1987, 1993 and its own format, CMF, which follows the 2003 edition; then some CMF result codes and whether jPOS counts each as a success:

As in the 1993 edition, a CMF action code names its category in the first digit: 0 approved, 1 and 2 denied, 4 reversals, 8 network management, 9 other answers, errors among them. The 1987 codes have no such structure: 08 approves and 07 keeps the card.

The first digit is not "success or failure". 4000 accepts a reversal, 8000 a network message and 9001 an advice. A sender that treats every code outside 0 as a failure keeps resending a reversal the receiver applied long ago, then parks it for someone to look at. In 1987 the same acknowledgements are 00.

A Gateway Between Editions Translates Each Code From Both Lists

A gateway connects 1987 terminals to a processor that answers with CMF's four-digit codes. Its first version keeps the last two digits, since 0000 becomes 00. A second version uses a table built from both specifications and falls back on the category for codes the table lacks:

Which of these does the first version get wrong?

Every row after the first. In 1987, 08 is "honour with identification", so a lost card is approved once the thief shows an ID. 11 approves, so an issuer that timed out approves the purchase at the terminal while nobody upstream has. 07 is "pick up card", so while the issuer is down, every cardholder's card is kept. 02 turns a partial approval into a referral, 03 (invalid merchant) turns an approval into a decline, 35 tells the merchant to keep a card that is merely on a closed account, and 16, "approved, update track 3" in 1987, turns insufficient funds into an approval.

The editions number their codes independently, so a translation is a table. A code the table lacks can still be placed by its first digit when that says denial (1) or error (9). An approval can't: it may be partial, and passed on as 00 it gives goods away. For it, and for any code the gateway can't place, the terminal gets 96 and the purchase is reversed upstream.

Problem statement

Your gateway connects 1987 terminals to a processor that answers with four-digit action codes. CodeTranslator holds a table, written code by code from both networks' lists, and tells each terminal what the processor decided. answerFor and mustReverse already work on top of toTerminal.

The processor's release notes add codes faster than the table is updated, and during last week's upgrade some answers arrived with no action code at all. Operations asks for three things: no terminal hands over goods the issuer may not have approved in full; no cardholder is told their card was refused when it was a system that failed; and no purchase is reversed when the processor plainly refused it.

Finish toTerminal in src/main/java/com/example/practice/CodeTranslator.java. About ten lines.

The tests use a table of their own and codes it doesn't list.

Summary


  • Several codes approve, and 10 covers only part of the amount. An approval read as a decline commits money that nothing gives back.
  • A decline is final for its request. Resending gets the same answer, and a resent 55 is one more wrong PIN. The code says whether the cardholder, the merchant or a phone call could change it.
  • An error code reports a failure, not a decision. 30 means fix your message, 91 and 96 a new transaction later, 63 an alert about the keys. A missing code decides nothing.
  • Later editions put the category in the first digit, and acceptances such as 4000 sit outside category 0.
  • A gateway translates each code from a table. Digits don't line up between editions; a denial or error off the table falls back on its category, and an approval it can't read is reversed.

Challenges


  1. A fuel pump asks for 100.00 and gets 10 for 60.00. What should the pump let the customer take, and which message tells the issuer what was actually taken (unit 4)?
  2. The processor's next release adds six codes your gateway's table lacks. How would you notice, before a cardholder does, that one reached the fallback?
  3. A switch answers 68, response received too late, to a purchase it gave up waiting for. What does the acquirer know about the money, and what should it do?


Design Note: Why Two Characters Became Four Digits


In 1987 approvals, declines and errors share one unordered list, so a code one side adds means nothing to the other until both update. The later editions' first digit lets a receiver act on a code it has never seen. The cost is a second numbering, and a table in every gateway between them.
