You start a new client for the first time. Q2 reports that it deployed the channel and the multiplexer, your code sends an 0800 echo, and after the full timeout the answer is null. Is the host down, or is the client wired wrong?

Your code sees nothing come back either way. The client itself can tell the two apart, if you know what each of its pieces does and what it reports when something is missing. The unit has six rules, one per section heading. Every output is from a jPOS 2.1.7 client talking to a small host on 127.0.0.1:8000 that answers every request with 39=00.

Q2 Builds the Client From the Files in deploy/

A jPOS client is a directory with three descriptors in it:

Q2 is the jPOS runtime. You start it with org.jpos.q2.Q2 as the main class and the project root as the working directory. For every file in deploy/ it creates the component the file names, configures it from the XML and starts it. Such components are called QBeans. Q2 started from /iso-client, then stopped with Ctrl-C:

Q2 initialises every new file in name order, then starts them in the same order, and stops them in reverse. 00_logger.xml is the one fixed name: Q2 deploys it first, even before it logs "Q2 started". The other prefixes are a convention (10_ channels, 20_ multiplexers, 30_ transaction managers, 50_ servers) that puts each component after the ones it uses.

Q2 also watches the directory. A new file is deployed, a deleted one undeployed. Change one, even just its timestamp, and Q2 throws the running component away and builds a new one. Touching 20_host_mux.xml while the client runs:

So you never create the channel or the multiplexer in your code, or as Spring beans configured with setters. A QMUX built with new has no queues, is never started, and is registered under no name.

Versions. The course runs on jPOS 2.1.7, Java 17 and Maven, the combination the practices are graded on (the build file is in 1.8). 2.1.x is jPOS's maintenance ("tail") line and 2.1.9 is its latest release. jPOS 3.x is the current line; it needs Java 23 or later and its tooling is Gradle-based. Unit s13 lists what changes there.

Licence. Q2 prints its licence when it starts: jPOS Community Edition, licensed under GNU AGPL v3.0. If users reach your modified jPOS application over a network, the AGPL requires you to offer them its source. The jPOS project sells a commercial licence for those who can't.

The Channel and the Multiplexer Share Only Two Queues, and the Queues Cross

The ChannelAdaptor owns the TCP connection. It connects, reconnects when the link drops, sends every message that appears in one queue and puts every message it receives into another. It knows nothing about requests and responses. The QMUX knows nothing about sockets: it writes requests to one queue, reads from the other, and hands each response to the thread waiting for it. The queues live in a Space, the in-memory store that jPOS components share. The channel logs each connection attempt (<connect>) and every message it sends (<send>) and receives (<receive>) to the logger named in logger="Q2", which 00_logger.xml defines (1.6). Unit c3 covers the adaptor in depth, unit c4 the multiplexer.

deploy/10_host_channel.xml:

deploy/20_host_mux.xml:

Each component names its queues from its own point of view: <in> is what it reads, <out> what it writes. The adaptor reads host-send and writes it to the socket; the multiplexer writes host-send. So the multiplexer's <out> is the adaptor's <in>, and the other way round. <unhandled> is where the multiplexer puts a message that no request is waiting for (1.5.1).

The mistake is to make the two descriptors look alike. With the adaptor's values in the multiplexer, <in>host-send</in> and <out>host-receive</out>, one echo with a five-second timeout gives:

The request went into host-receive, which only the multiplexer was meant to read, and nobody read it. The channel's log has no <send> entry, and the host's log stays empty. To the caller this looks exactly like a host that doesn't answer.

Q2 fills in the ${host.address:127.0.0.1} values when it reads the file. jPOS looks for an environment variable (host.address, then HOST_ADDRESS), then a Java system property, then cfg/default.yml, and uses the text after the colon only when all of them are missing. Started with HOST_PORT=8001, with -Dhost.port=8001, and with port: 8001 under host: in cfg/default.yml, the client connected to port 8001 each time. Keep real host names and credentials out of the descriptor.

isConnected() Knows About the Link Only Through <ready>

While its connection is up, the adaptor keeps an entry named after itself plus .ready (host-channel.ready) in the Space, and removes it when the connection drops. The multiplexer's <ready> points at that entry, and isConnected() does nothing more than check that the multiplexer is running and look for it.

Here the host is stopped for maintenance, so every connection attempt is refused. First without <ready>, then with it:

With <ready>, the client can answer the opening question:

  • isConnected() is false: the link is down. The channel's <connect> entries in the log say why (Connection refused, for instance).
  • isConnected() is true, and the channel never logged a <send>: the request didn't reach the adaptor. Check the queue names.
  • The channel logged a <send> and no <receive>: the host has the request and didn't answer.

Without <ready> the first case looks like the second, and you debug the queue names while the link is down.

  1. Coding practice

    Give a second link its own multiplexer

    • The multiplexer writes requests to the queue the adaptor reads and reads the queue the adaptor writes; with the names copied instead of crossed, every request waits out its timeout and the host sees nothing.
    • isConnected() looks only for the ready entry named in <ready>, the adaptor's name plus .ready; without it a dead link reports connected.

request Returns null When Nothing Comes Back


The first code you write is an echo: the 0800 network message with field 70 set to 301, which asks the host "are you there?".



The channel's log for one call:



(1) Check the link before you send. In 2.1.7 a request on a dead link doesn't fail at once: request never looks at isConnected(). It puts the message in host-send with the timeout as its lifetime and waits. Here the link is down when the client calls request with a 15-second timeout, and the host comes back three seconds later:



The request waited in host-send until the adaptor's next connection attempt, ten seconds after the refused one (its <reconnect-delay>), and then went out. A purchase would have kept the cardholder waiting ten seconds, and with a slightly later reconnect it would have expired unsent and request would have returned null. With <ready> configured, false from line (1) means nothing was sent, so you can say "host unavailable" right away.


(2) null is how jPOS says "no answer". request doesn't throw when the time is up; it returns null, and every call site has to check for it. Code that goes straight to response.getString(39) passes every test against a quick host and throws a NullPointerException the first time the host is slow. For an echo, null only means that the host didn't answer. For a purchase it means you don't know whether the host took the money: you reverse it, never simply send it again (unit c12).


The STAN (field 11) comes from one counter for the link, kept in the Space. Unit c2 explains why it must never be random.


Your Code Finds the Multiplexer by Name, Inside Q2's JVM, When It Needs It


Q2 registers the multiplexer under its name in the NameRegistrar, a registry inside the JVM, and QMUX.getMUX("host-mux") looks it up.


The lookup works only in the JVM that runs Q2. A Q2 in another process is invisible. An application with its own main starts Q2 itself, as a library, with the same deploy/ directory:



The multiplexer exists only after Q2 has deployed it, and is connected only later. The same JVM, asked at three moments:



q2.ready(...) returns once every descriptor is deployed. The channel connects on its own thread a moment later, so ClientApplication waits for host-channel.ready with Space.rd, a read that blocks until the entry appears or the time runs out.


A redeploy replaces the object (the three log lines at the end of 1.1).


Spot the Problem: The Cached Multiplexer


A payment service looks the multiplexer up once, when it starts, and keeps it in a field:



One afternoon an operator renames the unhandled queue in 20_host_mux.xml. From then on every request returns null, while the host is up and answering.


One echo, then a touch of 20_host_mux.xml, then one echo through the kept reference and one through a fresh lookup:



The host's log shows all three echoes arriving, and it answered each one. Q2 stopped the old multiplexer and deployed a new one under the same name. The old object still writes to host-send, so its request went out, but a stopped multiplexer no longer reads host-receive. The new one read the answer, found nobody waiting for it, and put it on the unhandled queue.


Look the multiplexer up each time you use it. The lookup is a map read. Catch NameRegistrar.NotFoundException and report it as "not deployed", a different problem from "link down".


Spring Starts and Stops Q2, and Nothing Else


jPOS 2.1.7 has no Spring integration of its own. In a Spring Boot application, for example a REST service that forwards payments, Q2 still runs the channel and the multiplexer from deploy/. Spring only starts Q2 with the application and stops it on shutdown:





One call to the service, then one after the context closed (Q2 undeployed both descriptors):



Spring starts lifecycle beans such as EmbeddedQ2 only after it has created every ordinary bean. A service that calls QMUX.getMUX in its constructor therefore runs before Q2 exists, and the application never starts: the constructor threw NotFoundException: mux.host-mux, and Spring gave up on the context.


Connection and send failures happen on the channel's own threads. Spring's @ControllerAdvice never sees them; they are in the jPOS log. Only what request throws to its caller, such as an ISOException, reaches the web request's thread.


Spring versions. The example uses Spring Boot 2.6 (spring-boot-starter), the line built on the Spring 5.3 that the course pins. Nothing in it depends on that version.

The Log Is Masked Before Anything Writes It


The channel logs every message it sends and receives, field by field. A purchase carries the card number (field 2), track 2 (field 35) and the PIN block (field 52). deploy/00_logger.xml keeps them out of the log in clear:



A logger hands each log event to its listeners in the order they are listed. SimpleLogListener writes to the console, RotateLogListener to log/q2.log. ProtectedLogListener writes nothing: it masks the fields listed in protect and blanks the ones in wipe, in the event that the listeners after it receive. One purchase with the test card 4111111111111111:



The log is masked, and the message on the wire is not. With SimpleLogListener moved above ProtectedLogListener, as someone might to "see the messages sooner", the console shows:



log/q2.log is still masked, because its listener still comes after the masking one. Whoever checks the log file finds nothing wrong, while the console, and whatever collects it from the container, holds card numbers and PIN blocks in clear. Put ProtectedLogListener first.


log/ must exist. Without it, Q2 prints a FileNotFoundException: log/q2.log warning among its first lines and keeps running, with the console working and nothing ever written to the file.

Summary


  • Q2 builds the client from deploy/, in file-name order, stops it in reverse, and replaces a component as soon as its file changes. A QMUX created with new is one that nothing can find.
  • The queues cross. The multiplexer's <out> is the adaptor's <in>. Get it backwards and every request times out while the host sees nothing.
  • isConnected() is only as good as <ready>. Without it a dead link reports connected, and a link problem looks like a wiring problem.
  • null means no answer, and a request on a dead link waits and may go out late. Check the link first, so that each outcome means one thing.
  • Look the multiplexer up when you use it, in the JVM that runs Q2. A kept reference stops hearing answers after a redeploy, and a lookup in a Spring constructor runs before Q2 exists.
  • Mask first. ProtectedLogListener protects only the listeners listed after it.

ProtectedLogListener: protect lists fields to mask (a PAN keeps its first six and last four digits); wipe lists fields to blank. It changes the log event only, never the message.


Challenges


These have no single answer.


  1. Your client runs in a container that ships its console output to a central log service. Which listeners do you keep, in which order, and how would you prove in a test that no card number leaves the container?
  2. A request made on a dead link waits in host-send for up to its timeout. Pick a timeout for an echo and for a purchase, given a <reconnect-delay> of 10 seconds. What does each choice cost when the link comes back after 4 seconds, and after 12?
  3. Operations want to change the host's port without restarting the client. Compare editing 10_host_channel.xml, changing cfg/default.yml, and changing an environment variable. Which of them take effect without a restart, and what happens to a request in flight?
  4. Your Spring service must answer "is the host reachable?" in under 100 ms for a load balancer's health check. What can it look at without sending anything, and what can't it know that way?


Design Note: Why Queues Between the Channel and the Multiplexer?


The adaptor and the multiplexer could have been one object that sends a request on the socket and reads the response from it. jPOS puts a pair of Space queues between them instead, at the price of two names to keep in step and a ready entry to tie the two components together.


In return, the adaptor can drop and rebuild its connection while the multiplexer sees only the ready entry come and go. Anything that reads and writes the two queues can stand in for the adaptor: unit c12 replaces it with a test host in the same JVM, and the multiplexer can't tell the difference.


A wrong queue name doesn't throw; it only makes requests wait. With <ready> in place and the channel's log in view (1.3), a wiring mistake shows up the first time you send an echo.
