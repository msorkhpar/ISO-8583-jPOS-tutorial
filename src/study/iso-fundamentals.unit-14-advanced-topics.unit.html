  14. Check yourself: what an authorization proves, and what a token protects

A web shop's order table leaks: 40,000 card numbers, each with its expiry date. What can a thief do with them? That depends on what else an authorization carries besides the card number, and on whether the shop had to keep the numbers at all. Five rules, one per section heading.

A Chip Purchase Carries a Cryptogram Over Its Own Data, So Nobody on the Path May Change That Data

A card number printed on plastic can be copied by anyone who has seen it. A chip can't be copied the same way: for each purchase it computes a cryptogram, the ARQC in tag 9F26 of DE 55 (unit 3). The cryptogram is a MAC (unit 8) under a key that only the chip and its issuer hold. It covers the amount, the currency, the date, the transaction type, a random number from the terminal, the card's transaction counter and a few more values, each of them also a tag in DE 55. The issuer recomputes the MAC from the tags it receives. A match proves that this card took part in this purchase, and that the values it covered arrived as the card saw them. A thief with the leaked table has no chip and no key.

A restaurant's gateway adds a 2.50 tip to a 25.00 chip purchase before forwarding it. Someone has noticed that field 4 and tag 9F02 (the amount) should agree, so the gateway updates both:

In the program, a retail MAC (ISO 9797-1 algorithm 3) under a test key stands in for the card's cryptogram. Each run prints the cryptogram as received, then whether the issuer's recomputation matches it:

The issuer finds each covered value by its tag, so their order in DE 55 doesn't matter: the gateway's code moved 9F02 to the end, and only its new value broke the match. The rewritten 9F02 breaks the cryptogram, and an issuer that checks it treats the card as counterfeit: most decline every tipped chip purchase in the restaurant. Changing field 4 alone keeps the cryptogram intact, because the cryptogram can't see field 4, but it asks the issuer to approve 27.50 on a card that agreed to 25.00. The issuer's comparison of field 4 with 9F02 catches that (unit 18). The tip belongs in the completion or the clearing record, as the network's rules say (unit 19), not in the authorization.

DE 55 also carries the terminal's own checks (tag 95), which the issuer reads together with field 22, the way the card number was read (chip, contactless, or magnetic stripe after the chip failed). Nobody on the path changes a tag the cryptogram covers. Pass DE 55 on as it came, unless the network's specification tells you how to re-wrap it.

A 3-D Secure Result Rides in the Authorization, and a Hop That Drops It Drops the Proof

Online there is no chip, and 3-D Secure proves the cardholder instead. Before the shop asks for the authorization, the issuer authenticates the customer: from device and purchase data alone, or, when it wants more, with a challenge in its app or a code. The result comes back to the shop as a few values:

  • the ECI (electronic commerce indicator), which says whether the cardholder was authenticated;
  • the authentication value (CAVV at Visa, AAV at Mastercard), a cryptogram the issuer can verify;
  • the directory server transaction ID and the protocol version.

The shop's gateway must put these into the authorization, and every hop after it must keep them. This gateway copies a fixed list of fields upstream, a list written when it carried only card-present traffic. The 3-D Secure values sit in field 48, in a layout made up for this example, and 22=812 is this network's code for an e-commerce purchase:

The customer did authenticate, but the authentication happened outside the authorization, and the authorization is all the issuer gets. It sees an e-commerce purchase with no result attached. Where the law requires strong customer authentication online, as in the European Economic Area, the issuer usually declines it with a code that asks for authentication, unless an exemption applies. Elsewhere it may approve. Under most networks' rules a fraud chargeback on an authenticated (or attempted) purchase falls on the issuer, and on an unauthenticated one on the merchant, whatever the amount: what decides it is whether the result reached the issuer in the authorization. So the thief with the leaked table can still buy at shops that skip 3-D Secure and don't ask for the CVV2, and those shops pay.

The authentication value proves one authentication for one purchase. Treat it like authentication data and keep it out of logs (unit 8).

Networks differ. Each network defines where the 3-D Secure values go in its 1987-based messages, often a private field with tagged subfields. On a 2023 link they go in the datasets of DE 34 (unit 17). Take the layout from your network's specification.

A Token Is Random, Shaped Like a Card Number Under a BIN of Its Own

The shop in the opening kept card numbers so that returning customers could pay with one click. It needed something that leads back to the card, not the card number itself. A token replaces the card number in every system that doesn't need the number: the shop's database, its logs, its analytics. A vault keeps the card number, sealed, and maps each token to it.

Three tokens under the made-up token BIN 990001:

Nothing in a token comes from the card. The obvious shortcut, encrypting the card number or hashing it, gives a value that can be turned back. Whoever holds the key decrypts every token at once. Unit s9 showed that an unkeyed hash of a card number whose BIN and last four digits are known is reversed by trying about 100,000 candidates, in a quarter of a second. A token that keeps the card's last four digits gives part of the number away; the vault can keep them as display data instead. With random digits, the leaked token table is only a list of numbers, and the vault holds the only map back.

The token looks like a card number so that every system on the way accepts it: field 2, a database column sized for 16 digits, the Luhn check that unit 10 described. The BIN is reserved for tokens. Without it, a random 16-digit number with a correct check digit can be a real card number: if a token escapes into a system that doesn't recognise it, the number is routed to the issuer of that range and can be approved against a stranger's card. A range your network has assigned for tokens can't collide with a real card, and any system can see from the first digits that it holds a token. The 990001 above is made up.

Network tokens. The tokens on this page belong to a merchant's or gateway's vault and are turned back into card numbers before anything goes to the network. Card networks also issue tokens of their own (EMVCo payment tokens), which travel to the network in field 2, usually with a cryptogram, and are turned back by the network's or issuer's token service. The design rules are the same.

A Token Belongs to the Requestor It Was Issued To

One customer pays at a bookshop and at a florist, both through the same gateway. Should both shops get the same token for that card?

A single token per card is tempting: it works like a customer ID that every shop shares. But then a token leaked from the bookshop pays at the florist, and anyone holding both shops' data can follow the customer from one to the other. So the vault issues tokens per requestor, the party that asked for them. It finds an existing token through the keyed lookup value of unit s9, never through the card number:

The bookshop gets the same token on every purchase, so one-click checkout and refunds keep working. The florist gets a different one. When the gateway receives a token, it uses it only for the requestor it was issued to.

  1. Issue tokens that nobody can mistake for cards or trace back to them

    • A token is issued per requestor and found through the keyed lookup value, never the card number, so a token leaked from one merchant is useless at another.
    • A token's digits are random, not derived from the card; it has sixteen digits and a correct check digit so card-number systems accept it, and a reserved BIN so it can never be a real card; a draw already taken is drawn again.

Only the Component That Builds the Network Message May Turn a Token Back Into a Card Number


The bookshop's developers ask for the right to detokenize: their refund screen wants to show the full card number.


That undoes the whole design. The thief who breaks into the bookshop's app now calls detokenize with the app's own credentials and gets every card number back. The app and its database are back in PCI DSS scope (unit 13). Tokenization is worth something only if it changes where card numbers can be read. So detokenizing is a separate permission, held by one component: the one that builds the ISO 8583 request for the network, here called the station. It acts for one requestor at a time:




The shop app may create and revoke tokens, and show display data kept beside them, such as the last four digits and the expiry date. A token the vault doesn't know, one revoked, or one presented for another requestor gets the same refusal, and the transaction stops before anything reaches the issuer. After a revoke the card gets a new token. The CVV is never stored, so no detokenization can return it.


The card number still leaves the vault for each authorization, but only to the station, inside the systems that are in PCI DSS scope anyway.

Summary


  • A chip purchase carries a cryptogram over its own data. Anything that changes a value the cryptogram covers makes the issuer see a counterfeit card, so DE 55 passes through unchanged.
  • A 3-D Secure result rides in the authorization. A hop that drops it turns an authenticated purchase into an unauthenticated one: declined where the law requires authentication, and a fraud chargeback for the merchant elsewhere.
  • A token is random, under a BIN of its own. A token derived from the card number can be turned back; one outside a reserved range can be a real card number.
  • A token belongs to its requestor. A token leaked from one merchant pays nowhere else, and tokens don't link a customer across merchants.
  • Only the component that builds the network message may detokenize. A merchant app that can detokenize puts every card number back in reach of a breach.

  2. Your vault issues 16-digit tokens under one 8-digit token BIN. How many tokens can it issue before a new draw collides more than one time in a hundred, and what do you do before that?

  4. A subscription service charges every month without the customer present. Which of this unit's proofs can such a charge carry, and what does the issuer rely on instead?


Design Note: Why Tokens Look Like Card Numbers


A token could be anything, a UUID or a random string. Many gateways make it a number of card length with a correct check digit because of everything already built around card numbers. Field 2, the card-number columns of databases, the validation in checkout forms and reports expect (usually sixteen) digits that pass the Luhn check. A token in that shape replaces the card number without changing any of them, and a merchant can switch to tokens system by system.


The price is that a token can be mistaken for a card. Length and check digit can't tell a token from a card number; only the reserved BIN can. Assessors have to check which systems see which ranges, and a token range that overlaps a real one turns a harmless number into someone's card. Some gateways choose the other side of the trade: tokens that deliberately fail the Luhn check, or contain letters, so nothing can take them for cards, at the cost of changing every system that stores them.
